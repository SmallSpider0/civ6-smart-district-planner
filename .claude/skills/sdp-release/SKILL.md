# Releasing vX.Y.Z

Who decides: every release waits for the maintainer's word ("发 vX.Y.Z"); a critical bug fix is reported at once (docs/maintaining.md §2 step 6). The version digit: docs/maintaining.md §9.

- When a milestone's issues are done, do §1 steps 0–6 (tests, screenshots, version, notes, report), report it ready (what is in it, what the tests showed, what is left, and the open issues labelled `workflow` for the maintainer to decide: docs/maintaining.md §10 "工作流怎么改") and go on with other work. After the word: §1 step 7 and §2.

Bug-fix PRs merge into `main` as usual in the meantime: `main` reaches no player. Windows is not tested before a release. This file is the release checklist.

## 1. Before the PR (on a release branch: the milestone's issues are merged one PR each)

0. Keep the screen from locking from the start of the release work (sdp-game-test, Before 1): it runs for hours and touches the game.
1. Every issue of the milestone is closed by this PR or moved on.
2. Tests (sdp-game-test, sdp-offline-runs), heavy ones on the second machine while the game tests run here. Book the game for the release tests when another session holds it (`sdplock.py take --next`). Real clicks, screenshots, the stress test and the three rulesets take the screen: when someone works on the machine they go into the night queue (sdp-game-test, When), so a release is often prepared by day, tested in the free hours and published after. Everything that does not need the screen is done first:
   - `python3 -I tools/validate.py`, `node tools/offline_tests.mjs`;
   - `python3 -I tools/run_tests.py --rulesets all`, plus Gathering Storm in English when the UI or text changed;
   - `python3 -I tools/realclick.py suite` when the UI changed;
   - `python3 -I tools/refresh_results.py --check --if-changed` (on the second machine; fetch `tests/compare/results/check_stamp.json` back and commit it): it skips the run when no solver, legality, panel-default or comparison file changed since the last stamped check, which the solver PRs run; explain any lower gain or new violation;
   - numbers in the report page whose source changed (the records in docs/notes/ name them; tooltips carry no measured numbers since #153);
   - stress test: load/run/check on the three saves, `tools/refresh_stress_md.py`. Skipped when the release changes only the interface: `git diff vLAST..HEAD -- SmartDistrictPlanner/Scripts` touches nothing but `SDP_Page*.lua` and `SDP_Preview.lua`, and the panel's changes do not alter what is sent to the solver. Say in the self-test report that it was skipped and why.
   - A bug these tests find is fixed now, without waiting for anyone's word (maintainer, 2026-11-07: a release waits for its fixes, not for a confirmation): one issue per bug (`bug`, `auto`, this version's milestone), reproduce it first, one PR each with a test that fails on the old code and Codex as usual (sdp-issue §4). Only a subjective choice in the fix (docs/maintaining.md §2 step 2) is written on the issue and waits; the rest is fixed. The release is ready, and its PR's auto-merge goes on (step 7), only when these fixes are merged and the affected tests pass again.
3. Screenshots when the UI changed: `shots.py` (zh and en, new round number in the name), point README, the report templates (`report/template.html`, `template_en.html`: image names, alt text and captions) and `workshop/src/*.html` at them, `tools/workshop.py render`, look at `workshop/images/`. Open `workshop/preview.jpg` too: the cover must be the one the Workshop item uses now (a new cover needs the item's owner).
4. `python3 -I tools/release.py prep X.Y.Z` (sets the modinfo version +1 and `VERSION` in `SDP_Panel.lua`, which the launch bar tooltip shows and validate.py checks against CHANGELOG; collects `changelog.d/*.md` by number into the new CHANGELOG section and deletes them; commit the deletions too), then write the change note's English half and shorten the Chinese half (players' words, no issue numbers). Typographic quotes in the note (`workshop.py check` refuses `"`).
5. Documents, every release (not only when a feature looks big): for each line of the release's CHANGELOG section, find every player-facing place that still describes the old behaviour, number or limit, and update it. The places:
   - README (en and zh), `docs/install-and-test.md`, `docs/install-en.md`, `docs/tester-guide.md`;
   - `workshop/description.bbcode` and `description_zh.bbcode`, the text inside the diagrams `workshop/src/*.html` (then `tools/workshop.py render`);
   - the report pages: `report/template.html`, `template_en.html`, the appendix parts `report/part_*.html`, sentences `report/build.py` writes;
   - the similar-mods table `report/similar.py` (our own entries: what we plan, the limits, rulesets, languages; it feeds README and the report) and `docs/notes/planner-comparison.md`;
   - the panel's tooltips in `SmartDistrictPlanner/Text/*.xml` that name the changed value.
   Method: grep these files for the old numbers and words of each change (e.g. after #142: "8 座", "eight cities", "at most 8"), in both languages. In the PR body, list each CHANGELOG line with the files changed for it, or "nothing to change" and what was searched.
6. Self-test report: a short block for this round at the top of "自动化测试结果" (tests and counts, what was checked by hand, what was not). Keep only the last two rounds there (git has the rest).
7. Commit ("Prepare vX.Y.Z"), push, one PR (title in English imperative; `Closes #N`; tests and platform; generated files and commands; ends with the session's PR footer). Auto-merge (squash) and Auto-fix on, once step 2's bug fixes are merged. Then `python3 -I tools/pr_wait.py add N` (the watch side session's standing wait picks it up) and go on to §2 when it reports the merge: a green CI run or an auto-merge wakes nobody (docs/maintaining.md, "子 agent 怎么派" 3, 5).

## 2. After the merge

1. `python3 -I tools/release.py notes X.Y.Z`; read `logs/release-vX.Y.Z.md` (English first, Chinese after, written for players; bold lead words per item are fine). The status page's "最近发布" takes each item's opening words of the notes' "since …" section: if that summary reads badly, fix the notes.
2. `python3 -I tools/release.py publish X.Y.Z`: release on main's commit, waits for the four files, checks GitHub Pages.
3. `SDP_STEAM_LOGIN=... python3 -I tools/release.py workshop X.Y.Z`: uploads (content, English title and description, change note; no preview image: the uploader is a contributor), downloads back, compares. The collaborator can upload from Windows instead (docs/workshop-upload.md). If SteamCMD wants a password, stop and give the person who owns the login the command it prints; never type credentials.
4. Item page, as the script's last line says (from the package's UPLOAD.md). Use Claude in Chrome, signed in to Steam as the contributor (the built-in browser's Steam sign-in drops). Before the first step run `list_connected_browsers`. If no browser is connected: `open -a "Google Chrome"`, wait about 20 seconds, `list_connected_browsers` again; up to 3 tries. Only after the third failed try report Chrome unreachable (status page and the maintainer). Never hand the item page to another session without these tries. Never type a password or code, and never confirm Steam's "sign out other sessions" prompt. When the item page is done, close every Chrome tab and quit Chrome (`osascript -e 'tell application "Google Chrome" to close every window' -e 'tell application "Google Chrome" to quit'`).
   - Simplified Chinese title and description: in Chrome, `https://steamcommunity.com/sharedfiles/itemedittext/?id=ITEM&language=6`, set `#description` to `description_zh.txt`, check the diff is only the intended lines, `ValidateForm()`, reload and check.
   - Pictures: in Chrome (its `file_upload` puts the file on the input), `managepreviews/?id=ITEM`: put the new file on the file input, click 上传, delete the old picture (hover its tile, then click the × at the tile's top right; a scripted click on `#preview_<id> a.btn_grey_black` did not delete; on 2026-11-03 calling `RemovePreviewForPublishedFile(document.getElementById('preview_<id>'), publishedfileid, '<id>')` in the page did, which is what that link runs; tiles are identified by the hash in the image URL, which matches the file name's suffix), reload the page (after a delete `SortPreviewImagesByFileName()` throws until reloaded), sort by running `SortPreviewImagesByFileName()` in the page (clicking 文件名 did not reorder on 2026-10-26), 保存并继续, then check the item page's order.
   - Pictures inside the description (`workshop/inline/`, listed with their placeholders): upload each new or changed one as a Steam artwork in Chrome (`https://steamcommunity.com/sharedfiles/edititem/767/3/`; name "智能区域规划器：<what>（中文 / English）", visibility 公开, tick the ownership box: the images are the project's own), copy the `images.steamusercontent.com` address from the artwork page, put it in place of the placeholder in both description files (commit it), and set the item page's descriptions from those files. Never put them in `managepreviews` (that is the carousel). Leave old artworks; deleting them is the maintainer's call. Done by the agent without asking (maintainer, 2026-10-30).
   - A new preview image needs the item's owner (DracoYus).
5. Close the milestone, `python3 -I tools/worktree.py prune --remote --yes` (a release branch goes once its fix is merged back into `main`: the tag keeps the version), and report: the release link, what was checked, what was not, and the Workshop comments and discussion posts whose problem this version fixes, each with a short draft reply (sdp-watch "Steam Workshop comments"); send none before the maintainer confirms it.
6. Post the confirmed Workshop replies. Put the `workflow` issues the maintainer adopted into one docs-only PR, with docs/workflow.html brought up to date; when the clean-up below is due, it is that PR. No new session follows a release: the main session stays, and the maintainer clears it when they like (docs/maintaining.md §4 item 5).
   - The draft replies from step 5 wait for the maintainer. Post each one they confirm from the main session, in Chrome on the item page (as in step 4), then quit Chrome.
   - Clean-up: when it is due (docs/maintaining.md §9); the last one is the bottom row of `docs/notes/rules-cleanup.md`. Send one subagent (Opus, medium) for two things: the maintainer's local memory and personal rules on this machine, and one docs-only PR for the repository's rule documents (AGENTS.md, CONTRIBUTING.md, docs/maintaining.md, `.claude/skills/sdp-*`, docs/workflow.html, the workflow parts of tools/README.md). It removes only what is repeated (one place keeps it, the others point there) or outdated (overruled by a later rule, or about a tool, option or file that no longer exists), shortens long incident accounts and statistics to one sentence of reason, never changes what a rule says, keeps what it is unsure of and lists it for the maintainer, and adds a row to `docs/notes/rules-cleanup.md`. Its PR merges by auto-merge.

## 3. Other cases

- **A few testers first**: tick pre-release when publishing, tag like `v1.1.0-rc.1`. Only the zip and the single-file pages are attached; the web pages and the Workshop package are not updated.
- **The live version is badly broken while `main` holds unready changes**: branch `release/1.0` from the last tag, fix it there, release v1.0.1, merge the fix back into `main`, then delete `release/1.0` (the tag keeps the version; branch from the tag again for another fix; `prune --remote` deletes it too).
- **A package for testers between releases**: `python3 -I tools/package.py` locally; named by the commit, with `TEST_GUIDE.md`.
