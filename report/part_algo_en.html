A.1Incremental, memoized evaluation (SDP_Board)

DMT scores a district only by its own tile and the 6 tiles around it, so the score depends on three things: the district type, the tile, and what is planned on the 6 neighbors. When a district moves, only the districts around its old and new tiles need a new score; each score is looked up in memory first, and DMT is called only when it is not there.

Pseudocode 
function score(district, tile)
    -- neighborCode: one digit per direction, the object planned on that neighbor
    key = (district.type, tile, neighborCode(tile))
    if memory[key] exists then return memory[key] end
    lay out this situation on the overlay; clear DMT's tile cache
    memory[key] = Σ weight[yield] × DMT.GetBonusYields(district)[yield]
    return memory[key]
end

function place(slot, newTile)                     -- Board:Put
    affected = {slot} ∪ objects on the old tile's 6 neighbors
                      ∪ objects on the new tile's 6 neighbors
    for obj in affected do total = total − oldScore[obj] + score(obj, obj.tile) end
end

A.2One-city search (SDP_Search)

First a cheap linear model picks a set of good layouts from a very large range; DMT then scores them exactly; finally local search and “remove a patch and place it again” correct the model's errors. The model only decides where to look; every final score comes from DMT.

Model score = each district's score alone + the mutual bonus of each pair of adjacent districts − the loss from taking good tiles; it is used only for ranking. Land loss: k specialty districts need population P = max(population, 3k − 2), the city works its best P tiles, and a tile taken loses its yield minus that of the (P+1)-th best tile.

Picking from the pool: given a number of districts, the ones beyond the Must ones are picked from the pool.

Distance cost, automatic districts, reminder tacks: the distance cost is a fixed deduction per candidate tile, added straight into the exact score and the model score. Automatic Aqueducts and Dams are added to the Must ones before solving, according to the city's situation. Reminder tacks are worked out once the plan is settled: DMT computes again without seeing an adjacent Woods or Rainforest tile, and if the bonus drops, that tile gets a reminder.

Pseudocode 
function solveCity(city, districts, effort)
    table = baseTable(districts, the city's candidate tiles)
    if number of layouts ≤ effort.exhaustiveLimit then best = exhaustive(table)
    else
        beam = beamSearch(districts by mutual bonus, most first, effort.beamWidth)
        best = among the effort.shortlist layouts in the beam with the best
               model scores, the one with the best DMT score
        localSearch from the first effort.starts of them
        then effort.rounds rounds of perturbAndRebuild
    end
    if no complete plan then                    -- leave out 1, then 2, ...
        for leftOut = 1, #must − 1 do
            solve the rest for each way of leaving out that many
            if found then break end
        end
    end
    return best, quality(best, model upper bound)
end

function solvePool(must, pool, count, effort)
    combos = every choice of (count − #must) from the pool, exclusive ones
             dropped (keep-apart ones only when short of the count),
             sorted by optimistic score
    for combo in the first effort.combos of combos do
        if optimistic(combo) ≤ the third best's real score then break end
        roughSolve(must + combo)
    end
    swapTypes(top three); solve the top three fully at this effort
    return three plans with different combinations
end

A.3Several cities together (SDP_Multi)

The cities share one table of candidate tiles: a tile two cities can both use may go to either, but holds only one object; bonuses across cities count as usual. The search reuses the one-city engine in blocks by city: one city is solved again at a time while the others stay fixed. Different starts lead to different local optima, so a fixed set of starts is run and the best result kept.

The plan takes in every site tack and your existing cities within 7 tiles of a new one, 8 cities at most. An empire-limited district (Government Plaza) gets only the slots still free, on the candidate tiles of each city whose list has it. Coverage (Reach) is off by default; when on, a district whose buildings help the cities around it, such as a Factory or a Zoo, earns the weight for each additional city of yours it covers; the radius is read from the rules.

A.4City sites (SDP_Sites + SDP_SiteSolver)

K sites are picked from a hundred or more candidates: a cheap rough score filters first, then only some sites are scored with a district plan, and finally a combination search runs over the sites scored that way.

A.5Computing over several frames (SDP_Task)

The game's UI Lua has a single thread: a 6-second computation freezes the game for 6 seconds. Long computations run in a coroutine that computes one quota a frame and then yields; the quota adjusts to the length of the last frame. Between frames the hypothetical tacks are put away, so the rest of the game never sees them. The result does not depend on where the work is cut.

Work units: 1 DMT call = 1, 1 layout evaluation = 0.25, 20 model nodes = 1. Computing in one go, the game does about 20,000 units a second; over several frames, 7,400–9,900 a second for one city and about 15,000 for several cities.

A.6Housing and Appeal (SDP_Appeal)

G1

A Neighborhood gives Housing by its tile's Appeal; a Preserve gives Housing by its own Appeal, and the unimproved tiles around it yield more by their Appeal. Appeal itself changes with the plan, so each tile's Appeal under the plan is worked out first, then the rules tables are looked up.

This part = Housing weight × Housing + each yield's weight × the yields around the Preserve, minus the same without the plan (an existing or tacked Neighborhood that drops to a lower Housing level also counts). The yields around a Preserve count only for a Must Preserve: a Preserve picked from the pool counts only its Housing, and its yields are shown in the result, marked “pool pick, not scored”; otherwise late in the game the Preserve would almost always be picked first. When a district takes a tile with an improvement that gives Housing, such as a Farm or a Pasture, the Housing the city loses (the game adds up the per-tile Housing of the whole city and rounds down; a Farm gives 0.5) is shown on its own line in the result and not scored: counting it was tried, and with the panel's default settings both adjacency and city output got worse. A feature a district clears counts only for the tiles around it; the district's own tile keeps its Appeal (measured for Woods, Rainforest and Marsh). Every rule is read from the rules tables: AppealHousingChanges, Adjacent_AppealYieldChanges, and the Appeal values of districts and features; clearing a feature for a district needs the player to have the tech that removes it (Mining for Woods), and water tiles keep their Appeal. Calibrated in the game: within 4 tiles of the capital, all 61 tiles have the predicted Appeal; in three late-game saves the game built 9 plans the way a player builds them, and 7 of them had the predicted Appeal and Housing; in the other 2 a Neighborhood tile was off by 1, for reasons not yet found (B.8); the yields around Preserves match the rules table tile by tile.
