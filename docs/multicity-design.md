# 多城规划设计：城址 + 多城区域 + 奇观

**状态：已确认（2026-10-19，第 12 节的待定项按默认）。阶段 8–12 已完成（第 15、16 节），2026-10-20 在游戏内三种规则集下验证，并按实测校准了耗时（第 17 节）。合作者在 Windows 上实测后的 11 条反馈按第 20 节实现（阶段 14–18）。**第 8 节的耗时是开发前的推算，实测见第 17 节。各档质量来自离线基准（第 9.5 节），用的是简化的假 DMT；游戏内只验证了正确性和耗时，没有游戏内的质量基准。

本文描述新增的两步流程：
1. **选城址**：在已探索的地图上为若干座新城选位置，给出多套方案供预览和选择。
2. **多城区域 + 奇观**：对新城（及可选的现有城市）联合规划区域和奇观，同样给出多套方案。

单城规划的流程不变，新增**求解档位**和**继续优化**（第 7 节），并计入**占用地块的产出损失**（4.2，面板上可关闭）。单城求解算法在阶段 8 重写（第 15 节）：同样的耗时下质量明显更高，结果不再与旧版本逐位相同，改由基准测试保证不差于旧版本。

## 1. 与需求文档的关系

需求文档第二节的约束不修改，以下几处是本功能对它们的扩展，在此记录：

| 约束 | 单城规划 | 两步流程 |
|---|---|---|
| 3 目标函数 | 五种相邻产出加权和，另计入区域占用地块的产出损失（见 4.2，可关闭） | **第 1 步城址评分**另外计入地块产出、水源、资源、地貌等（见 3.3）；**第 2 步**在相邻加成之外计入区域、奇观占用地块的产出损失（见 4.2） |
| 性能（停顿 ≤ ~2 秒） | 快速、标准两档同步计算（≤ 0.8 秒）；精细档分帧 | **分帧计算**：每帧只算一小段，单帧停顿远小于 2 秒；总耗时更长，有进度条和取消 |
| 结果质量 | 两区域穷举时最优；三档可选，可继续优化 | **不保证最优**，改为四项可测试的保证（见 4.7）；三档可选，给出多套方案、质量指示，可继续优化 |

确定性（约束 6）完全保留：只遍历排序数组，预算按计数，同分有确定的决胜规则，结果与分帧方式无关（见第 6 节），也与机器快慢无关（见 7.1）。

## 2. 总体结构

```
SDP_Panel（面板，三个页签：单城 / 城址 / 多城；每页有档位选择）
 ├─ 单城：SDP_Solver（为一座城搭好问题，交给 SDP_Search）+ 档位 + 继续优化
 ├─ 城址（第 1 步）
 │   ├─ SDP_Sites       候选城址、各项因素、城址得分
 │   └─ SDP_SiteSolver  城址组合搜索、多套方案
 ├─ 多城（第 2 步）
 │   ├─ SDP_Multi       参与城市、格子归属、联合求解、增量评估、多套方案
 │   └─ SDP_Wonders     可规划奇观、奇观合法性
 ├─ SDP_Search          搜索引擎：单项表、穷举、模型集束搜索、局部搜索、扰动重建（单城和多城共用）
 ├─ SDP_Board           增量 + 记忆的 DMT 评估（4.6）
 ├─ SDP_Land            地块部分（4.2）
 ├─ SDP_Tiers           三档参数（单城、第 1 步、第 2 步集中定义在这一处）
 ├─ SDP_Task            分帧调度：进度、取消、局面变化检测、耗时统计
 ├─ SDP_Preview         地图预览：格子着色 + 地图图标，不打真钉
 └─ 复用：SDP_Overlay / SDP_Solver / SDP_City / SDP_Rules / SDP_Pins
```

两步之间通过**地图上的市中心钉**衔接：第 1 步采用的方案打成市中心钉（图标 `ICON_DISTRICT_CITY_CENTER`，DMT 会把它当作市中心计算）；第 2 步读取地图上全部市中心钉，包括玩家手放的。因此只用第 2 步也可以：玩家自己放市中心钉，再做多城规划。

## 3. 第 1 步：选城址

### 3.1 输入

- 新城数量 K（默认 3，上限 6）。地图上已有的市中心钉视为已选定的城址，另外再选 K 个。
- 最远距离 D（默认 8，可调）：每个城址离本国某座现有城市、或本方案里另一个城址不超过 D 格，允许"接力"向外扩张（见 3.5）。
- 计划的区域（所有新城共用一份，用于估算区域分和所需人口；第 2 步可按城修改）。
- 权重：预设或手动调整（见 3.3）。
- 方案数 N（默认 3）。
- 档位（见第 7 节）。

### 3.2 候选城址

候选为全部已揭示的格子，排除：
- 水域、山脉、不可通行的格子；
- 不能建城的地貌（`Features.Settlement = false`，如绿洲、自然奇观）；
- 他国领土；
- 与任何城市（含他国、城邦）或已有市中心钉距离不超过 `CITY_MIN_RANGE` 的格子。间距从游戏数据读（Base `GlobalParameters.xml:98`，值 3），不用 DMT 写死的 3（`IsValidCityCenterPosition`，`dmt_yieldcalculator.lua:613`），这样改了城市间距的模组也能算对；
- 三环内未揭示格超过一半的格子（信息太少，评分不可靠）；
- 离本国最近的现有城市超过 K × D 格的格子（接力也到不了；是否真能接力到，在 3.5 的组合搜索里检查）。

游戏的定居透镜接口 `Map.GetContinentPlotsWaterAvailability()`（`MinimapPanel.lua:565`）会返回"不能建城"的格子列表，用来交叉校验上述规则（覆盖范围需实测）。游戏 AI 的推荐城址 `GetSettlementRecommendations`（`WorldViewIconsManager.lua:710`）只作对照显示，不参与计算。

**两级筛选**：
1. **粗评**（不调 DMT）：按 3.3 中除区域分以外的各项给全部候选打分，取前 M 个（按档位 20 / 40 / 80）。
2. **精评**：对这 M 个城址用 DMT 估算区域分，得到完整的城址分。

粗评不含区域分，相邻加成很高但地块很差的城址可能在第一级被筛掉。缓解办法：精细档的 M 更大；继续优化会逐批放宽 M（见 7.3）；玩家可以手放市中心钉，直接进入第 2 步。

### 3.3 因素与得分

| 类别 | 因素 | 数据来源（全部运行时读取） | 计入方式 |
|---|---|---|---|
| 成长 | 水源（住房） | 河流 `plot:IsRiver`、湖 `IsLake`、带淡水的地貌（`Features.AddsFreshWater`，如绿洲）、沿海 `IsCoastalLand`；住房 `CITY_POPULATION_RIVER_LAKE / COAST / NO_WATER`（5 / 3 / 2），加第一个时代的市中心建筑（粮仓），计划里有沿海区域（港口）时加它的建筑的住房（灯塔、海港；风云变幻灯塔在沿海城市再 +2，`Buildings.Housing` 与 `MODIFIER_CITY_OWNER_ADJUST_BUILDING_HOUSING`） | **水源分** = 住房权重 ×（该城址住房的价值 − 无水城址住房的价值），价值按第 27 节的递减算法，目标人口取 P（#55、#56） |
| | 地块产出 | `plot:GetYield`（六种产出，已含可见资源）加最好的改良（第 27 节） | **耕作分** = 三环内（除去区域占用格）价值最好的 P 格的加权和；P 是建齐计划特色区域所需人口：k 个特色区域需 `3k − 2`（名额公式 `1 + floor((人口-1)/3)` 的反推） |
| | 引水渠潜力 | 市中心是否挨着山、河、湖（合法性由 DMT 判定） | 只显示，不计分（引水渠的住房由修正器决定，不做解析） |
| 资源 | 奢侈资源 | `Resources.ResourceClassType`、`Happiness`（一种奢侈资源可供几座城宜居度）；每格份数 `plot:GetResourceCount`；玩家已有数量 `GetResourceAmount` | **奢侈分** = 宜居权重 × （Σ 新种类的 `Happiness` + 重复份数 × 重复价值）。新种类是玩家还没有、本方案第一次获得的种类，只有它的第一份算新种类；其余每一份（已有种类的、方案内重复的）都算重复份数，可用于交易，重复价值默认 1 |
| | 战略资源 | 同上，`RESOURCECLASS_STRATEGIC`；风云变幻按每格每回合开采量 `Resource_Consumption.ImprovedExtractionRate`，原版和迭起兴衰按每格份数；可见性 `IsResourceVisible` | **战略分** = 战略权重 × （Σ 各格数量 + 新种类数 × 2）。未研究对应科技的战略资源看不到，界面提示"可能还有未知资源" |
| | 加成资源 | `RESOURCECLASS_BONUS`；收获的一次性产出 `Resource_Harvests`（如铜 40 金币） | 每回合产出在耕作分里；一次性收获价值计入地貌分 |
| 地貌 | 树林、雨林、沼泽等可移除地貌 | `Features.Removable`；砍伐的一次性产出 `Feature_Removes`（树林 20 生产力、雨林 10 生产力 + 10 食物、沼泽 20 食物） | **地貌分** = 地貌权重 × Σ 各格（一次性产出 × 进度倍数 ÷ 折算回合数 20）× 对应产出的权重；加成资源的收获价值也按同样方式计入。区域格先砍伐、收获再建，不损失这部分（第 27 节）。地貌带来的相邻加成（如圣地挨树林）在区域分里，每回合产出在耕作分里，界面分类显示各种地貌的格数 |
| 区域 | 区域潜力 | DMT（见 3.4） | **区域分** = 该城址计划区域的最佳摆法的加权相邻加成（线性模型估计）。山脉、雨林、自然奇观、河流等带来的相邻加成都在这里体现 |
| 地形 | 山脉 | 地形表 `Mountain` | 不能耕作、不能建区域，体现在耕作分和可用格数里；相邻加成体现在区域分里 |
| | 自然奇观 | 地貌表 `NaturalWonder` | 不能建城、不能建区域；自身产出在耕作分里；相邻加成在区域分里；提高周边魅力 |
| | 魅力 | `plot:GetAppeal` | **魅力分** = 三环内可建区域格的平均魅力 × 魅力权重（默认权重 0，即默认不计） |
| | 可用格数 | 三环内能建区域的格子数 | 少于计划区域数时扣分；少于一半时该城址判为不可用 |
| | 泛滥平原、火山土（风云变幻） | 地貌 | 产出已在耕作分里；另外显示灾害风险提示 |
| 区位 | 与本国城市重叠 | 三环重叠格 | 组合级处理（见 3.5） |
| | 他国边界 | 他国领土格 | 已属他国的格子不可用，自然降低各项得分；另外显示"三环内他国格数" |
| | 忠诚度（迭起兴衰、风云变幻） | 9 格内各城人口与距离；常数 `CITIZEN_IDENTITY_PRESSURE_*`（`Expansion1_GlobalParameters.xml`） | **只作风险提示**：外国压力不超过本国为"低"，不超过 2 倍为"中"，超过为"高"（阈值为初值）。真实公式还受总督、时代、政策影响，只能近似，不计分 |
| | 未揭示格 | 可见性 | 不计分，显示数量 |
| 特性 | 文明、领袖特性 | 区域相邻类特性由 DMT 计入 | 改地块产出的特性（如马里的沙漠）在无主格上 `GetYield` 可能读不到（需实测） |

**城址分** = 区域分 + 耕作分 + 水源分 + 奢侈分 + 战略分 + 地貌分 + 魅力分 − 可用格不足扣分

奢侈与战略的重复价值、新战略种类的加分、折算回合数都是初值，按基准测试和试玩反馈调整。

风险提示（忠诚度、未揭示格、灾害、离本国最近城市的距离、可能有未知战略资源）显示在城址和方案上，不计入得分。

**权重**：原有五项（科、文、信、金、产）加食物、宜居、战略、地貌、魅力共十项，取值 0–3。面板默认只显示预设，展开后可逐项调整：

| 预设 | 科 文 信 金 产 | 食物 | 宜居 | 战略 | 地貌 | 魅力 |
|---|---|---|---|---|---|---|
| 均衡（默认） | 1 1 1 1 1 | 1 | 1 | 1 | 1 | 0 |
| 成长优先 | 1 1 1 1 1 | 2 | 1 | 1 | 1 | 0 |
| 区域优先 | 2 2 2 2 2 | 1 | 1 | 0 | 1 | 0 |

### 3.4 区域分的估算

对 M 个城址逐个跑完整的单城求解太慢，改为：
1. **共享单项表**：对 M 个城址三环的并集（标准档约 600 格），用 DMT 评估每种计划区域在每格上单独放置的得分和合法性。这时不放假想市中心。
2. **市中心修正**：每个城址的市中心只影响它相邻的 6 格（相邻加成和引水渠等合法性），把这 6 格在放上该城址市中心后重新评估。
3. **线性模型**：用现有求解器的线性模型（单项分 + 区域互惠表）做深度优先搜索，得到该城址的最佳区域摆法和区域分。每个城址的节点预算按档位（5 千 / 2 万 / 4 万）。

这一步得到的是估计值，第 2 步再用 DMT 精确求解。

### 3.5 组合搜索与多套方案

从 M 个城址中选 K 个：
- **间距**：所选城址之间、与现有城市之间距离都大于 `CITY_MIN_RANGE`。
- **接力距离**（评审确认允许接力）：把现有城市、地图上已有的市中心钉和所选城址看作点，相距不超过 D 的两点之间连线；每个所选城址都必须能沿这些连线连回某座现有城市。这一条件在分支定界的每个节点上检查，不影响上界的有效性。
- **组合级修正**（只有选定一组后才能算）：
  - 新种类按组合判定：一组城址里同一种新资源只有第一份算新种类，其余算重复份数；
  - 重叠格只能归一座城：耕作分、地貌分和资源分里，重叠格分给对它估值最高的城（同分时给编号小的城）；
  - 两城的区域摆法落在同一格时，扣掉冲突区域换到次优格的损失。
- **分支定界**：城址按得分排序；上界 = 已选得分 + 剩余最好的若干个城址单独得分之和。组合级修正只会减分，所以这个上界对估计分有效。节点预算按档位（10 万 / 50 万 / 200 万）。
- **多套方案**：保留前 N 套"足够不同"的组合：一套方案与排在它前面的每一套相比，至少有一个城址与对方所有城址的距离都 ≥ 2 格。

### 3.6 输出

每套方案列出：总分、各城址的分项得分与风险提示、质量指示（见 7.4）。选中某套即在地图上预览（第 5 节）。点"采用"后为每个城址打一个市中心钉（名称为城址编号，接在现有城市的编号之后），可以撤销；采用后玩家可以手动挪动或增删这些钉。

**各城址的分项按方案归属**（Issue #8、#9，2026-10-22）：

- 方案总分里的奢侈、战略资源是整套方案一起算的：两个城址都够得着的格子归耕作损失大的一方（3.5），同一种新奢侈、新战略只算一次新种类。原来每行的奢侈分、战略分却是城址单独算的，两边重叠的资源会两边都算，新种类也会每个城址各算一次，行上的数加起来对不上总分。
- 现在每个城址只算方案里归它的格子上的资源；新种类记在方案里第一个拥有它的城址上（按格子编号顺序）。各城址的奢侈分、战略分加起来等于方案的资源分，各城址的分加起来等于方案总分（两个城址的区域抢同一格时，再减去这部分冲突）。
- 行上的数仍是加权后的分数。悬停提示列出这个城址拿到的奢侈、战略资源和份数，标出算作新种类的那几种，并写出对应的分数，如"奢侈资源（8 分）：皮草 1（新）, 葡萄酒 1（新）"。还看不见的战略资源不列。
- 距离分两行：离我方最近的城市或已打的城址钉（与原来相同，打分时就算好的）；离本方案其他城址最近的距离（方案只有一个城址时不显示）。

## 4. 第 2 步：多城区域 + 奇观

### 4.1 参与城市与格子归属

- **新城**：地图上全部市中心钉（第 1 步打的和玩家手放的）。
- **现有城市**（评审确认默认一起规划）：
  - 离任一新城不超过 7 格的现有城市默认勾选，一起规划新区域。7 格以内两城的三环才可能相邻，区域才会互相影响。
  - 更远的现有城市只作固定邻居（已建区域和已有钉计入总分但不动）。
  - 可逐城勾选或取消。参与规划的城市总数（新城 + 现有城市）上限 8；超过时按离新城的距离取最近的，其余只作固定邻居。
  - 现有城市要规划的区域默认取计划区域中该城尚未建造、也没有钉的那些，可按城修改。已建区域和已有钉照旧锁定。
- **每城的候选格**：三环内，排除他国领土、市中心、已有区域、奇观、自然奇观、已有地图钉（沿用 `SDP_City` 的规则）。另外：
  - 新城不能用已属本国其他城市的格子；
  - 现有城市只能用自己的格子和无主格；
  - 无主格默认之后能获得。
- **重叠格**：两座城都够得着的格子，可以出现在两座城的候选里；求解时一格只能放一个区域或奇观，放了谁就归谁。

### 4.2 目标函数

联合总分 = 相邻部分 + 地块部分：
- **相邻部分**：与单城规划相同，所有新区域和所有固定 subject（各参与城市四环内的已建区域、市中心、锁定钉）的加权相邻加成，权重为五项（科、文、信、金、产）。跨城相邻（两座城的区域挨在一起互给加成）由 DMT 自然计入。
- **地块部分**（评审确认计入）：每个参与城市的耕作分，定义同 3.3。区域或奇观占掉一格后，这格不能再耕作。建区域会移除地貌和加成资源，玩家先砍伐、收获再建，所以一次性产出不算损失（第 27 节，#52）。
  - 耕作分按"人口 P 能耕作的最好 P 格"计算，所以占掉一个好格的损失是它与第 P+1 好的格子之差，而不是它的全部产出；占掉一个本来就不会耕作的格子没有损失。
  - 新城的 P 按建齐该城计划特色区域所需人口；现有城市取当前人口与这个数的较大者。
  - 权重为五项加食物、地貌。

提升 = 联合总分 − 基线（不放新区域、新奇观时的联合总分）。

单城规划同样计入地块部分（评审确认），P 的取法同现有城市；面板上有开关"计入占用地块的产出损失"，默认打开，关闭时只算相邻加成，与现有版本一致。

### 4.3 全局约束

- 每城每种区域最多一个（社区等可重复区域的多个放置，沿用单城的限制）。
- 全帝国有上限的区域（如市政广场）：已建 + 已有钉 + 本方案合计不超过上限。剩下的名额给要它的城里排在最前的几座，其余的城改从候选里补（第 23 节）。
- 城址钉一环内没有主人的格子只给这座新城（建城时归它，第 23 节）。
- 新城的特色区域名额：只提示不阻止（与单城一致）。
- 奇观：每个奇观全局最多一个；已被任何玩家建成、或已有本玩家钉的奇观不再规划。

### 4.4 奇观

- **可选奇观**：`MapTacks.PlayerWonders` 中 `Buildings.IsWonder` 的条目（去掉它附带的通用奇观图标 `DISTRICT_WONDER`），玩家勾选要建的奇观。不检查科技与时代（属于提前规划）。
- **下拉框顺序**（Issue #7）：先按时代，取前置科技、前置市政中较晚的那个时代（`Eras.ChronologyIndex`）；同一时代按生产力造价（`Buildings.Cost`）从低到高；再相同按类型名。都从 GameInfo 读。下拉项悬停显示时代。交给求解器的奇观仍按类型名排列，求解结果不受显示顺序影响。
- **合法性**：DMT `CanPlacePin`，subject 为 `{ Type = "WONDER", Key = 奇观类型 }`（`dmt_yieldcalculator.lua:387`）。DMT 已覆盖地形、地貌、河流、海岸、湖泊、山脉、需相邻资源等规则；"需相邻某区域"会读假想区域（`IsAdjacentToDistrict` 读 `GetMapPinSubject`）。
- **需相邻区域时要求同城**：DMT 不区分区域属于哪座城，游戏要求该区域属于建奇观的城（2026-10-23 引擎审计证实，第 26 节）。
- **需相邻改良设施时一起规划**（#51）：`Buildings.AdjacentImprovement` 非空的奇观（只有迭起兴衰、风云变幻的阿耳忒弥斯神庙：营地）旁边没有玩家的营地或营地钉时，方案在旁边放一个营地，和奇观一起打钉、一起撤销。营地可以属于任何一座本方城市，但不能在无主格上（引擎探针，第 28 节）。
- **得分**：奇观本身没有相邻产出（DMT `GetBonusYields` 只对区域和改良设施取产出），它对目标的影响全部来自邻居：如剧院广场（及其特色区域雅典卫城）每相邻一个奇观加文化（`Wonder_Culture`，原版 +1，迭起兴衰、风云变幻改为 +2，由 DMT 从数据读取），以及它占掉的格子和移除的地貌。奇观自身效果（如佩特拉让沙漠增产）不计。
- **放不下的奇观**：列出原因（DMT 的不可放置说明）。

### 4.5 求解

待摆放的对象是"（城市，区域）"和"奇观"。下文中轮数、起点数、局部搜索动作、评估上限都按档位取值（见 7.2）。

起点和块坐标上升里调用的单城求解器要加一个可选的"地块部分"：线性模型里把每格的占用损失（按该城当前第 P+1 好的格子近似）作为该格的单项扣分，精确评估时按 4.2 计算。单城模式默认也启用这一项；关闭时结果与现有版本相同。

1. **准备**：每个参与城市在 overlay 中放上它的市中心，用 DMT 评估每个对象在每个候选格上的单项得分与合法性。第 1 步的单项表在局面未变时直接复用。
2. **起点**：按城市编号依次用现有单城求解器规划，前面城市的方案作为后面城市的锁定邻居；然后把奇观按"合法格最少的先放"逐个放到单项得分最好的合法格。
3. **块坐标上升**：轮流固定其他城市，用单城求解器重解一座城（奇观作为固定邻居）；再对奇观整体重排。迭代到总分不再提升或达到轮数上限。
4. **全局局部搜索**：按档位允许的动作，采用提升最大的一步，直到没有严格提升或预算用尽。每一轮候选动作有几百个，不能都做 DMT 评估：先用线性模型给全部候选动作打分，只对得分最高的前 k 个（按档位 10 / 20 / 40）做 DMT 增量评估。动作有三种：
   - 单个移动：一个对象移到另一个空闲合法格（含其他城市的重叠格）；
   - 两两交换：两个对象互换位置；
   - 成对移动：两个相邻的对象一起挪到另一对相邻的空闲格。用来跳出"整体平移才更好，但单独挪任何一个都会先降分"的局部最优。
5. **多套方案**：从**固定的起点序列**中依次取起点，各做一遍 3–4：
   - 起点 1：按城市编号顺序；
   - 起点 2：按城市编号逆序；
   - 起点 3 起：依次改用各城单城求解短名单中的次优布局（按城市编号、短名单名次的固定顺序枚举）。

   本档位取前若干个起点（3 / 5 / 9），继续优化时接着往后取（见 7.3）。结果按总分排序，保留"足够不同"的方案：与排在前面的每一套相比，至少有 max(2, 对象数的 20%) 个对象的位置不同。不足 N 套时如实显示实际套数。
6. **补放**（2026-10-20 加入，`Session:Repair`）：搜索结束后，若最好的方案里还有要求的对象没放上、而它有合法格（例如学院四周被别的区域占满，大图书馆无处可放），按单项得分从高到低逐格试放：把它放在这一格，把这格上原有的对象、它要挨着的区域，以及（奇观的话）其他奇观重新求解（`Search:SolveBlock`），其余对象不动。放上的对象更多的方案优先，即使总分略低（"要的东西能放就放"）。补放有自己的预算（本档位的四分之一），某一格成功就结束这个对象的补放。离线对比的奇观场景里由此补回了 6 座奇观（第 18.1 节）。

所有同分比较按（城市编号，对象类型，plot index）字典序决胜。

### 4.6 增量评估

多城时固定 subject 有几十个，每次全量评估约 12 毫秒（推算），局部搜索要评估几百到上万次。阶段 8 实现为 `SDP_Board`（单城也用），比原计划的增量评估更进一步：

- **增量**：一个对象从格 A 移到格 B 时，只重算 A、B 及其相邻格上的 subject。
- **记忆**：一个 subject 的得分只取决于（它的类型、所在格、相邻 6 格上的规划对象）。`SDP_Board` 把问过 DMT 的每一种组合记下来（相邻格的规划对象编成一个数作键），同样的邻居组合再出现时不再调用 DMT。搜索中反复出现的组合很多：穷举 3 个区域的 3.3 万种布局只需约 2900 次 DMT 调用，局部搜索的大部分尝试一次 DMT 都不用调。
- **合法性**：区域的 `CanPlacePin` 只与本格和附近的市中心有关（`CanPlaceDistrictCheckHelper`），每个（区域，格）问一次；奇观可能要求相邻某区域，按邻居组合记忆。
- 每个方案最后再做一次全量评估，与增量值比对（结果里的 `Stats.Mismatch`）。

地块部分只涉及被改动的格子，按产出排序走到第 P 格为止，开销可以忽略。

依据：DMT 的相邻加成只读本格和相邻 6 格的特征（`GetBonusYields` 遍历 `Map.GetAdjacentPlots`）。例外：市中心的 3 格间距检查（第 2 步市中心不动，不受影响）、"一条河只能有一座堤坝"。**上线前必须验证**：`tests/test_incremental.lua` 在三种规则集下用固定序列生成的布局比对增量与全量评估（得分和合法性）；不一致的 subject 类型改为全量评估。

### 4.7 质量保证（替代"最优"）

| 保证 | 做法 | 测试 |
|---|---|---|
| 确定性 | 只遍历排序数组，预算按计数，确定的决胜规则；结果与分帧方式、机器快慢无关 | 同一局面求解两次结果深比较相等；分帧额度为 1 和 1000 时结果相等 |
| 不差于逐城单独规划 | 起点 1 就是逐城依次规划的结果，之后只接受严格提升 | 断言最佳方案提升 ≥ 起点 1 的提升 |
| 小规模精确 | 合法组合数不超过本档位的穷举上限（300 / 1200 / 6000）时直接穷举 | 2 城各 1–2 个区域时与暴力枚举的最优相等 |
| 质量透明 | 显示距估计上界的差距和收敛情况（见 7.4） | 基准测试统计上界被突破的次数（见第 9 节） |

## 6. 分帧计算（`SDP_Task`）

- **适用范围**：第 1 步、第 2 步的全部档位，以及单城的精细档。单城的快速、标准档仍同步计算。
- **调度**：`ContextPtr:SetUpdate` 每帧调用一次，执行一段计算后返回。协程可用时用协程写（需实测；游戏本体 UI 没用过协程，AMT 用之前先检查了是否存在）；不可用时写成显式状态机。
- **按计数切片**：游戏 Lua 的计时器只有秒级精度（见 AGENTS），不能在一帧内按毫秒计时。每帧执行一定数量的工作单位（DMT 评估次数、搜索节点数），数量根据上一帧的帧间隔（`UI.GetElapsedTime` 逐帧更新）自适应调整，目标约 20 毫秒/帧。
- **确定性**：算法结果只取决于输入、档位和继续优化次数，与切片边界无关。
- **局面快照**：开始时记录回合数、地图钉、计划参数；DMT overlay 的真实钉快照只加载一次。每帧执行前后安装、卸载 overlay，保证本 Lua 状态之外不受影响。
- **作废与取消**：检测到局面变化（回合结束、地图钉增删、新揭示格子）时作废结果并提示重新计算；面板上有取消按钮。
- **关闭面板不取消**（评审确认）：计算在后台继续。启动栏按钮的悬停提示显示进度；算完时播放提示音（沿用游戏已有音效）并在按钮上做标记；重新打开面板即可看到进度或结果。同一时间只运行一项计算，运行期间其他页签的求解按钮不可用。
- **渐进显示**：第 2 步每算完一套方案就加入列表，第 1 套出来即可预览，其余的继续算。
- **耗时统计**：记录每次求解完成的工作单位数和所用时间（按帧间隔累加；同步求解则取求解前后两帧的时间差），得到本机的处理速度，供 7.5 的预计耗时使用。

## 7. 档位、继续优化与质量指示

### 7.1 原则

1. **档位只改预算的数量，不按时间截止。**同一档位、同样的继续优化次数，在任何机器上结果完全相同，只是快慢不同。慢机器每帧自动少做一些，界面不卡，只是要多等。
2. **不做"按机器速度自动选档"，也不做"算到 X 秒就停"。**那样结果会取决于机器性能和当时的负载，破坏确定性（约束 6）。档位由玩家明确选择，预计耗时只用来提示。
3. **单城算法已重写**（阶段 8，第 15 节）：不再保证与旧版本逐位相同；在离线基准上各档都不差于旧版本，3 个区域以内仍与穷举最优相同。
4. 三个页签各自记住所选档位，默认"标准"。

### 7.3 继续优化

结果出来后显示"继续优化"按钮。每点一次，按固定顺序追加下一批计算，结果只会变好或不变：

| | 每次追加 | 已穷举时 |
|---|---|---|
| 单城 | 从精评布局中再取 5 个起点各做一次局部搜索，再做一批扰动重建（动作与轮数按当前档位）；四轮扰动都没有改进且起点用完后不可再继续 | 按钮不可用，显示"已穷举，结果最优" |
| 第 1 步 | 按粗评排名再纳入 20 个城址（M 增加 20），重新做组合搜索；新旧方案合并后重新筛选 N 套 | 同左 |
| 第 2 步 | 从起点序列中再取一批起点（数量等于当前档位的起点数），各做一遍 4.5 的 3–4；新旧方案合并后重新筛选 N 套 | 同左 |

结果由（输入，档位，继续优化次数）唯一决定，可以复现。求解统计里显示"档位 + 继续优化 n 次"。

|---|---|---|
| 穷举 | 本次走了穷举 | "已穷举，结果最优" |
| 距估计上界 | 上界 U = 各对象最佳单项提升之和 + 全部正的对象间互惠（与现有分支定界同一口径）；差距 = (U − 提升) / U，只在 U > 0 时显示。一律用**提升**而不用总分，避免固定邻居的基线把比例虚抬 | "距估计上界 ≤ X%" |
| 收敛 | 最近一批起点（单城为最近一批短名单布局）都没有找到更好的方案 | "已收敛" 或 "可能还有提升，可继续优化" |
| 预算用尽 | 任一阶段的计数预算用完（现有 `Stats.Truncated`） | "搜索预算用尽" |

**为什么叫"估计上界"**：线性模型按比例折算 `TilesRequired`，一般会高估，所以 U 通常不低于真实最优。但有反例：两个新区域同时挨着同一个已有区域时，单独放各给它 +0（取整），一起放才 +1，这部分不在 U 里。U 因此不是严格的上界。基准测试统计它被突破的频率；如果经常被突破，就给 U 加上修正量。第 1 步的上界只覆盖精评过的 M 个城址，界面注明"仅限精评城址"。

### 7.5 预计耗时

- 档位选择旁显示"预计约 X 秒"：X = 该档位的预计工作量 ÷ 本机处理速度。
- 预计工作量按问题规模（候选格数、对象数、城数）和档位预算估算。
- 本机速度来自本局之前的求解统计（第 6 节）；本局第一次求解前用 Mac 实测的默认速度。
- 预计耗时只用来提示，不影响任何计算。

## 8. 耗时估算（推算，需实测）

依据（Mac 实测，见自测报告）：DMT 联合评估（2 个区域加固定邻居）约 0.5 毫秒，搜索节点约 2 微秒；单城 4 个区域 0.08–0.19 秒，8 个区域 0.18–0.80 秒。单个区域的单项评估未单独测过，按 0.25–0.5 毫秒估计。分帧后实际等待时间按纯计算时间的约 1.8 倍估计。

标准档的分解（其他档位的总耗时见 7.2）：

| 环节 | 规模 | 纯计算 |
|---|---|---|
| 第 1 步：候选与粗评（只读地块数据） | 数百至上千个候选 | < 0.5 s |
| 第 1 步：共享单项表 | 约 600 格 × 8 种区域 ≈ 4800 次 | 1–2.5 s |
| 第 1 步：市中心修正 | 40 个城址 × 6 格 × 8 种 ≈ 1900 次 | 0.5–1 s |
| 第 1 步：每个城址的线性搜索 | 40 × 2 万节点 | 约 1.6 s |
| 第 1 步：组合搜索与多套方案 | 40 选 K，分支定界，50 万节点 | 约 1 s |
| **第 1 步合计** | | **5–7 s，实际等待约 9–12 s** |
| 第 2 步：准备（单项表、各城短名单） | 4 城 × 约 30 格 × 9 种对象 | 1–2 s |
| 第 2 步：每个起点的联合精修 | 4 城 × 6 区域 + 3 个奇观；起点 + 3 轮块坐标上升（每轮约 1 s）+ 局部搜索（约 1 s） | 3–5 s |
| **第 2 步合计（5 个起点）** | | **16–27 s，实际等待约 30–50 s；第 1 套约 10–15 s 出现** |

精确联合求解（4 城 × 6 区域约 30^24 种组合）不可行，这是不保证最优的原因。

## 9. 基准测试

目的：测出各档位实际能达到最优的多少，用来定档位参数、默认档和对外宣称的数字。没有测过的比例不写进使用文档。

### 9.1 场景

固定种子（20261019 及另外 2 个种子）× 三种规则集，每个组合取：

| 类别 | 规模 |
|---|---|
| 单城 | 3、4、6 个区域；含与不含锁定钉 |
| 多城（小） | 2 城各 1–2 个区域（可穷举） |
| 多城（大） | 3–4 城各 4–6 个区域，加 2–3 个奇观 |
| 城址 | K = 2、3 |

场景由 `tests/fixtures/` 脚本搭建（建城、放市中心钉），与现有测试共用固定对局。

### 9.2 参照解

| 规模 | 参照 | 说明 |
|---|---|---|
| 单城 3 个区域、多城（小） | **真最优**：DMT 穷举全部合法组合 | 单城 3 区域约 2.7 万种组合，约 15 秒 |
| 单城 4–6 个区域、多城（大） | **已知最好解**：精细档 + 继续优化 20 次的最好结果，配合估计上界给出区间 | 不是真最优；报告时注明 |
| 城址 | 估计分排名第一的组合，经第 2 步精细档精确求解后，是否仍在全部组合的前 3 名 | 衡量区域分估计的误差；食物等系数的模型误差无法用基准测试衡量 |

### 9.3 指标与达标线

- **质量比例** = 本档位的提升 ÷ 参照解的提升（都用提升，不用总分）。报告每档的平均值、最差值。
- **耗时**：每档的墙钟时间、DMT 评估次数、搜索节点数。
- **上界**：估计上界被参照解突破的次数。
- **继续优化曲线**：标准档继续优化 0、1、3、10 次的质量比例，用来判断"继续优化"是否值得。
- **达标线**（暂定）：标准档平均 ≥ 95%、最差 ≥ 90%；精细档平均 ≥ 98%。不达标时先改算法或参数，再定发布的默认值。

### 9.4 运行与记录

- 游戏内基准放在 `tests/bench/`（不以 `test_` 开头，不进常规测试），用 `@timeout` 放宽时限，单独运行。`cost_dmt.lua`、`cost_search.lua` 测 DMT 调用、布局评估和搜索节点在游戏里的实际单价，用来校准离线估算和 `SDP_Tiers` 的工作单位。
- 结果写进 `docs/self-test-report.md`（每档质量与耗时表），并据此更新 7.2 的参数和"预期质量"一行。

### 9.5 离线基准（阶段 8 起）

算法迭代主要在离线完成，不用开游戏：`node tools/offline_tests.mjs -v tests/offline/bench_single.lua`（用法见 `tools/README.md`）。

- 场景：6 个固定种子的随机地图（15×13，首都居中，偶数种子带一个已建区域）× 3、4、6、8 个区域 × 是否计入地块部分。
- 参照解：3 个区域用穷举最优；更多区域用"精细档 + 继续优化 3 次"和三次模拟退火（固定伪随机序列，只在测试里用）中最好的，档位结果更好时自动更新参照。
- 成本：假 DMT 统计调用次数，按游戏内单价折算：`SDP_Tiers` 工作单位（DMT 调用 + 0.25 × 布局评估 + 节点 / 20），一次算完时每单位约 0.05 毫秒（2026-10-20 游戏内实测，第 17 节）。
- 局限：假 DMT 只有主要的相邻规则（山脉、树林、雨林、河流、区域互邻、奇观、水渠—工业区、娱乐—剧院、市政广场），没有改良设施、海港、特色区域的特殊规则和修正器。离线质量只说明搜索本身有效，游戏内仍要按 9.1–9.3 复核。

面板：档位下拉框和预计耗时、"计入占用地块的产出损失"开关（食物、地貌两个权重只在打开时可调）、继续优化与取消按钮、质量说明一行、精细档分帧运行、关闭面板时在启动栏按钮的悬停提示里显示进度、算完播放提示音并在按钮上加标记。

### 15.2 算法迭代（离线基准，第 9.5 节）

| 版本（标准档，平均 / 最差，占参照解） | 6 个区域 | 8 个区域 | 预计耗时（8 个区域） |
|---|---|---|---|
| 旧算法（MVP） | 87.5% / 67% | 89.6% / 83% | 约 1.2 秒 |
| + 增量记忆评估、模型按单项分从高到低搜索、更紧的上界、"不取整"模型（邻近市中心和已有区域的半个加成计入）、整组平移 | 98.8% / 93% | 95.5% / 89% | 约 1.2 秒 |
| 模型深度优先搜索换成集束搜索（宽 400） | 100% / 100% | 97.4% / 94% | 约 0.3 秒 |
| + 4 轮扰动重建 | 100% / 100% | 98.3% / 94% | 约 0.56 秒 |
| + 集束先放与其他区域互惠最多的（现行） | 100% / 100% | 99.2% / 96% | 约 0.56 秒 |

计入地块部分时结果相近（8 个区域标准档 99.1%）。快速档 8 个区域 98–99%、约 0.13 秒；精细档全部 100%、约 2.2 秒（分帧）。

几个发现：
- 旧算法的主要问题是模型深度优先搜索被节点预算截断时，只看过编号小（地图左上）的格子；以及单个区域移动无法把整片区域搬到更好的位置。
- 模型本身相当准：漏掉的好方案，模型分往往比找到的更高，问题在搜索没走到。所以把预算从模型搜索节点挪到集束搜索，比加深搜索有效得多。
- 首次改进（first improvement）、两两成对移动在这些场景里没有收益，未启用。

### 16.2 与设计的出入

- **"需相邻区域"的奇观没有加"同城"限制**：合法性完全按 DMT（相邻有该区域即可，不论属于哪座城）。2026-10-23 引擎审计证实游戏要求同城，v1.2.0 已加（第 26 节）。
- **城址评分不含有帝国上限的区域**（市政广场等）：每个城址都算一份会重复计算。
- **城址的区域分用完整的单城搜索**（快速档参数）而不是只用线性模型：共享 `SDP_Board` 的记忆让它足够便宜，估计更准。
- **多城页签暂不能逐城修改计划**：所有城市共用一份计划，现有城市自动跳过已建和已有钉的区域。接口已支持 `Plans`（按城覆盖），界面以后再加。
- **多城页签没有"允许砍伐"开关**：始终允许（与单城默认一致）。
- **渐进显示**：计算中只显示进度百分比，全部算完才列出方案（设计 6 的"第 1 套出来即可预览"未做）。

### 16.3 离线测试

- `spec_multi`：参与城市与开关、上限；新城不能用现有城市的格子；一格一个对象、帝国上限、不差于逐城依次规划；现有城市跳过已建区域；确定性；小规模与暴力枚举一致；共享地块只归一城；多套方案互不相同；奇观（已建、已有钉、缺少所需区域、需相邻区域时摆在规划的区域旁边）。
- `spec_sites`：候选排除规则、`CITY_MIN_RANGE` 读游戏数据、水源/奢侈/战略的计分、组合的间距与接力、确定性、分支定界与逐对枚举一致、修正不会让组合超过各城址分之和。
- `spec_panel`：用 `tests/offline/ui.lua` 的控件替身加载整个面板，三个页签依次求解（同步与分帧）、预览、打钉与撤销、关闭面板后后台算完的提示。只能证明脚本逻辑无误，布局与真实点击仍要在游戏里看。

### 16.4 多城离线基准

`tests/offline/bench_multi.lua`：4 个种子的随机地图（21×15），首都 + 3 个市中心钉，每城 5 个区域 + 市政广场，有/无地块部分。参照解为精细档 + 继续优化 1 次 + 模拟退火中最好的。

| 档位（平均 / 最差，占参照解） | 只算相邻 | 计入地块部分 | 预计耗时（推算） |
|---|---|---|---|
| 逐城依次规划（起点 1 本身） | 92.7% | 94.7% | — |
| 快速 | 94.1% / 87% | 97.4% / 93% | 约 1.3 秒 |
| 标准 | 98.2% / 95% | 98.4% / 96% | 约 6 秒 |

迭代中的发现：
- 只加起点（城市顺序）几乎没有收益；扰动重建在标准档受布局尝试上限限制，40 轮以上无差别。
- 一个场景里最优方案把三座新城的区域并成一大片（跨城相邻互给加成）。逐城规划时束宽越大，第一座城越"自顾自"地选最好的位置，反而走不到这种形状；快速档的窄束偶然走到了。于是起点改为固定的组合：逐城（全宽）、联合（所有城的区域一次束搜索）、逐城（三分之一束宽）、逆序（全宽、三分之一束宽）……标准档计入地块时从 97.3% 提到 98.4%。
- 预计耗时按单城的单价推算；多城一次布局评估更重（棋盘大、每城一个地块模型），在离线虚拟机里与推算之比约为单城的两倍，游戏内标准档可能在 8–10 秒，仍远低于设计的 30–50 秒，待实测。精细档的离线基准未跑完，参数沿用设计。

### 17.2 游戏内发现并修改的问题

- **城址精评取不到能连通的城址**：地图揭示较多时，粗评前 M 名可能都离本方城市超过接力距离 D，组合全部不连通，结果为"无城址"。改为按粗评顺序只取"能连回"的城址精评：离本方城市或城址钉 D 格内，或离已精评的城址 D 格内（最多 K − 1 次接力）。
- **后台结果把预览画到地图上**：面板关闭时算完会渲染结果并显示预览。现在面板关闭时算完即清除预览，打开页签再显示。
- **方案行和选中页签的文字看不清**：按 `TradeOverview` 的做法，选中、未选中各用一套文字。
- **多城档位不单调**：离线基准里快速档在一张图上比标准、精细档好（47 对 45），原因是搜索路径不同（交换动作、穷举上限），不只是束宽。现在每档先跑轻一档的起点（`SDP_Tiers.Multi.*.Prelude`，`Session:RunPrelude`），起点结果只取决于输入和参数，所以不会低于轻一档的起点。共享的记忆评估让这部分几乎不增加 DMT 调用。前置有自己的预算：跑完后重新设定预算，本档的起点和扰动仍有全部预算（不这样做时精细档在一张图上反而少 1 分）。精细档前置标准档后，自身起点从 6 个减到 4 个，质量不变（离线 98.2% / 100%），耗时少约 15%；只前置快速档的方案更省时，但计入地块时会低于标准档，未采用。

### 17.3 耗时校准

- 单价：一次 DMT 调用约 0.042 毫秒，一次布局评估约 0.01 毫秒，一个模型节点 0.002–0.005 毫秒。`SDP_Tiers.UNITS_PER_TRY` 改为 0.25、`NODES_PER_UNIT` 改为 20，一个单位约等于一次 DMT 调用；一次算完时每秒约 2 万单位，分帧时单城每秒 7400–9900 单位、多城约 15000 单位（`SDP_Task.DEFAULT_SPEED` = 11000 取中间，每次算完后按本机实测更新；`AT_ONCE_SPEED` = 20000）。
- 工作量：搜索通常远在预算用完之前收敛，原先"按预算估计"偏长 5–10 倍。现在按实测的典型工作量估计（`Work`）：单城 = 格数 × (a·k + b·k²)；多城 = 每槽每格的工作量 × 30 格 × 槽数 × (城数 / 2)^0.35，再加前置档位；城址 = 每个精评城址每个区域的工作量 + 组合数（约 C(M, K) 的四分之一）。预算上限仍按原来的计数，结果不受估计影响。
- 实测（一次算完，最终版本）：单城标准档 6 个区域 0.25 秒；多城 3 城 × 6 区域标准档 2.7 秒、精细档 4.3 秒；选城址 3 座精细档 3.5 秒。经面板分帧：多城标准档实际等待 4.4 秒、精细档 9.1 秒。都远低于第 8 节推算的 30–50 秒。预计工作量与实测相差在 10% 以内。

### 18.1 吸收这些功能后，怎样保持评估公平

本次离线对比的主指标是本 mod 的目标（DMT 显示的相邻加成）。吸收地块产出、覆盖范围、改良设施这类功能后，评估要同步改，原则是不让任何一方的目标函数单独当裁判：

1. **多把尺子，不只用本模组的目标**：每个方案同时报告：DMT 相邻加成（钉上显示的数）、**城市总产出**（相邻加成 + 市民耕作最好的若干块地，人口多少就算几块，各产出权重 1；本次已加入），以及各项目标自己的指标（如工业区、娱乐中心覆盖的城市数，改良设施的产出）。这些指标由裁判独立计算，不复用任何规划器的代码。汇总时用帕累托支配（在所有指标上都不差、至少一项更好）计数，而不是只比一个加权和。
2. **交叉评分**：用对手自己的目标函数（AMT 的 `EvaluatePlan`、EP 的规则引擎）给所有方案打分。本模组的方案在对手自己的标准下也不差，结论才算稳；在它们的标准下输了，如实写出。
3. **每把尺子都给对手最好的设置**：对每个指标，对手用最贴近该指标的设置（计入地块时用它们自己的地块惩罚，只看科研时给它们科研焦点），必要时在它们的参数空间里搜索取最好的一组，作为对手的上限；同时保留面板默认设置的结果。本模组同样报告默认设置（面板默认计入地块损失）。
4. **多组权重**：在几组产出权重（均衡、科研、生产、信仰……）下各评估一次，结论不能只在“全部为 1”时成立。
5. **留出场景**：指标和场景在改算法之前定下来。调参只用一部分种子，最终对比用调参时没用过的种子，避免把算法调成只适合这批场景。
6. **引擎校准**：在游戏里抽样，把方案真的建出来，读引擎实际给出的相邻产出，与 DMT 裁判对照，确认裁判本身没有偏差。
7. **统计与公开**：逐场景配对比较，报告胜 / 平 / 负和置信区间，不只报平均；裁判只看地图钉、不知道方案来自谁；公开原始结果和测试框架，任何人都能重跑。

已做到：第 1 条的城市总产出（`CmpRun.Judge` 的 `output = gain + worked`）、第 3 条的默认设置（AMT `DEFAULTW`、EP `DEFAULT`、本 mod `STANDARD_LAND`）、第 7 条的盲评与配对比较；裁判还区分漏放的区域“确实放不下”（`no_plot`）与“有位置却没放”（`placeable`：方案打成钉后城市仍有槽位，且 3 环内有一格 DMT 可放、不违反其他规则）。2026-10-20 的结果：单城 72 个场景本模组标准档 97% 拿到最高加成（AMT 54%、EP 26%），漏放中“有位置却没放”本模组 0、AMT 52、EP 75；城市总产出本模组（计入地块）83% 最高（AMT 58%、EP 35%）。

随后（2026-10-20 傍晚）又做到：第 2 条交叉评分（`compare.mjs --crossscore`；`cmp_cross_amt.lua` 复现 AMT 的 `EvaluatePlan`，`cmp_cross_ep.lua` 复现 EP 的 `PlanTotal`，各自对自己方案的打分与它们运行时自报的一致）；第 4 条三组权重（`~SCI`、`~PROD`、`~FAITH`，某一项 ×3，规划器和裁判同用）；第 5 条留出集（`HS`/`HM`，种子 50000 起，改算法时不看）；第 7 条的置信区间（2000 次确定性自助重抽样）与符号检验。另加了奇观（`W`，24 个）与选城址（`C`，12 个，独立裁判 `JudgeSites`）的正面对比。结果见 [self-test-report.md](self-test-report.md) 与“介绍与评测”页的附录 B。奇观对比发现本 mod 会漏放需要挨着某个区域的奇观，已加"补放"（4.5 第 6 步）。

第 6 条引擎校准 2026-10-20 晚在游戏里做了（`tests/bench/calibrate_judge.lua`）：放置透镜的加成与 DMT 逐格比较，罗马、日本、高卢三局共 306 组，原因不明的差异 0；已建的 13 个相邻区域引擎与 DMT 逐项相同。唯一的差异是 DMT 把沉船算作海洋资源（AGENTS 坑 28），对所有规划器的裁判影响相同。

第 1 条的帕累托计数与覆盖城数见第 19 节。还没做：改良设施的指标（等第 18 节第 2 项）；第 3 条在对手参数空间里搜索上限。

## 19. 覆盖范围（第 18 节第 7 项，2026-10-20 实现）

工厂、电厂、动物园、体育场、水族馆等建筑的效果不只给本城：城市中心在建筑所在区域若干格内的本方城市都能得到，同类不叠加。只看相邻加成时，规划工业区、娱乐中心不会考虑它们能覆盖几座城。覆盖范围是多城页签的可选目标项，默认关；v1.4.0 起单城页签也有（19.7）。

### 19.1 规则（全部从 GameInfo 读）

- **区域的覆盖半径**：`GameInfo.Buildings` 中 `PrereqDistrict` 为该区域、`RegionalRange > 0` 的建筑，取最大的 `RegionalRange`。只算通用建筑（`TraitType` 为空）和本文明特性带来的建筑（`MapTacks.PlayerTraits`）。特色区域按它替换的区域算（汉萨同工业区）。风云变幻的数据：工业区 6、娱乐中心 6、水上乐园 9。
- **奇观的覆盖半径**：奇观自身的 `RegionalRange`（斗兽场、杰贝尔巴尔卡尔 6；马拉卡纳体育场 100000，即全帝国）。
- **类别**：同一基础区域算一类（工业区和汉萨同类），每个奇观自成一类。一座城被某一类覆盖一次就算覆盖，再多不加（游戏里同类效果不叠加）。
- **距离**：区域（奇观）所在格到城市中心的格距 ≤ 半径（`Map.GetPlotDistance`）。

### 19.2 目标

- **被覆盖的对象**：玩家的全部城市（参加规划的和不参加的都算），加上本次规划的新城（市中心钉）。
- **原有覆盖**：玩家已建的和已打钉的同类区域（勾选"替换旧钉"时被替换的那些钉不算）。已建或已打钉的奇观本来就不会再规划，不需要原有覆盖。
- **覆盖项** = 覆盖权重 × 方案新增覆盖的（城市, 类别）个数。总目标 = DMT 加权相邻加成 + 地块部分 + 覆盖项。
- **覆盖权重**：0–3，默认 0（关）。单位与相邻加成相同：权重 1 表示每新覆盖一座城记 1 分。游戏里一座城被覆盖的实际收益：工厂 +3 生产力，电厂再加 +3～+4；动物园、体育场、水族馆各 +1 宜居度。所以 1 是保守的估价，玩家可以调高。
- **放在哪，和从候选里挑哪个**：覆盖项影响玩家要求的区域、奇观放在哪里；有区域数量、从候选里挑时（20.1），覆盖也计入挑选，所以权重高时工业区、娱乐中心可能先被挑中（`SDP_Search` 的精确评估不区分必建和候选）。区域只会进玩家列了它（必建或候选）的城。AMT 的覆盖请求对所有城开放，可能把区域放进没要它的城（第 2 节）；本 mod 不这样做。
- **权重为 0 时**不建覆盖模型，求解过程和结果与只算相邻加成、地块时完全相同。
- 需求文档约束 3 规定目标函数是五种产出的加权和。覆盖项是玩家主动打开才有的扩展，默认关，面板上单独一列，悬停说明含义。

### 19.3 搜索

- **精确评估**（`SDP_Search` 的 `Evaluate`）：在 DMT 加成和地块部分之外，加上覆盖项。每个已放、有覆盖半径的槽，查它所在格能新覆盖的（城市, 类别）列表（按格缓存，每格最多十几座城），去重计数。代价远小于一次 DMT 调用。
- **模型**（短名单、集束搜索的排序和乐观上界）：槽的单放值加上"该格单独放时新增覆盖的城数 × 权重"。两个同类槽覆盖同一座城时，模型会重复计算，所以模型偏乐观，上界仍然是乐观的；最终都以精评为准。
- 局部搜索、扰动重建、补放都比较精评值，不需要改。"逐城依次规划不劣于"的保证（4.7）仍然成立：逐城起点和联合搜索用的是同一个目标。

### 19.4 界面

- **权重**：多城页签的权重行加一列"覆盖"（0–3，默认 0），悬停说明含义和估价参考。
- **结果摘要**：权重大于 0 时，在"相邻、地块"之后加"覆盖 +N 城"。
- **结果行**：有覆盖半径的区域、奇观，在产出明细后写"新覆盖 N 城"，悬停列出这些城的名字。N 只数这一格新覆盖的城（范围内、以前没被已建或已打钉的同类区域覆盖），一个都没有时不写（v1.4.0 起；原来数范围内全部城市，含本城和已覆盖的）。两个同类区域覆盖同一座城时两行都列出它，摘要只算一次。
- **单城页签**：v1.4.0 起有同一列，见 19.7。

### 19.5 评估（按 18.1 的原则）

- **指标"覆盖"**：由裁判独立计算，不复用 `SDP_Coverage` 的代码。裁判读规则数据的 `RegionalRange`，数每类区域覆盖的城数。
- **场景集 `V`**：12 个后期多城场景，每个 3–4 座城，逐城给清单。只有一两座城的清单里有工业区或娱乐中心，其余区域照常。现有的多城场景每座城的清单相同，要工业区的城自己就覆盖了自己，覆盖项不起作用，所以要专门的场景。
- **参加者**：本 mod 覆盖权重 0、1、3；AMT 用同样的逐城清单，它自带覆盖。EP 只能全局设置区域、不能逐城给清单，也不算区域的覆盖，不参加。
- **报告内容**：覆盖城数、DMT 相邻加成，两项一起做帕累托比较（两项都不差、至少一项更好）。权重 0 时，原有场景的方案逐个与不计覆盖时相同（回归）。
- **预期**：权重 1 时覆盖增加、相邻几乎不降；权重 3 时覆盖更多、相邻略降。
- **结果（2026-10-20，标准档）**：12 个场景中 7 个不计覆盖也已全部覆盖（几座城都在 6 格以内）。其余 5 个里，权重 1 时 4 个多覆盖 1 座城、相邻加成不降；另 1 个（V05）相邻 −1、覆盖不变，是标准档的搜索波动，精细档下为相邻 −1、覆盖 +1。权重 3 时最多多覆盖 2 座，相邻 −4（V05）、−7（V11）。本 mod 自报的覆盖数、相邻加成与裁判一致；权重 0 时 88 个原有方案逐个不变。AMT 在 V04 把工业区放进清单上没有工业区的城，这个场景不比；其余 11 个两项一起比，本 mod 权重 1 时 4 个更好、5 个相同、2 个各有胜负（V05、V11：本 mod 相邻高 3、9，覆盖少 1），没有更差的；权重 3 时 6 个更好、5 个相同；不计覆盖时有 3 个场景覆盖比 AMT 少 1 座。与预期一致。

  - 集合计数、同类不叠加、原有覆盖、被替换的钉不算；

### 19.7 单城页签（#61，v1.4.0）

**做法**：单城页签的权重行加同一列“覆盖”（键 `COVERAGE`，0–3，步长 1，默认 0，悬停与多城页签共用 `LOC_SDP_WEIGHT_COVERAGE`）。两页的权重列都是共用的 9 列后面接 `SDP_UI.COVERAGE_COLUMN`，每列 50 像素。

- **模型**：`SDP_Solver.NewSession` 在 `request.Coverage > 0` 时建 `SDP_Coverage.New`，传给 `SDP_Search`，与多城同一份代码（半径、类别、原有覆盖都照 19.1、19.2）。权重 0 时不建模型，结果逐字不变（`spec_coverage` 的单城用例比较了全部三套方案和 DMT 调用数）。
- **要覆盖的城**：玩家的全部城市（本城在内），加上地图上全部市中心地图钉（`SDP_Coverage.SiteTargets`，键 `S<格编号>`）。单城页签没有逐个城址的开关，所以全算。带奇观时请求转给 `SDP_Multi`（`Only` 只有这座城），这时城址不参加规划，也照样全部算作要覆盖的城。
- **从候选里挑**：与多城相同，覆盖计入挑选（19.2）。
- **结果**：`Covered`、`CoveredBy`、`CoverageDelta` 与多城的字段相同（汇总挪进 `SDP_Coverage` 的 `Summary`，两边共用），`Gain` 计入覆盖项；摘要单列覆盖分，悬停按类别列出新覆盖的城（城址写“城址 n”，编号同多城页签）；结果行同 19.4。
- **热力图**（“好位置”）不计覆盖：它是单个区域的 DMT 值。

**实测（收益与代价，悬停提示里的数）**：42 座真实城市，覆盖权重 0、1、3 各跑一遍标准档，只规划目标城，别的城都作邻居，裁判独立计算覆盖与相邻加成。

- **AI 存档 14 座**：`RC01`–`RC14`（真实集 `RS` 的同一批城，15 格窗口重新导出，9 格内的本方城市和已覆盖它们的区域都在场景里），结果 `tests/compare/results/coverage_single.jsonl`。权重 1、3 都只有 RC03 多覆盖 1 城，相邻不降。
- **玩家存档 28 座**：`RP01`–`RP28`（社区参照布局的每座参照城，`tools/covscene.py` 导出），结果 `tests/compare/results/coverage_player.jsonl`。权重 1：RP12 多覆盖 3、相邻 −1，RP27 多覆盖 3、相邻 −3；权重 3 再加 RP05（+2，−4）、RP09（+1，−2）、RP11（+2，−3）。
- **合起来**：权重 1 时 42 座里 3 座多覆盖，各让出 0–3 点相邻；权重 3 时 6 座，最多让出 4 点。离线耗时比权重 0 多约 5%（14 座 10.36 → 10.76 / 10.83 秒，28 座 3.75 → 3.87 / 3.99 秒），DMT 调用数基本不变。
- 这两组入库的结果跑的是多城求解器只规划一座城（`cmp_sdp` 对一座城的多城场景传 `Only`，与单城页签带奇观时的路径相同），跑法见 tools/README.md 的 `RC`、`RP`。实现后临时让这 42 个场景改走 `SDP_Solver` 重跑一遍（126 次，没有入库）：多覆盖的城、覆盖数和相邻加成与上面逐个相同，全部合法，耗时比权重 0 多 1%–3%。
- RP16、RP17（波兰）里本模组自报的新覆盖（0、1）与裁判（6、7）不同，权重 0 时裁判也是 6、7，方案不随权重变，两条路径都一样；原因没有查（#61 之外）。

**测试**：离线 `spec_coverage.lua` 的单城用例（权重 0 逐字不变、工业区挪向邻城、城址计入、已覆盖的城不计也不列、从候选里挑计入覆盖），`spec_panel.lua` 经箭头自己的点击回调调整这一列、求解、带奇观时权重随请求进 `SDP_Multi`；游戏内 `test_features.lua` 两项：新局里工业区挪到够得着市中心地图钉的格（2026-10-24 风云变幻罗马局：(61,23) → (61,24)，相邻不变）；有多座城的存档（`tools/stress.py load pangaea-gs`）里找一座附近有未覆盖本方城市的城，核对新覆盖的城逐个与独立计数相同（大阪的工业区从 (28,15) 挪到 (28,11)，相邻 +4 → +3，新覆盖 1 座邻城）。

## 20. 实测反馈的改进（阶段 14–18，2026-10-20）

合作者在 Windows 上实测，功能正常，另提了 11 条意见。可行性分析与设计稿在 claude.ai 的 artifact「实测反馈改进设计」里（没有收进仓库）；待确认的 7 个问题都按其中的默认做法实现。本节记录实现与验证。

### 20.1 区域组合的自动选择（反馈 1、8、11）

**玩家怎么指定**：每个区域一个状态（`SDP_UI`）。占人口名额的区域：必建 / 候选 / 不建，默认候选；全帝国限一个的（市政广场、外交区）只能必建或不建，默认不建。不占名额的：自动 / 必建 / 不建（20.3）。另有"区域数量"：要规划几个占人口名额的区域，必建的也算在内；默认等于必建个数，这时不挑，结果与以前相同。

**请求**：`SDP_Solver` 的 `Pool`（候选类型）与 `Count`；`SDP_Multi` 另有按城的 `Pools`、`Counts`、`Autos`；`SDP_SiteSolver` 的 `PlanCount`（每个城址按几个区域估分，默认 3）。不传这些字段时行为与以前完全相同（第 20.6 节的回归）。

**搜索**（`SDP_Search` 的 pools）：候选区域是标了 `Optional` 的槽，每组（城市）放 `Pools[组]` 个。
- `Combos(g)`：列出所有组合，按乐观分排序。乐观分 = 每个槽最好的模型单放分 + 组合内及与必建区域之间的正互惠（每对一次）+ 必建区域自身的同样估计；与集束搜索的上界同一口径。组合超过 5000 个时只保留单独估分最高的候选。
- 单城 `RunPools`：按乐观分依次求解前 `Combos` 个组合（快速 3、标准 8、精细 20）。每个组合先粗解：布局数不超过 `ScreenExact` 时穷举，否则模型集束搜索、精评 `ScreenShortlist` 个布局、做一次局部搜索。某组合的乐观分低于当前第三名的实际分时，后面的不再算。
- `SwapCombos`：从前三名出发，把一个候选换成另一个、放到它最好的空格（精确评估），会进前三的新组合也粗解。
- `RefineCombos`：前三名组合按本档位完整求解（布局数不超过 `ExactLimit` 时穷举，否则更多起点和扰动重建；扰动只动已放的槽，组合不变）。
- 三套方案（`Search:Solutions`）：各组合的最好布局按分数排，组合不同即算不同方案；不足三套时用搜索途中保留的、位置差异足够大的布局补（`KeepAlternative`，规则同 4.5）。
- 继续优化：再粗解一批排在后面的组合，并给前三名更多起点。
- 多城：`SDP_Multi` 逐城起点时为每座有候选的城粗解前 `Combos` 个组合（快速 2、标准 3、精细 4），选最好的；联合起点取每座城排第一的组合；按城轮换重解时保留当前组合；每次局部搜索后试"换类型"（`TypeSwaps`：任一城把一个候选换成另一个，最好的改进一步，最多四轮）。放不下足够候选的城在结果里报"候选不够"。
- 选城址：`SDP_Sites.Fine` 对每个精评城址用同一个 `RunPools`（城址参数加 `Combos` 快速 2、标准 3、精细 4）。勾选的占名额区域不多于 `PlanCount` 时全部计入，与以前相同。

**比较的是目标函数**：不同区域之间只按加权相邻加成（打开时加上地块、覆盖和距离成本）比较。区域里建筑本身的产出不计，所以没有相邻加成的区域（军营、航空港）放在候选里不会被挑中，界面提示设为必建。

**离线基准**（`tests/offline/bench_pools.lua`，4 个种子 × 4 种情形，参照为逐个组合用标准档加 3 次继续优化求解后取最好）：

| 情形 | 快速 | 标准 | 精细 |
|---|---|---|---|
| 7 选 3（35 种组合） | 100%，约 0.11 s | 100%，约 0.38 s | 100%，约 2.3 s |
| 必建 1 + 6 选 3（20 种） | 100%，约 0.14 s | 100%，约 0.68 s | 100%，约 2.6 s |
| 必建 3（含水渠）+ 5 选 3（10 种） | 98.3%（最差 93%），约 0.17 s | 100%，约 0.93 s | 100%，约 2.8 s |
| 7 选 5（21 种） | 98.2%（最差 93%），约 0.18 s | 100%，约 0.99 s | 100%，约 4.6 s |

耗时为按游戏内实测单价折算的一次算完时间（第 17.3 节）；挑选时一律分帧计算。精细档最初逐个组合穷举（约 4.6 s），改为粗解用 `ScreenExact` = 3000、只对前三名穷举后降到约 2.3 s，质量不变。

多城（`tests/offline/bench_multipools.lua`，首都 + 3 个城址钉，每座城学院必建、再从 5 个候选挑 2 个，3 个种子）：精细档 3/3 达到参照（各档、精细档加两次继续优化、“先逐城挑再联合规划”中最好的值），约 6.5 s；快速、标准档平均 97.6%（最差 93%），约 0.5 s、2.5 s。最差的种子上标准档挑的组合与精细档相同，直接给定这组区域不挑时标准档也是同样的分数，差距在多城摆放搜索，与挑选无关。第 21 节给标准档加了宽束联合起点后，标准档 3/3 达到参照，约 3.1 s。

### 20.2 距离成本（反馈 9）

- 每个区域、奇观扣 `权重 × (到最近的本方市中心的格数 − 1)`，与各项收益同一单位；`SDP_City.DistanceCosts`。最近的市中心包括玩家的城市和参与规划的城址钉（选城址时是该城址自己）。
- `SDP_Search` 的 `Costs`：每个候选格一个扣分，加进精确评估和模型单放分，结果里是 `CostDelta`（≤ 0），`Gain = 相邻 + 地块 + 覆盖 + 距离`。
- 权重 0–3、步长 0.5，默认 0；三个页签的权重行都有这一列（短字“距离”，见 20.5）。
- 游戏里区域的造价与距离无关；与距离有关的是取得格子的先后（`PLOT_INFLUENCE_DISTANCE_MULTIPLIER`）和买地价格（`GetPlotPurchaseCost`）。所以这是玩家的偏好，悬停提示里说明。

### 20.3 自动加入的区域（反馈 4）

- 种类从数据判断（`SDP_Rules.AutoKind`）：`Districts.Aqueduct`（水渠和替代它的特色区域，如罗马浴场）为 WATER；`Districts_XP2.PreventsFloods`（堤坝，只在风云变幻）为 FLOOD。
- 条件（`SDP_City.NeedsAuto`）：WATER——城市缺淡水，现有城市按游戏自己的 `GetGrowth():GetHousingFromWater()` 低于河流、湖泊的 5（`CITY_POPULATION_RIVER_LAKE`），城址按市中心格（河流、湖泊、带淡水的地貌）；FLOOD——三环内候选格里有堤坝要求的地貌（`District_RequiredFeatures`：泛滥平原）不少于 `SDP_Rules.AUTO_FLOOD_PLOTS` = 3 格。
- 本城已建、已有钉、不能建时不加。加入的区域当作必建，位置照常求解（工业区挨着它们 +2 生产力），结果里标"自动加入"；没有合法位置时报"自动加入的……放不下"。
- 面板：不占名额的区域默认"自动"（能自动的），可改成必建或不建。选城址页不自动加。

### 20.4 提醒钉（反馈 5）

- `SDP_Remind.Find(玩家, 方案)`：把方案放上假想层；对每个规划区域相邻、地貌可移除（`Features.Removable`）且方案没有建在上面的格，用 `SDP_Overlay.HideFeature` 让 DMT 看不到这格的地貌，再算一次该区域的加成，少了至少 1 点的记下来。
- `HideFeature` 的做法：安装假想层时包一层 DMT 的全局函数 `GetRealizedPlotFeatures`（DMT 的 `GetBonusYields` 每次都经它读邻格特征，相邻规则和文明、万神殿的地貌修正都在这里取地貌），被隐藏的格返回去掉 `ADJACENCY_FEATURE` 的副本。卸载时还原。
- 按现在的数据，参与相邻规则的可移除地貌只有树林（圣地、修道院）和雨林（学院；巴西、"神圣道路"等修正还有更多区域）。"每 2 片树林 +1"这类规则按数量取整，相邻的树林数为奇数时砍一片不损失，不提醒。
- 只提醒规划的区域（设计稿还提到"因它变化的已有区域"，没有做：已有区域旁的地貌与这次规划无关）。
- 打钉见 design.md 的图钉一节；面板默认打开"提醒钉"。

### 20.5 界面（反馈 2、3、6、7、10）

- 多城页的城址钉可以取消勾选（`Participants` 的 `Sites`）：不参与规划、不算新城，钉仍在，仍是固定邻居；附近现有城市是否默认参加只按仍参与的城址算。

### 20.6 测试

- **离线**：`spec_pools.lua` 13 项（不挑时结果不变、与逐对暴力枚举一致、三套方案组合不同、确定性与继续优化、距离成本、自动水渠堤坝、提醒、选城址按 k 个、多城按城挑选、城址钉取消、多城的距离与自动），`spec_panel.lua` 加了一项（状态、数量、挑选、三套方案、提醒钉的打与撤）。全部离线测试 72 项通过。

## 21. 多城标准档：宽束联合起点（2026-10-21）

**问题**：多城挑选基准（20.1）的种子 11 上，标准档 26 分、精细档 28 分；直接给定同样的区域、不挑选时标准档也是 26，差在摆放。逐起点打点：精细档的 28 来自它自己的联合起点（束宽 600），首都和两个城址的 9 个区域连成一片，跨城互给加成。标准档的联合起点束宽 300，走不到这个形状；之后 24 轮扰动也跳不出来，因为扰动把区域逐个放回最好的空格，一次挪不动一整片。

**试过的做法**（离线基准 11 个场景：`bench_multi` 4 张图 × 只算相邻 / 计入地块，`bench_multipools` 3 张图；耗时为按单价折算的一次算完时间，与改动前比）：

| 做法 | 结果 |
|---|---|
| 联合起点本身的束宽加倍 | 种子 11 找到 28，但不单调：`bench_multi` 计入地块的种子 11 从 45 掉到 42。原来束宽 300 的联合起点正是拿到 45 的那个；宽束的最好模型布局局部搜索后只有 41 |
| 联合束搜索的前 3、5 个布局都做局部搜索 | 没有改进 |
| 另加一个 2 倍束宽的联合起点，照常做逐城轮换 | 11 个场景都不低于改动前，挑选 3/3 达到参照；耗时 +25–28% |
| 同上，束宽 1.5 倍 | 质量相同，耗时 +24%：这个起点的开销大半在逐城轮换，不在束宽 |
| 同上，2 倍束宽，不做逐城轮换（采用） | 质量相同，耗时 +18–19% |
| 再把扰动从 24 轮减到 8 轮以抵消耗时 | 计入地块的种子 41 少 1 分（48 → 47）。扰动在 2 个场景上各加了 1 分，不能省 |
| 精细档自己也加 2 倍（束宽 1200）的联合起点 | 11 个场景没有改进，耗时 +22%，不采用 |

逐起点的统计还显示，原有 5 个起点里第 1、3 个从未单独拿到最高分，第 4 个只有一次，且紧接着的第 5 个也拿到了同样的分。样本只有 11 个场景，删起点可能伤到别的地图，没有删。

**做法**（`Session:RunWideJoint`）：标准档在原来 5 个起点之后再跑一次联合起点，束宽是本档的 2 倍（`SDP_Tiers.Multi.STANDARD.WideJoint = 2`），只做局部搜索和换类型，不做逐城轮换（`WideRounds = 0`），然后照常扰动。原有起点一个不动，所以起点组合只增不减。只在 2 座城以上运行；单城加奇观时联合起点与逐城差别不大，不跑。精细档的前置是标准档（`PRELUDE_KEYS` 带上这两个参数），所以精细档也跑这个起点，仍不低于标准档的每个起点，耗时约多 7%。预计耗时另加 `WideWork = 20`（每槽每格的单位，约为标准档自身工作量的 23%），只在 2 座城以上计入。

**参照重算**：17.4 那组多城基准的参照解是 2026-10-19 算的。此后提交 8c14f2a 起候选格排除了不可移除的奢侈、战略资源（AGENTS 坑 26），旧参照里有的布局现在不合法：按当时的参照，标准档像是从 98.2% 掉到 95.4%，逐个提交二分后确认是参照过时，不是搜索退化。用当前代码重算参照（精细档 + 继续优化 + 2 万步模拟退火），只算相邻从 55、58、55、52 变为 54、57、50、52，计入地块从 46、50、44、48 变为 46、47、44、48。17.4 里"三档都停在 95%"的那张图（种子 37，只算相邻），按新参照标准、精细档都达到了。

### 22.2 港口与商业中心分城（默认打开）

**依据**（规则从数据读，`SDP_Rules.Apart`）：找建筑上的 `MODIFIER_PLAYER_ADJUST_TRADE_ROUTE_CAPACITY` 修正，其要求集合里有取反的 `REQUIREMENT_CITY_HAS_BUILDING`（参数 `BuildingType`）时，这个建筑所需的区域与参数建筑所需的区域配成一对。游戏规则里只有一对：灯塔（港口）的贸易路线容量要求本城没有市场（商业中心）。所以两者建在同一座城只多 1 条贸易路线，分在两座城多 2 条。特色区域按 `DistrictReplaces` 算作它替代的区域（英国皇家海军船坞、腓尼基U型港、马里曼丁哥市场）。

**行为**：
- 只约束"从候选里挑"：同一座城不挑两个配对的区域；城里已经有其中一个（已建、城市三环内已打钉、或设为必建）就不挑另一个。
- 必建的照建；方案里一座城同时有两者时（必建，或下一条的放行），结果多一行"港口与商业中心同城：灯塔不增加贸易路线"（`Together`）。
- "尽量"：只有不这样就凑不够区域数量时才放行（该城的组合全部冲突时，`ApartRelaxed`）。
- 多城按城判断。相邻加成不限同城，一座城的港口仍可给邻城的商业中心 +2，联合求解会倾向两城贴边布置。

**搜索**：`Search:Combos` 生成组合时跳过冲突的候选与组合（候选被城里已有的配对区域挡住时，先从池里去掉再按 `COMBO_LIMIT` 截断）；没有不冲突的组合时整组放行。`SwapMoves`（换类型）跳过会造成冲突的交换。挑选之外的搜索步骤不改变每座城的组合，不需要处理。

**界面**：开关在"占人口名额的区域"标题行中间（单城、多城两页），名称用规则里两种区域的名字（多于一对时写"部分区域分城"），悬停给出规则原文；规则集里没有这种修正时隐藏。英文的分组标题改短（"Need population"）以留出位置。

**影响**：现有离线基准和对比场景的候选池里没有港口，结果不变（22.4）。

### 22.3 社区的住房、保护区的魅力（`SDP_Appeal`）

**规则**（全部读 GameInfo，列名以规则库为准，AGENTS 坑 32）：
- 住房：`AppealHousingChanges`（`DistrictType`、`MinimumValue`、`AppealChange`）。社区基础 `Districts.Housing` = 4，魅力 ≥ 4 +2、≥ 2 +1、≥ -1 0、≥ -3 -1、其余 -2；保护区基础 1，最后一档 -1。刚果的姆班赞没有这些行，住房固定，不随位置变，不计。
- 保护区周边：`Adjacent_AppealYieldChanges`（古树林：迷人 食+1 信+1，惊艳 食+2 信+2 文+2；避难所：迷人 金+1 科+1，惊艳 金+2 科+2 产+2），只给相邻的未开发地块（`Unimproved`）。两个建筑都按已建计（与相邻加成不问建筑的约定一致）。
- 魅力变化：区域的 `Districts.Appeal`（圣地、剧院、娱乐中心、水上乐园、保护区等 +1，工业区、军营、航空港、宇航中心等 -1，奇观按 `DISTRICT_WONDER` +1）加给相邻格；建区域清掉的可移除地貌（`Features.Removable` 的 `Appeal`：树林 +1，雨林、沼泽 -1）和改良设施（`Improvements.Appeal`）从相邻格扣掉。

**模型**：某格的魅力 = 游戏当前的魅力（`Plot:GetAppeal`）+ 相邻的规划区域、奇观和未建的锁定钉带来的变化。已建的区域已经在游戏的魅力里。
- 住房项 = 住房权重 × Σ（方案里的社区、保护区，以及城市旁已建、已打钉的社区、保护区）的住房。方案让已有社区降档要付代价。区域占掉农场、牧场这类给住房的改良设施时城市少的住房，只在结果里提示，不算进这一项（22.6）。
- 保护区周边产出：每个相邻、未被方案或固定区域占用、无改良设施、城市能耕作的地块，按它在方案下的魅力得到上面的产出。打开"计入地块"时，这些产出加到地块模型里该格的值上（`SDP_Land.ScoreTaken` 的 `boost`），只有升进城市最好的 P 格才算；关闭时按各产出权重全部计入。打钉的保护区只计住房，周边产出不计（已建保护区的周边产出已在游戏的地块产出里）。从候选里挑出的保护区也只计住房，周边产出在结果里显示、标“候选，不计分”；设为必建时才计（22.6）。
- 一个方案的这一项 = 方案的值 − 空方案的值，所以没有社区、保护区时为 0，结果里 `AppealDelta` 为 nil。

**目标与权重**：住房单独一列权重（"住房"，0–3，默认 1），即 1 住房折合 1 点产出。目标 = 相邻 + 地块 + 覆盖 + 距离 + 住房与魅力。

**搜索**：`Search:Evaluate` 加这一项（每次精确评估：标记方案里的格，算社区、保护区所在格和保护区周边格的魅力，开销与区域数成正比；问题里没有这类区域时模型为 nil，不增加开销）。模型的单放分只给社区、保护区本身加上它单独放在这格时的值；其他区域对已有社区的影响只在精确评估里算。最初把后者也加进单放分，开发集上标准档在 2 个场景搜偏（S06 相邻 25 → 22，住房也没增加），去掉后 7 组受影响的场景目标总和从 993 升到 997。互惠表给"社区或保护区 + 会加魅力的区域"加 1 个住房权重的乐观项，让模型保持上界。

**显示**：结果行"住房 +6（魅力 4）"，保护区另写"周边地块 食+2 信+2 ……"；汇总行加"住房与魅力 +x"。

**局限**：魅力以游戏现在的值为底，文明、总督、政策、奇观的修正已含在内；但方案改变某格时（如清掉地貌），依附于那格原状的修正（如总督“林业管理”）不会跟着变。方案外以后才建的改良设施不在模型里；保护区的周边产出假设这些地块一直不开发。

  - 保护区的古树林、避难所建成后，立刻读和 3 秒后再读周边地块产出都没有变化（`HasBuilding` 为真）。想过一回合再读时，回合被外交界面挡住；关闭外交界面后游戏崩溃。崩溃发生在游戏自己的网络线程加载证书时（libcurl / libcrypto 检测到堆损坏），栈上没有 Lua。周边产出改在后期存档里，用 AI 自己建的保护区核对（22.6）。

### 22.5 真实鼠标点击测试（`tools/realclick.py`）

游戏窗口不向辅助功能暴露控件，电脑操作工具的点击会被它自己的安全校验拒绝（"无法确认窗口在编辑哪个文档"，2026-10-19 起一直如此）。改用系统鼠标事件：
- `tools/click/sdp-click.swift` 编译成 `~/Applications/SDPClick.app`（`python3 -I tools/realclick.py build`），在"系统设置 → 隐私与安全性 → 辅助功能"里授权一次。必须是用 `open` 启动的独立应用：macOS 按启动命令行工具的应用（这里是 Claude）判断辅助功能权限，单独给可执行文件授权无效。放在 iCloud 之外，因为 iCloud 给文件加的扩展属性让 codesign 失败。
- 点哪里由游戏自己给：在面板的 Lua 状态里取控件的 `GetScreenOffset` 和尺寸（UI 单位，1920 × 1080），按窗口大小换算成屏幕坐标，不靠截图估坐标。
- 每次点击前检查：游戏在最前（不在时用 `open -b` 唤到前台）、点在游戏窗口内、该点最上层的窗口属于游戏；任一不满足就不点。窗口所有者名称前有一个不可见字符（U+0092），游戏进程在系统应用列表里的 pid 是 -1，所以按名称包含 "Civilization VI" 找窗口。
- 套件开始前先关掉排队的弹窗（历史时刻、加速等全屏弹窗会盖住面板接住点击，第一次运行就是这样全部失败的）。
- 每一步点击后从面板状态读回结果核对；结束后把前台还给原来的应用。

### 22.6 后期存档压力测试（`tools/stress.py`）

发布前在 AI 自动打出的后期存档上跑一遍全部功能并计时。三个场景：风云变幻盘古大陆标准图（北条时宗，远古开局，联机速度 200 回合）、风云变幻大陆大图（威廉明娜，中世纪开局 150 回合）、迭起兴衰群岛（伯里克利，古典开局 170 回合）。每张存档上的步骤：普查；AI 自建保护区的周边产出；人口最多的 6 座城各做候选池（快速、标准，标准档求两次核对确定性）与最多 6 个必建；前 3 座城做“社区 + 保护区 + 工业区”和“港口与商业中心在候选里”；精细档；选城址 3 个；4 城、8 城多城与打钉；打满空格后重复单城、多城；面板各页签；全部撤销。最后让游戏把“社区 + 保护区 + 工业区”的方案建出来，读游戏的魅力和住房（`check`）。结果写在 `tests/stress/results/`，汇总见自测报告和“介绍与评测”页附录 B.8。

**发现并修好的**：

**测试工具上的**：
- 自动回合以玩家 0 身份观察时，AI 的外交发到本地界面等回答，回合停住；改为以观察者身份（AGENTS 坑 33）。自然灾害、世界危机弹窗占住事件队列也会停住，生成存档时每次轮询都关掉排队的弹窗。
- 读档后停在“继续游戏”按钮；读档前打开自动开始（AGENTS 坑 35）。
- 一次打很多钉后游戏要忙一阵：DMT 每收到一个新钉，就更新它和周围的钉，每次都把整张钉数据表读出、改一项、再存回。盘古大陆存档上一次打 83 个钉后忙了 12.6 秒；正常一次打 15 个钉约 0.25 秒。压力测试把这段等待单独记一步，后面的求解单独计时。

**住房与魅力的后期复核**：每张存档上，游戏把前三座城的“社区 + 保护区 + 工业区”方案建出来，读城市住房里“区域”“改良设施”两项的变化和社区、保护区格的魅力（`check`）。建法与玩家相同：在格上下令建造（`CityOperationTypes.BUILD`），再把这一项建完（`FinishProgress`）；建造前只给这座城补上这些区域的前置科技、市政和人口。最初用测试接口 `CreateDistrict` 直接建，后来发现它清不清地貌和正常放置不一样（AGENTS 坑 36）。

复核中发现并改进的两处模型：

| 问题 | 实测 | 修改 |
|---|---|---|
| 区域占掉农场这类改良设施，城市少的住房没算 | 改良设施的住房是全城“每块住房”（住房 ÷ 所需块数，农场 1/2）加总后向下取整：1 块农场 0，2 块 1，3 块 1，3 块农场加 1 块牧场 2 | `SDP_Appeal.ImprovementHousing` 按城市算出总和，方案拿掉的部分减掉后再取整；结果列表单列“占掉的改良设施：住房 -x”，只作提示，不计入分数。先试过计入“住房与魅力”：开发集 352 次运行里 70 次方案变了，面板默认设置（标准档、计入占地）84 次运行的相邻加成合计 -11、城市总产出合计 -5，两项都变差（农场一块只值半个住房，取整后时有时无，把方案推向别处），所以没有采用。离线测试覆盖取整 |
| 区域建在地貌上时本格魅力 | 用正常流程在各种地貌上建社区（社区本身魅力为 0，`tests/bench/probe_ownplot.py`）：树林 8 块里 6 块本格少 1（另 2 块读数不变，可能是陈旧读数）；雨林 2 块本格不变；邻格照常变化 | 清掉的地貌是正值（树林）才从本格扣掉，负值（雨林、沼泽）不扣。沼泽没有样本。v1.3.1 改正（#58）：两张风云变幻存档、新开的原版和迭起兴衰局里树林 16 块里 15 块本格不变（另 1 块 +1，格上有伐木场），只有群岛存档 4 块少 1，模型改为本格不随清掉的地貌变。v1.4.0 查清两个例外（#58）：① 玩家学了“自然保护”市政后，领土里从没砍过的树林（原生林）本格魅力 +1（市政说明原文；游戏的地块提示用 `Plot:HasFeatureBeenAdded` 区分原生林与种下的次生林），清掉后本格少 1。群岛存档那 4 块就是这种：存档里属于学了这项市政的玩家的 28 块树林，清掉后本格全少 1，其余 103 块全不变；给没学的玩家补上市政，他的树林也变成这样。v1.3.1 给盘古存档补市政后读数没变，是因为补市政后游戏不马上重算魅力，读到的是旧值。② 被掠夺的改良设施让本格和每个陆地邻格 -1（百科：“每个相邻的被掠夺单元格 -1”），区域把它拆掉后本格 +1、邻格多 +1。那 2 块本格 +1 的格（种植园、伐木场）都被掠夺过；在游戏里把种植园修好，本格和陆地邻格各 +1。模型加上这两项：原生林按 `Features.AddCivic`（规则表里只有树林有）；掠夺的 -1 是引擎规则，规则表里没有，写成常量。用新模型重算后期复核那 9 套方案（方案不变，每套前重新读档，再按正常流程建出来比），社区格的魅力和住房 9 套全部与游戏相同（v1.3.1 是 7 套） |

三张存档 9 个方案（正常流程）：社区、保护区格的魅力 17/17 相同；改良设施住房 9/9 相同；区域住房 8/9 相同。剩下的一个是盘古大陆东京的保护区：魅力 0，按规则表给 1 住房，游戏给 2；同一存档和另两张存档里魅力 3、-3、1 的保护区都对得上。东京有总督雷娜的“林业管理”，但这块地周围没有地貌，这条修正不适用。原因没有查明，模型在这里少算了 1。

**保护区周边产出只在必建时计分**（2026-10-22 定）：后期地图上惊艳、迷人的地块多，保护区周边产出动辄 40–70 点，从候选里挑时几乎总是先挑保护区（盘古大陆多城方案 +169 里有 +165 来自这一项）。这些产出要建古树林、避难所两座建筑才有，而其他区域的建筑产出都不计。所以改为：保护区设为必建时计入周边产出；从候选里挑时只计住房，周边产出照常显示，标“候选，不计分”。改后同一个多城方案是 +34（相邻 +40、地块 -6），截图已换。


## 23. 第三轮实测反馈：城址一环、帝国限建区域、奇观顺序（2026-10-22）

合作者在 Windows、风云变幻下报了三个问题（#26–#28）。

**城址一环（#26）**：多城方案把一座城的区域放到了另一个城址钉的一环里。游戏里新城建立时会拿走一环内没有主人的格子，原来那座城就建不了了。现有城市的一环早已归它自己，扫描时按 `OTHER_CITY` 排除，没有问题；漏的是还没建城的城址。现在 `SDP_City.Scan` 和 `ScanSite` 都排除“其他城址钉一环内、没有主人”的格子（`SITE_RING`）。城市已经拥有的格子不受影响，城址自己的一环照常可用。识别城址钉的代码从 `SDP_Multi.Sites` 挪到 `SDP_City.Sites`。这条对单城页同样生效：先打了城址钉，再规划旁边的城，也不会占用城址的一环。这些格子也不再算进这座城的占地。

**帝国限建区域（#28）**：共用清单里市政广场设为必建、每城数量 3 时，三座城都把市政广场算作必建，候选名额都是 0；而市政广场只生成一个槽位，求解器挑一座城放，另外两座城就各少一个区域。改为建槽位之前就分配：要它的城里按参与者顺序（城址在前，即城市列表从上到下）取前几座，数量是上限剩下的名额；其余的城记 `MAX_PER_PLAYER`，不再算作必建，候选名额相应加一。代价是不再由求解器在各城之间挑市政广场的位置。想放在别的城，就只在那座城自己的清单里设为必建。

离线对比（2026-10-22，`compare.mjs -s '^[SMCV][0-9][^~]*$' -p sdp`，436 次运行）：单城、选城址、覆盖范围三组 376 次的摆放与改动前逐格相同；本模组自报的加成与裁判相同，违规只有“没有位置”的漏放，与改动前相同。变的是多城组（每座城的清单都有市政广场且都是必建）：60 次里 28 次市政广场换了城（现在总在第一座城），30 次摆放不同。标准档 12 个场景的总加成 487 → 481，4 个场景各少 1–2，其余不变；快速档 481 → 475，精细档 487 → 482，计入地块的一组 440 → 446。这是上面说的代价：所有城都只要必建区域时，原来由求解器挑市政广场放哪座城更好。

**奇观顺序（#27）**：截图里的下拉框按内部类型名排序，正是 v1.0.0 的排序方式。v1.1.0 的代码（按时代、造价、类型）没有问题。2026-10-22 在 Mac 上实测过：Mods 文件夹里和创意工坊各有一份时，“额外内容”里两份都能启用，但开局时游戏只按模组 ID 找，加载先登记的那份，与启用哪一份无关（AGENTS.md 坑 38）。合作者在上架前手动装过测试包，Mods 里那份登记在前，所以最可能的情况是游戏一直加载着 Mods 文件夹里的旧版。本机这一轮的第一次游戏内测试也因此跑了创意工坊里的 v1.1.0（deploy 改了文件后，本地那份重新登记，排到了创意工坊那份后面）；`run_tests.py` 现在开测前检查，加载的是创意工坊那份就停下。为了让问题报告能说清加载的是哪一份，启动栏按钮的悬停提示加上了版本号（`SDP_Panel.lua` 的 `VERSION`，`validate.py` 检查它和 CHANGELOG 最新的版本一致）；问题模板改为让玩家照这里填。

## 24. 第四轮实测反馈：领土连通、预览显示、预览图（2026-10-23，v1.1.2）

合作者第四轮提了 #33、#34、#35、#41 四个问题，这一版一起修。

**领土连通（#35，#38）**：多城方案把京都的娱乐中心放到了三环的东南角，它和京都之间的格子都是城 2、城 3 规划的区域。游戏里城市只能扩张或购买挨着自己领土的格子，城 2 建起来后那格成了飞地，京都永远拿不到。原来的候选格规则只排除其他城址一环内无主的格（第 23 节的 `SITE_RING`），没有考虑连通。现在分两层：

- 扫描（`SDP_City.Scan`、`ScanSite`）：从城市现在拥有的格（城址：中心加一环）出发，经三环内无主的格相邻扩展（其他玩家、其他城的格和其他城址的一环都不能经过），到不了的无主格排除（`UNREACHABLE`）。`scan.Reach` 记下起点集、可经过集和可达集。单城页同样生效：被别国领土隔开的格不再规划。
- 布局（`SDP_Search.Reachable`，`spec.Reach`）：多城评估每个布局时，对每座城再走一遍，这次把其他城在这个布局里放的区域当作挡住的格；哪座城的区域连不回去，这个布局就不合法。只有别的城的区域落在这座城可经过的格上时才走，走一遍不超过几十个格，远比一次 DMT 评估便宜。奇观不挡路、也不要求连通（它属于拥有那格的城，由玩家决定）。

没有做的是“按距离分格”（离别的城更近的格留给它）：那不是游戏规则，中间的无主格以后归谁取决于文化扩张和购买的先后。结果里改为标出“需先扩张或购买”，由玩家决定买不买。

**暂不能建的标注（#38）**：`scan.Candidates` 每格带 `Unowned`（城市还没拥有；城址的一环算拥有）和 `RemoveTech`（`Features.RemoveTech` 里玩家还没有的科技，如树林要采矿）。方案里的每个区域照抄这两项，结果行写“（需先扩张或购买）”“（需先研究采矿）”。只是提示，不进分数、不改合法性；要科技的格游戏当下不让建，研究后就可以。

**裁判**：离线对比的裁判（`CmpRun.Judge`）加了同样的连通检查（违规种类 `unreachable`，算硬违规）。

## 26. v1.2.0：淹没的沿海低地、奇观的同城区域（2026-10-23，#44、#45）

两条都是第 25 节的引擎审计发现的、引擎有而 DMT 没有的规则。

**淹没的沿海低地（#44）**。`SDP_City` 的候选格排除风云变幻里沿海低地中当前被淹没或已沉没的格（`TerrainManager.GetCoastalLowlandType(plot) ~= -1`，且 `IsFlooded` 或 `IsSubmerged`），排除原因 `FLOODED`；没有 `TerrainManager`（原版、迭起兴衰）时不排除。只看当前状态，不预测以后的海平面。在大陆存档上实测：城市修了防洪堤（`BUILDING_FLOOD_BARRIER`）后，它的格 `IsFlooded` 立即变为假，引擎恢复可建，本模组的排除也随之取消，不需要另外处理。离线对比：导出工具把低地类型和淹没状态写进场景（`low`、`flooded`、`submerged`），模拟引擎由此回答 `TerrainManager`，裁判把放在淹没格上的区域记为违规（`flooded`），判“有位置却没放”时也不算这些格；大陆存档的 12 个场景重新导出，场景核对仍 0 差异。审计复核：大陆存档 1368 组里一致 1361，余下 7 组都是运河（坑 27），淹没格的差异没有了。

**奇观的同城区域（#45）**。`SDP_Search` 多了 `Owners`：每个候选格可能归哪些城（哪些参与城市的候选里有它），每个固定区域属于哪些城（它的格在哪些参与城市的领土或可达范围里）。需相邻某区域的奇观，只有挨着其中一座城的那种区域（固定的，或布局里分给那座城的）时才算合法；单独评估时只看固定区域，挨着候选格时只用同一座城能用的候选格。单城页放奇观走的也是 `SDP_Multi`（只有这一座城），同样生效。裁判对奇观逐个检查：旁边有所需区域、但都不是同一座城的，记为 `wonder_other_city`。离线测试：首都的学院挨着城址的格，只规划城址时大图书馆不再放在那里。

## 27. 第五轮反馈：地块价值、换格、住房（2026-10-23，#52、#54、#55、#56）

合作者的五条反馈先由子 agent 调研（规则库、游戏代码、玩家社区、对比模组），结论和方案写在各 Issue 里，维护者确认后再改。#53（默认权重）移到里程碑“目标与权重”，只做调研和实验。

### 27.1 地块价值（#52）

- 规则：建区域会移除格上的可移除地貌和加成资源，不给一次性产出；先砍伐、先收获再建才有。社区里先砍后建、丘陵留给矿山都有多个独立来源。
- 每格的价值改为修上改良后的产出（`SDP_Land.PlotValues`）：从 `Improvement_ValidTerrains/Features/Resources` 推出能修的改良，取 `Improvement_YieldChanges` 加上玩家已有科技、市政的 `Improvement_BonusYieldChanges` 最好的一个；有自己改良的资源只能修那种改良。地貌、资源保留和移除各算一次，取较高的；保留的一方要扣掉放弃的一次性产出。已修改良的格直接用 `GetYield`。不算农场三角、特色改良、政策。
- 一次性产出随进度增长：× (1 + 9 × max(科技进度, 市政进度))（社区公式，待游戏内核实）。玩家看不见的资源，产出从 `GetYield` 里扣掉。特性禁止收获的文明（`MODIFIER_PLAYER_ADJUST_PREVENT_HARVEST_RESOURCE`）不收获。“允许移除地貌”关闭时地貌保留。
- 一次性产出不再算作区域的损失：地块分只算耕作的 P 格。城址的地貌分仍是它能砍、能收的一次性产出。
- 结果行提示“先砍伐或收获”，以及收获资源需要的科技（`Resource_Harvests.PrereqTech`，原来只提示地貌的移除科技）。

### 27.2 换格与重叠格（#54）

- 实测（后期存档，本方全部城市，`CityManager.GetCommandTargets(city, CityCommandTypes.SWAP_TILE_OWNER)`）：本方城市之间能换的格同时满足挨着本城领土、格上没有区域、不在对方市中心一环内；换后本城能在那格建区域。
- 这类格成为候选格（`SDP_City` 的 `Reach.Swap`，候选的 `Swap` 为原来的城），结果写“需从某城换格”。由单城、多城页的开关“从本方其他城换格”控制（请求的 `Swap`，默认关闭）：下面实测的代价（手动换格、求解约慢一倍）由玩家权衡，维护者 2026-10-24 定为默认关闭。耕作损失记在原来那座城：单城页签为这些城各建一个地块模型（只含它已有的格），多城页签里城市已有的格留在它的地块模型里。
- 单城页签里无主、离另一座本方城市更近的格，耕作分归那座城（与多城页签一致）。
- 离线对比的裁判按同样的条件认可换格（`cmp_lib.lua` 的 `Swappable`，记 `swapped` 格数），不再判 `other_city_tile`、`unreachable`。
- **开关的实测数字**（面板提示引用，改了求解器、规则或测试集后重跑并更新提示）：`node tools/compare.mjs -s '^R[MS]' --add sdp:STANDARD_SWAP,sdp:STANDARD_SWAP_LAND --only sdp:STANDARD,sdp:STANDARD_LAND,sdp:STANDARD_SWAP,sdp:STANDARD_SWAP_LAND`，结果在 `tests/compare/results/swap.jsonl`。v1.3.0（2026-10-24）：

### 27.3 住房（#55、#56）

- 规则：住房比人口多 2 及以上时全速成长，多 1 时半速，追平后 1/4（`CITY_HOUSING_LEFT_*`）。
- 一座城的第 k 点住房，在目标人口 T 以内算 1，之后每多一点减半：累计价值 `HousingValue(n, T) = n`（n ≤ T），`T + 1 − 0.5^(n−T)`（n > T）。住房部分按城市分别累计（`SDP_Appeal` 的 `Cities`）：方案前的住房是游戏给的 `GetHousing()`（城址、市中心钉为水源住房加粮仓），减去模型自己计入的已建住宅区；T 取当前人口和建齐计划特色区域所需人口中较大的。
- 选城址：水源分改用单独的住房权重（默认 1，“成长优先”为 2），不再乘食物权重；计划 3 个区域时默认结果不变。计划里有港口时把港口建筑的住房计入城址（不影响港口放哪格），是“建筑产出不计”的例外。

## 28. 奇观要挨着的改良设施（2026-10-24，#51）

**哪些奇观**：规则表里 `Buildings.AdjacentImprovement` 非空的只有阿耳忒弥斯神庙（`IMPROVEMENT_CAMP`，迭起兴衰、风云变幻；原版没有这个奇观）。营地只能建在鹿、皮草、象牙、松露上（`Improvement_ValidResources`，保留地貌），必须在本方领土（`CanBuildOutsideTerritory` = 0）。代码只读这一列，不写奇观名。

**DMT 认不认改良钉**：认。`IsAdjacentToImprovement` 读邻格的 `GetMapPinSubject`，`Type = "IMPROVEMENT"` 的 subject 直接算作那种改良，所以 overlay 里放一个营地 subject，神庙的 `CanPlacePin` 就通过。但 DMT 不检查改良本身能不能建在那格（`CanPlacePin` 对改良是 TODO），这部分由本模组按规则表判断（AGENTS 坑 43）。

**引擎探针**（`tests/bench/probe_camp.py`，风云变幻新局，首都 A 和四格外的城 B 各拥有两环，给全部科技；在 A 的一格旁放营地，问引擎 A 能不能在那格建神庙：`CityManager.GetOperationTargets` 与 `CanStartOperation`）：

| 营地在 | 引擎 | DMT |
|---|---|---|
| A 自己的格 | 6/7 允许（不允许的一格压着铝，奇观不能建在战略资源上，候选格本来就排除） | 7/7 允许 |
| B 的格（别的本方城市） | 3/4 允许（不允许的一格压着葡萄，奢侈资源，同上） | 4/4 允许 |
| 无主格 | 0/4 允许 | 4/4 允许 |

结论：营地属于哪座本方城市都行（与需相邻区域的奇观要求同城不同，第 26 节），但要在玩家的领土里。另在核心状态里全图比较本模组的营地规则与 `ImprovementBuilder.CanHaveImprovement`：3404 格全部一致。这个接口在界面状态里是 nil，所以规划时只用规则表（接口存在时也问它）。

**做法**：

1. 建奇观槽时（`SDP_Multi`）对每个候选位置算 `SDP_Wonders.Support`：旁边已有玩家的营地或营地钉时不用再放（`Needed` 为假）；否则列出旁边能放营地的格（`Plots`，按格序号排序）：已揭示，没有市中心、区域、奇观、自然奇观、改良、钉，不是被淹的沿海低地，是玩家的格或参与城市能扩张到的无主格（`Reach.Reached`），且规则允许（有自己改良的可见资源只认那些，否则看地貌、地形）。没有任何位置能满足时奇观不进求解，原因“需要相邻营地，但附近没有能建它的格”（`NEEDS_IMPROVEMENT`）。
2. 搜索（`SDP_Search`）不枚举营地位置：每次评估布局，对每个需要营地的奇观取它的列表里第一个没被布局占用的格（`SupportPlots`），取不到就判不合法。营地作为“静默”的棋盘槽放上（`SDP_Board.Put` 的第三个参数）：DMT 看得见它（奇观的合法性、邻居的相邻加成按有营地算），它自己没有分数也不判合法性。棋盘按“先撤走换了位置的营地，再移动区域，最后放营地”的顺序更新，区域移到营地格上时营地自动换到下一格。单独评估奇观（`Singles`）时同样放第一个营地格。
3. 计分：营地自己的产出不计（宜居等奇观效果本来就不在目标里），方案的分数与不放营地时的定义相同；营地格仍可耕作，地块分不变。最后的完整评估（`SDP_Overlay.Evaluate` 的 `extra`）把营地放在图层上但不计分，与搜索一致。
4. 结果：奇观的方案项带 `Support = { Type, X, Y, Index, Unowned }`。两个页签在奇观那一行下面列一行营地（“供阿耳忒弥斯神庙相邻”，未拥有的格写“需先扩张或购买”），预览显示营地图标，打钉时和奇观在同一批，名字是城市编号，撤销一起删；再规划时本模组的营地钉随“替换之前的钉”一起换掉，别人打的营地钉当作固定邻居（约束 7）。
5. 不做：科技检查（建神庙要射术，射术的前置是畜牧业，能建神庙就能建营地）；营地带来的宜居计分；工业区挨矿山这类改良钉的规划（另开 Issue）。

**验证**：离线测试 `tests/offline/spec_support.lua`（假世界加了鹿、营地和一个需相邻营地的奇观：有鹿时奇观带营地、营地格不被区域占用、区域移到营地格时营地换格且棋盘与完整评估一致、没有营地格时给原因、已有营地钉或已建营地时不再放、两个页签的结果行、预览、打钉与撤销）。离线对比新增 `WA` 组 8 个场景（tools/README）：本模组标准档和计入占地各 8 次运行，奇观全部放上、营地全部合法、自报加成与裁判一致（`tests/compare/results/wonders_artemis.jsonl`）。AMT 也随神庙打营地钉（对比框架原先把它的改良钉丢掉，裁判因此判神庙不合法，现已传给裁判），8 个场景全部合法；EP 只认已建的营地，8 个场景都没放神庙。相邻加成本模组标准档对 AMT 4 胜 2 平 2 负，对 EP 6 胜 1 平 1 负；输给 AMT 的两个场景营地格相同，差在区域摆法。游戏内 `tests/test_support.lua`（夹具在首都两环放鹿）。
