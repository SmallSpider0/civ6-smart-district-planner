# 多城规划设计：城址 + 多城区域 + 奇观

**状态：已确认（2026-10-19，第 12 节的待定项按默认）。阶段 8–12 已完成（第 15、16 节），2026-10-20 在游戏内三种规则集下验证，并按实测校准了耗时（第 17 节）。**第 8 节的耗时是开发前的推算，实测见第 17 节。各档质量来自离线基准（第 9.5 节），用的是简化的假 DMT；游戏内只验证了正确性和耗时，没有游戏内的质量基准。

本文描述新增的两步流程：
1. **选城址**：在已探索的地图上为若干座新城选位置，给出多套方案供预览和选择。
2. **多城区域 + 奇观**：对新城（及可选的现有城市）联合规划区域和奇观，同样给出多套方案。

单城规划的流程不变，新增**求解档位**和**继续优化**（第 7 节），并计入**占用地块的产出损失**（4.2，面板上可关闭）。单城求解算法在阶段 8 重写（第 15 节）：同样的耗时下质量明显更高，结果不再与旧版本逐位相同，改由基准测试保证不差于旧版本。

## 1. 与需求文档的关系

需求文档第二节的约束不修改，以下几处是本功能对它们的扩展，在此记录：

| 约束 | 单城规划 | 两步流程 |
|---|---|---|
| 3 目标函数 | 五种相邻产出加权和，另计入区域占用地块的产出损失（见 4.2，可关闭） | **第 1 步城址评分**另外计入地块产出、水源、资源、地貌等（见 3.3）；**第 2 步**在相邻加成之外计入区域、奇观占用地块的产出损失（见 4.2） |
| 性能（停顿 ≤ ~2 秒） | 快速、标准两档同步计算（≤ 0.8 秒）；精细档分帧 | **分帧计算**：每帧只算一小段，单帧停顿远小于 2 秒；总耗时更长，有进度条和取消 |
| 结果质量 | 两区域穷举时最优；三档可选，可继续优化 | **不保证最优**，改为四项可测试的保证（见 4.7）；三档可选，给出多套方案、质量指示，可继续优化 |

确定性（约束 6）完全保留：只遍历排序数组，预算按计数，同分有确定的决胜规则，结果与分帧方式无关（见第 6 节），也与机器快慢无关（见 7.1）。

## 2. 总体结构

```
SDP_Panel（面板，三个页签：单城 / 城址 / 多城；每页有档位选择）
 ├─ 单城：SDP_Solver（为一座城搭好问题，交给 SDP_Search）+ 档位 + 继续优化
 ├─ 城址（第 1 步）
 │   ├─ SDP_Sites       候选城址、各项因素、城址得分
 │   └─ SDP_SiteSolver  城址组合搜索、多套方案
 ├─ 多城（第 2 步）
 │   ├─ SDP_Multi       参与城市、格子归属、联合求解、增量评估、多套方案
 │   └─ SDP_Wonders     可规划奇观、奇观合法性
 ├─ SDP_Search          搜索引擎：单项表、穷举、模型集束搜索、局部搜索、扰动重建（单城和多城共用）
 ├─ SDP_Board           增量 + 记忆的 DMT 评估（4.6）
 ├─ SDP_Land            地块部分（4.2）
 ├─ SDP_Tiers           三档参数（单城、第 1 步、第 2 步集中定义在这一处）
 ├─ SDP_Task            分帧调度：进度、取消、局面变化检测、耗时统计
 ├─ SDP_Preview         地图预览：格子着色 + 地图图标，不打真钉
 └─ 复用：SDP_Overlay / SDP_Solver / SDP_City / SDP_Rules / SDP_Pins
```

两步之间通过**地图上的市中心钉**衔接：第 1 步采用的方案打成市中心钉（图标 `ICON_DISTRICT_CITY_CENTER`，DMT 会把它当作市中心计算）；第 2 步读取地图上全部市中心钉，包括玩家手放的。因此只用第 2 步也可以：玩家自己放市中心钉，再做多城规划。

## 3. 第 1 步：选城址

### 3.1 输入

- 新城数量 K（默认 3，上限 6）。地图上已有的市中心钉视为已选定的城址，另外再选 K 个。
- 最远距离 D（默认 8，可调）：每个城址离本国某座现有城市、或本方案里另一个城址不超过 D 格，允许"接力"向外扩张（见 3.5）。
- 计划的区域（所有新城共用一份，用于估算区域分和所需人口；第 2 步可按城修改）。
- 权重：预设或手动调整（见 3.3）。
- 方案数 N（默认 3）。
- 档位（见第 7 节）。

### 3.2 候选城址

候选为全部已揭示的格子，排除：
- 水域、山脉、不可通行的格子；
- 不能建城的地貌（`Features.Settlement = false`，如绿洲、自然奇观）；
- 他国领土；
- 与任何城市（含他国、城邦）或已有市中心钉距离不超过 `CITY_MIN_RANGE` 的格子。间距从游戏数据读（Base `GlobalParameters.xml:98`，值 3），不用 DMT 写死的 3（`IsValidCityCenterPosition`，`dmt_yieldcalculator.lua:613`），这样改了城市间距的模组也能算对；
- 三环内未揭示格超过一半的格子（信息太少，评分不可靠）；
- 离本国最近的现有城市超过 K × D 格的格子（接力也到不了；是否真能接力到，在 3.5 的组合搜索里检查）。

游戏的定居透镜接口 `Map.GetContinentPlotsWaterAvailability()`（`MinimapPanel.lua:565`）会返回"不能建城"的格子列表，用来交叉校验上述规则（覆盖范围需实测）。游戏 AI 的推荐城址 `GetSettlementRecommendations`（`WorldViewIconsManager.lua:710`）只作对照显示，不参与计算。

**两级筛选**：
1. **粗评**（不调 DMT）：按 3.3 中除区域分以外的各项给全部候选打分，取前 M 个（按档位 20 / 40 / 80）。
2. **精评**：对这 M 个城址用 DMT 估算区域分，得到完整的城址分。

粗评不含区域分，相邻加成很高但地块很差的城址可能在第一级被筛掉。缓解办法：精细档的 M 更大；继续优化会逐批放宽 M（见 7.3）；玩家可以手放市中心钉，直接进入第 2 步。

### 3.3 因素与得分

| 类别 | 因素 | 数据来源（全部运行时读取） | 计入方式 |
|---|---|---|---|
| 成长 | 水源 | 河流 `plot:IsRiver`、湖 `IsLake`、带淡水的地貌（`Features.AddsFreshWater`，如绿洲）、沿海 `IsCoastalLand`；住房 `CITY_POPULATION_RIVER_LAKE / COAST / NO_WATER`（5 / 3 / 2） | **水源分** = （该城址住房 − 无水住房）× 食物权重 |
| | 地块产出 | `plot:GetYield`（六种产出，已含可见资源） | **耕作分** = 三环内（除去区域占用格）产出最好的 P 格的加权和；P 是建齐计划特色区域所需人口：k 个特色区域需 `3k − 2`（名额公式 `1 + floor((人口-1)/3)` 的反推） |
| | 引水渠潜力 | 市中心是否挨着山、河、湖（合法性由 DMT 判定） | 只显示，不计分（引水渠的住房由修正器决定，不做解析） |
| 资源 | 奢侈资源 | `Resources.ResourceClassType`、`Happiness`（一种奢侈资源可供几座城宜居度）；每格份数 `plot:GetResourceCount`；玩家已有数量 `GetResourceAmount` | **奢侈分** = 宜居权重 × （Σ 新种类的 `Happiness` + 重复份数 × 重复价值）。新种类是玩家还没有、本方案第一次获得的种类，只有它的第一份算新种类；其余每一份（已有种类的、方案内重复的）都算重复份数，可用于交易，重复价值默认 1 |
| | 战略资源 | 同上，`RESOURCECLASS_STRATEGIC`；风云变幻按每格每回合开采量 `Resource_Consumption.ImprovedExtractionRate`，原版和迭起兴衰按每格份数；可见性 `IsResourceVisible` | **战略分** = 战略权重 × （Σ 各格数量 + 新种类数 × 2）。未研究对应科技的战略资源看不到，界面提示"可能还有未知资源" |
| | 加成资源 | `RESOURCECLASS_BONUS`；收获的一次性产出 `Resource_Harvests`（如铜 40 金币） | 每回合产出在耕作分里；一次性收获价值计入地貌分 |
| 地貌 | 树林、雨林、沼泽等可移除地貌 | `Features.Removable`；砍伐的一次性产出 `Feature_Removes`（树林 20 生产力、雨林 10 生产力 + 10 食物、沼泽 20 食物） | **地貌分** = 地貌权重 × Σ 各格（一次性产出 ÷ 折算回合数 20）× 对应产出的权重；加成资源的收获价值也按同样方式计入。地貌带来的相邻加成（如圣地挨树林）在区域分里，每回合产出在耕作分里，界面分类显示各种地貌的格数 |
| 区域 | 区域潜力 | DMT（见 3.4） | **区域分** = 该城址计划区域的最佳摆法的加权相邻加成（线性模型估计）。山脉、雨林、自然奇观、河流等带来的相邻加成都在这里体现 |
| 地形 | 山脉 | 地形表 `Mountain` | 不能耕作、不能建区域，体现在耕作分和可用格数里；相邻加成体现在区域分里 |
| | 自然奇观 | 地貌表 `NaturalWonder` | 不能建城、不能建区域；自身产出在耕作分里；相邻加成在区域分里；提高周边魅力 |
| | 魅力 | `plot:GetAppeal` | **魅力分** = 三环内可建区域格的平均魅力 × 魅力权重（默认权重 0，即默认不计） |
| | 可用格数 | 三环内能建区域的格子数 | 少于计划区域数时扣分；少于一半时该城址判为不可用 |
| | 泛滥平原、火山土（风云变幻） | 地貌 | 产出已在耕作分里；另外显示灾害风险提示 |
| 区位 | 与本国城市重叠 | 三环重叠格 | 组合级处理（见 3.5） |
| | 他国边界 | 他国领土格 | 已属他国的格子不可用，自然降低各项得分；另外显示"三环内他国格数" |
| | 忠诚度（迭起兴衰、风云变幻） | 9 格内各城人口与距离；常数 `CITIZEN_IDENTITY_PRESSURE_*`（`Expansion1_GlobalParameters.xml`） | **只作风险提示**：外国压力不超过本国为"低"，不超过 2 倍为"中"，超过为"高"（阈值为初值）。真实公式还受总督、时代、政策影响，只能近似，不计分 |
| | 未揭示格 | 可见性 | 不计分，显示数量 |
| 特性 | 文明、领袖特性 | 区域相邻类特性由 DMT 计入 | 改地块产出的特性（如马里的沙漠）在无主格上 `GetYield` 可能读不到（需实测） |

**城址分** = 区域分 + 耕作分 + 水源分 + 奢侈分 + 战略分 + 地貌分 + 魅力分 − 可用格不足扣分

奢侈与战略的重复价值、新战略种类的加分、折算回合数都是初值，按基准测试和试玩反馈调整。

风险提示（忠诚度、未揭示格、灾害、离本国最近城市的距离、可能有未知战略资源）显示在城址和方案上，不计入得分。

**权重**：原有五项（科、文、信、金、产）加食物、宜居、战略、地貌、魅力共十项，取值 0–3。面板默认只显示预设，展开后可逐项调整：

| 预设 | 科 文 信 金 产 | 食物 | 宜居 | 战略 | 地貌 | 魅力 |
|---|---|---|---|---|---|---|
| 均衡（默认） | 1 1 1 1 1 | 1 | 1 | 1 | 1 | 0 |
| 成长优先 | 1 1 1 1 1 | 2 | 1 | 1 | 1 | 0 |
| 区域优先 | 2 2 2 2 2 | 1 | 1 | 0 | 1 | 0 |

### 3.4 区域分的估算

对 M 个城址逐个跑完整的单城求解太慢，改为：
1. **共享单项表**：对 M 个城址三环的并集（标准档约 600 格），用 DMT 评估每种计划区域在每格上单独放置的得分和合法性。这时不放假想市中心。
2. **市中心修正**：每个城址的市中心只影响它相邻的 6 格（相邻加成和引水渠等合法性），把这 6 格在放上该城址市中心后重新评估。
3. **线性模型**：用现有求解器的线性模型（单项分 + 区域互惠表）做深度优先搜索，得到该城址的最佳区域摆法和区域分。每个城址的节点预算按档位（5 千 / 2 万 / 4 万）。

这一步得到的是估计值，第 2 步再用 DMT 精确求解。

### 3.5 组合搜索与多套方案

从 M 个城址中选 K 个：
- **间距**：所选城址之间、与现有城市之间距离都大于 `CITY_MIN_RANGE`。
- **接力距离**（评审确认允许接力）：把现有城市、地图上已有的市中心钉和所选城址看作点，相距不超过 D 的两点之间连线；每个所选城址都必须能沿这些连线连回某座现有城市。这一条件在分支定界的每个节点上检查，不影响上界的有效性。
- **组合级修正**（只有选定一组后才能算）：
  - 新种类按组合判定：一组城址里同一种新资源只有第一份算新种类，其余算重复份数；
  - 重叠格只能归一座城：耕作分、地貌分和资源分里，重叠格分给对它估值最高的城（同分时给编号小的城）；
  - 两城的区域摆法落在同一格时，扣掉冲突区域换到次优格的损失。
- **分支定界**：城址按得分排序；上界 = 已选得分 + 剩余最好的若干个城址单独得分之和。组合级修正只会减分，所以这个上界对估计分有效。节点预算按档位（10 万 / 50 万 / 200 万）。
- **多套方案**：保留前 N 套"足够不同"的组合：一套方案与排在它前面的每一套相比，至少有一个城址与对方所有城址的距离都 ≥ 2 格。

### 3.6 输出

每套方案列出：总分、各城址的分项得分与风险提示、质量指示（见 7.4）。选中某套即在地图上预览（第 5 节）。点"采用"后为每个城址打一个市中心钉（名称为城址编号，接在现有城市的编号之后），可以撤销；采用后玩家可以手动挪动或增删这些钉。

## 4. 第 2 步：多城区域 + 奇观

### 4.1 参与城市与格子归属

- **新城**：地图上全部市中心钉（第 1 步打的和玩家手放的）。
- **现有城市**（评审确认默认一起规划）：
  - 离任一新城不超过 7 格的现有城市默认勾选，一起规划新区域。7 格以内两城的三环才可能相邻，区域才会互相影响。
  - 更远的现有城市只作固定邻居（已建区域和已有钉计入总分但不动）。
  - 可逐城勾选或取消。参与规划的城市总数（新城 + 现有城市）上限 8；超过时按离新城的距离取最近的，其余只作固定邻居。
  - 现有城市要规划的区域默认取计划区域中该城尚未建造、也没有钉的那些，可按城修改。已建区域和已有钉照旧锁定。
- **每城的候选格**：三环内，排除他国领土、市中心、已有区域、奇观、自然奇观、已有地图钉（沿用 `SDP_City` 的规则）。另外：
  - 新城不能用已属本国其他城市的格子；
  - 现有城市只能用自己的格子和无主格；
  - 无主格默认之后能获得。
- **重叠格**：两座城都够得着的格子，可以出现在两座城的候选里；求解时一格只能放一个区域或奇观，放了谁就归谁。

### 4.2 目标函数

联合总分 = 相邻部分 + 地块部分：
- **相邻部分**：与单城规划相同，所有新区域和所有固定 subject（各参与城市四环内的已建区域、市中心、锁定钉）的加权相邻加成，权重为五项（科、文、信、金、产）。跨城相邻（两座城的区域挨在一起互给加成）由 DMT 自然计入。
- **地块部分**（评审确认计入）：每个参与城市的耕作分与地貌分，定义同 3.3。区域或奇观占掉一格后，这格不能再耕作；建区域会移除地貌，砍伐价值也随之消失。
  - 耕作分按"人口 P 能耕作的最好 P 格"计算，所以占掉一个好格的损失是它与第 P+1 好的格子之差，而不是它的全部产出；占掉一个本来就不会耕作的格子没有损失。
  - 新城的 P 按建齐该城计划特色区域所需人口；现有城市取当前人口与这个数的较大者。
  - 权重为五项加食物、地貌。

提升 = 联合总分 − 基线（不放新区域、新奇观时的联合总分）。

单城规划同样计入地块部分（评审确认），P 的取法同现有城市；面板上有开关"计入占用地块的产出损失"，默认打开，关闭时只算相邻加成，与现有版本一致。

### 4.3 全局约束

- 每城每种区域最多一个（社区等可重复区域的多个放置，沿用单城的限制）。
- 全帝国有上限的区域（如政府广场）：已建 + 已有钉 + 本方案合计不超过上限。
- 新城的特色区域名额：只提示不阻止（与单城一致）。
- 奇观：每个奇观全局最多一个；已被任何玩家建成、或已有本玩家钉的奇观不再规划。

### 4.4 奇观

- **可选奇观**：`MapTacks.PlayerWonders` 中 `Buildings.IsWonder` 的条目（去掉它附带的通用奇观图标 `DISTRICT_WONDER`），玩家勾选要建的奇观。不检查科技与时代（属于提前规划）。
- **合法性**：DMT `CanPlacePin`，subject 为 `{ Type = "WONDER", Key = 奇观类型 }`（`dmt_yieldcalculator.lua:387`）。DMT 已覆盖地形、地貌、河流、海岸、湖泊、山脉、需相邻资源等规则；"需相邻某区域"会读假想区域（`IsAdjacentToDistrict` 读 `GetMapPinSubject`）。
- **需相邻区域时要求同城**：DMT 不区分区域属于哪座城，本功能保守地要求该区域属于奇观所在的城（需实测游戏规则）。
- **得分**：奇观本身没有相邻产出（DMT `GetBonusYields` 只对区域和改良设施取产出），它对目标的影响全部来自邻居：如剧院广场（及其特色区域雅典卫城）每相邻一个奇观加文化（`Wonder_Culture`，原版 +1，迭起兴衰、风云变幻改为 +2，由 DMT 从数据读取），以及它占掉的格子和移除的地貌。奇观自身效果（如佩特拉让沙漠增产）不计。
- **放不下的奇观**：列出原因（DMT 的不可放置说明）。

### 4.5 求解

待摆放的对象是"（城市，区域）"和"奇观"。下文中轮数、起点数、局部搜索动作、评估上限都按档位取值（见 7.2）。

起点和块坐标上升里调用的单城求解器要加一个可选的"地块部分"：线性模型里把每格的占用损失（按该城当前第 P+1 好的格子近似）作为该格的单项扣分，精确评估时按 4.2 计算。单城模式默认也启用这一项；关闭时结果与现有版本相同。

1. **准备**：每个参与城市在 overlay 中放上它的市中心，用 DMT 评估每个对象在每个候选格上的单项得分与合法性。第 1 步的单项表在局面未变时直接复用。
2. **起点**：按城市编号依次用现有单城求解器规划，前面城市的方案作为后面城市的锁定邻居；然后把奇观按"合法格最少的先放"逐个放到单项得分最好的合法格。
3. **块坐标上升**：轮流固定其他城市，用单城求解器重解一座城（奇观作为固定邻居）；再对奇观整体重排。迭代到总分不再提升或达到轮数上限。
4. **全局局部搜索**：按档位允许的动作，采用提升最大的一步，直到没有严格提升或预算用尽。每一轮候选动作有几百个，不能都做 DMT 评估：先用线性模型给全部候选动作打分，只对得分最高的前 k 个（按档位 10 / 20 / 40）做 DMT 增量评估。动作有三种：
   - 单个移动：一个对象移到另一个空闲合法格（含其他城市的重叠格）；
   - 两两交换：两个对象互换位置；
   - 成对移动：两个相邻的对象一起挪到另一对相邻的空闲格。用来跳出"整体平移才更好，但单独挪任何一个都会先降分"的局部最优。
5. **多套方案**：从**固定的起点序列**中依次取起点，各做一遍 3–4：
   - 起点 1：按城市编号顺序；
   - 起点 2：按城市编号逆序；
   - 起点 3 起：依次改用各城单城求解短名单中的次优布局（按城市编号、短名单名次的固定顺序枚举）。

   本档位取前若干个起点（3 / 5 / 9），继续优化时接着往后取（见 7.3）。结果按总分排序，保留"足够不同"的方案：与排在前面的每一套相比，至少有 max(2, 对象数的 20%) 个对象的位置不同。不足 N 套时如实显示实际套数。

所有同分比较按（城市编号，对象类型，plot index）字典序决胜。

### 4.6 增量评估

多城时固定 subject 有几十个，每次全量评估约 12 毫秒（推算），局部搜索要评估几百到上万次。阶段 8 实现为 `SDP_Board`（单城也用），比原计划的增量评估更进一步：

- **增量**：一个对象从格 A 移到格 B 时，只重算 A、B 及其相邻格上的 subject。
- **记忆**：一个 subject 的得分只取决于（它的类型、所在格、相邻 6 格上的规划对象）。`SDP_Board` 把问过 DMT 的每一种组合记下来（相邻格的规划对象编成一个数作键），同样的邻居组合再出现时不再调用 DMT。搜索中反复出现的组合很多：穷举 3 个区域的 3.3 万种布局只需约 2900 次 DMT 调用，局部搜索的大部分尝试一次 DMT 都不用调。
- **合法性**：区域的 `CanPlacePin` 只与本格和附近的市中心有关（`CanPlaceDistrictCheckHelper`），每个（区域，格）问一次；奇观可能要求相邻某区域，按邻居组合记忆。
- 每个方案最后再做一次全量评估，与增量值比对（结果里的 `Stats.Mismatch`）。

地块部分只涉及被改动的格子，按产出排序走到第 P 格为止，开销可以忽略。

依据：DMT 的相邻加成只读本格和相邻 6 格的特征（`GetBonusYields` 遍历 `Map.GetAdjacentPlots`）。例外：市中心的 3 格间距检查（第 2 步市中心不动，不受影响）、"一条河只能有一座水坝"。**上线前必须验证**：`tests/test_incremental.lua` 在三种规则集下用固定序列生成的布局比对增量与全量评估（得分和合法性）；不一致的 subject 类型改为全量评估。

### 4.7 质量保证（替代"最优"）

| 保证 | 做法 | 测试 |
|---|---|---|
| 确定性 | 只遍历排序数组，预算按计数，确定的决胜规则；结果与分帧方式、机器快慢无关 | 同一局面求解两次结果深比较相等；分帧额度为 1 和 1000 时结果相等 |
| 不差于逐城单独规划 | 起点 1 就是逐城依次规划的结果，之后只接受严格提升 | 断言最佳方案提升 ≥ 起点 1 的提升 |
| 小规模精确 | 合法组合数不超过本档位的穷举上限（300 / 1200 / 6000）时直接穷举 | 2 城各 1–2 个区域时与暴力枚举的最优相等 |
| 质量透明 | 显示距估计上界的差距和收敛情况（见 7.4） | 基准测试统计上界被突破的次数（见第 9 节） |

- 第 2 步：每个区域、奇观打一个钉，名称是所属城市的编号（现有城市按建城顺序为 1、2、……，城址接在后面）。图标已经表明是什么区域，名称只用来区分城市；面板里的城市名前也带同样的编号。

## 6. 分帧计算（`SDP_Task`）

- **适用范围**：第 1 步、第 2 步的全部档位，以及单城的精细档。单城的快速、标准档仍同步计算。
- **调度**：`ContextPtr:SetUpdate` 每帧调用一次，执行一段计算后返回。协程可用时用协程写（需实测；游戏本体 UI 没用过协程，AMT 用之前先检查了是否存在）；不可用时写成显式状态机。
- **按计数切片**：游戏 Lua 的计时器只有秒级精度（见 AGENTS），不能在一帧内按毫秒计时。每帧执行一定数量的工作单位（DMT 评估次数、搜索节点数），数量根据上一帧的帧间隔（`UI.GetElapsedTime` 逐帧更新）自适应调整，目标约 20 毫秒/帧。
- **确定性**：算法结果只取决于输入、档位和继续优化次数，与切片边界无关。
- **局面快照**：开始时记录回合数、地图钉、计划参数；DMT overlay 的真实钉快照只加载一次。每帧执行前后安装、卸载 overlay，保证本 Lua 状态之外不受影响。
- **作废与取消**：检测到局面变化（回合结束、地图钉增删、新揭示格子）时作废结果并提示重新计算；面板上有取消按钮。
- **关闭面板不取消**（评审确认）：计算在后台继续。启动栏按钮的悬停提示显示进度；算完时播放提示音（沿用游戏已有音效）并在按钮上做标记；重新打开面板即可看到进度或结果。同一时间只运行一项计算，运行期间其他页签的求解按钮不可用。
- **渐进显示**：第 2 步每算完一套方案就加入列表，第 1 套出来即可预览，其余的继续算。
- **耗时统计**：记录每次求解完成的工作单位数和所用时间（按帧间隔累加；同步求解则取求解前后两帧的时间差），得到本机的处理速度，供 7.5 的预计耗时使用。

## 7. 档位、继续优化与质量指示

### 7.1 原则

1. **档位只改预算的数量，不按时间截止。**同一档位、同样的继续优化次数，在任何机器上结果完全相同，只是快慢不同。慢机器每帧自动少做一些，界面不卡，只是要多等。
2. **不做"按机器速度自动选档"，也不做"算到 X 秒就停"。**那样结果会取决于机器性能和当时的负载，破坏确定性（约束 6）。档位由玩家明确选择，预计耗时只用来提示。
3. **单城算法已重写**（阶段 8，第 15 节）：不再保证与旧版本逐位相同；在离线基准上各档都不差于旧版本，3 个区域以内仍与穷举最优相同。
4. 三个页签各自记住所选档位，默认"标准"。

### 7.3 继续优化

结果出来后显示"继续优化"按钮。每点一次，按固定顺序追加下一批计算，结果只会变好或不变：

| | 每次追加 | 已穷举时 |
|---|---|---|
| 单城 | 从精评布局中再取 5 个起点各做一次局部搜索，再做一批扰动重建（动作与轮数按当前档位）；四轮扰动都没有改进且起点用完后不可再继续 | 按钮不可用，显示"已穷举，结果最优" |
| 第 1 步 | 按粗评排名再纳入 20 个城址（M 增加 20），重新做组合搜索；新旧方案合并后重新筛选 N 套 | 同左 |
| 第 2 步 | 从起点序列中再取一批起点（数量等于当前档位的起点数），各做一遍 4.5 的 3–4；新旧方案合并后重新筛选 N 套 | 同左 |

结果由（输入，档位，继续优化次数）唯一决定，可以复现。求解统计里显示"档位 + 继续优化 n 次"。

### 7.4 质量指示

汇总行显示以下指示，悬停显示数值细节：

| 指示 | 定义 | 显示 |
|---|---|---|
| 穷举 | 本次走了穷举 | "已穷举，结果最优" |
| 距估计上界 | 上界 U = 各对象最佳单项提升之和 + 全部正的对象间互惠（与现有分支定界同一口径）；差距 = (U − 提升) / U，只在 U > 0 时显示。一律用**提升**而不用总分，避免固定邻居的基线把比例虚抬 | "距估计上界 ≤ X%" |
| 收敛 | 最近一批起点（单城为最近一批短名单布局）都没有找到更好的方案 | "已收敛" 或 "可能还有提升，可继续优化" |
| 预算用尽 | 任一阶段的计数预算用完（现有 `Stats.Truncated`） | "搜索预算用尽" |

**为什么叫"估计上界"**：线性模型按比例折算 `TilesRequired`，一般会高估，所以 U 通常不低于真实最优。但有反例：两个新区域同时挨着同一个已有区域时，单独放各给它 +0（取整），一起放才 +1，这部分不在 U 里。U 因此不是严格的上界。基准测试统计它被突破的频率；如果经常被突破，就给 U 加上修正量。第 1 步的上界只覆盖精评过的 M 个城址，界面注明"仅限精评城址"。

### 7.5 预计耗时

- 档位选择旁显示"预计约 X 秒"：X = 该档位的预计工作量 ÷ 本机处理速度。
- 预计工作量按问题规模（候选格数、对象数、城数）和档位预算估算。
- 本机速度来自本局之前的求解统计（第 6 节）；本局第一次求解前用 Mac 实测的默认速度。
- 预计耗时只用来提示，不影响任何计算。

## 8. 耗时估算（推算，需实测）

依据（Mac 实测，见自测报告）：DMT 联合评估（2 个区域加固定邻居）约 0.5 毫秒，搜索节点约 2 微秒；单城 4 个区域 0.08–0.19 秒，8 个区域 0.18–0.80 秒。单个区域的单项评估未单独测过，按 0.25–0.5 毫秒估计。分帧后实际等待时间按纯计算时间的约 1.8 倍估计。

标准档的分解（其他档位的总耗时见 7.2）：

| 环节 | 规模 | 纯计算 |
|---|---|---|
| 第 1 步：候选与粗评（只读地块数据） | 数百至上千个候选 | < 0.5 s |
| 第 1 步：共享单项表 | 约 600 格 × 8 种区域 ≈ 4800 次 | 1–2.5 s |
| 第 1 步：市中心修正 | 40 个城址 × 6 格 × 8 种 ≈ 1900 次 | 0.5–1 s |

| 第 1 步：组合搜索与多套方案 | 40 选 K，分支定界，50 万节点 | 约 1 s |
| **第 1 步合计** | | **5–7 s，实际等待约 9–12 s** |

| 第 2 步：每个起点的联合精修 | 4 城 × 6 区域 + 3 个奇观；起点 + 3 轮块坐标上升（每轮约 1 s）+ 局部搜索（约 1 s） | 3–5 s |
| **第 2 步合计（5 个起点）** | | **16–27 s，实际等待约 30–50 s；第 1 套约 10–15 s 出现** |

## 9. 基准测试

目的：测出各档位实际能达到最优的多少，用来定档位参数、默认档和对外宣称的数字。没有测过的比例不写进使用文档。

### 9.1 场景

固定种子（20261019 及另外 2 个种子）× 三种规则集，每个组合取：

| 类别 | 规模 |
|---|---|
| 单城 | 3、4、6 个区域；含与不含锁定钉 |
| 多城（小） | 2 城各 1–2 个区域（可穷举） |
| 多城（大） | 3–4 城各 4–6 个区域，加 2–3 个奇观 |
| 城址 | K = 2、3 |

场景由 `tests/fixtures/` 脚本搭建（建城、放市中心钉），与现有测试共用固定对局。

### 9.2 参照解

| 规模 | 参照 | 说明 |
|---|---|---|
| 单城 3 个区域、多城（小） | **真最优**：DMT 穷举全部合法组合 | 单城 3 区域约 2.7 万种组合，约 15 秒 |
| 单城 4–6 个区域、多城（大） | **已知最好解**：精细档 + 继续优化 20 次的最好结果，配合估计上界给出区间 | 不是真最优；报告时注明 |
| 城址 | 估计分排名第一的组合，经第 2 步精细档精确求解后，是否仍在全部组合的前 3 名 | 衡量区域分估计的误差；食物等系数的模型误差无法用基准测试衡量 |

### 9.3 指标与达标线

- **质量比例** = 本档位的提升 ÷ 参照解的提升（都用提升，不用总分）。报告每档的平均值、最差值。
- **耗时**：每档的墙钟时间、DMT 评估次数、搜索节点数。
- **上界**：估计上界被参照解突破的次数。
- **继续优化曲线**：标准档继续优化 0、1、3、10 次的质量比例，用来判断"继续优化"是否值得。
- **达标线**（暂定）：标准档平均 ≥ 95%、最差 ≥ 90%；精细档平均 ≥ 98%。不达标时先改算法或参数，再定发布的默认值。

### 9.4 运行与记录

- 游戏内基准放在 `tests/bench/`（不以 `test_` 开头，不进常规测试），用 `@timeout` 放宽时限，单独运行。`cost_dmt.lua`、`cost_search.lua` 测 DMT 调用、布局评估和搜索节点在游戏里的实际单价，用来校准离线估算和 `SDP_Tiers` 的工作单位。
- 结果写进 `docs/self-test-report.md`（每档质量与耗时表），并据此更新 7.2 的参数和"预期质量"一行。

### 9.5 离线基准（阶段 8 起）

算法迭代主要在离线完成，不用开游戏：`node tools/offline_tests.mjs -v tests/offline/bench_single.lua`（用法见 `tools/README.md`）。

- 场景：6 个固定种子的随机地图（15×13，首都居中，偶数种子带一个已建区域）× 3、4、6、8 个区域 × 是否计入地块部分。
- 参照解：3 个区域用穷举最优；更多区域用"精细档 + 继续优化 3 次"和三次模拟退火（固定伪随机序列，只在测试里用）中最好的，档位结果更好时自动更新参照。
- 成本：假 DMT 统计调用次数，按游戏内单价折算：`SDP_Tiers` 工作单位（DMT 调用 + 0.25 × 布局评估 + 节点 / 20），一次算完时每单位约 0.05 毫秒（2026-10-20 游戏内实测，第 17 节）。
- 局限：假 DMT 只有主要的相邻规则（山脉、树林、雨林、河流、区域互邻、奇观、水渠—工业区、娱乐—剧院、政府广场），没有改良设施、海港、特色区域的特殊规则和修正器。离线质量只说明搜索本身有效，游戏内仍要按 9.1–9.3 复核。

### 15.2 算法迭代（离线基准，第 9.5 节）

| 版本（标准档，平均 / 最差，占参照解） | 6 个区域 | 8 个区域 | 预计耗时（8 个区域） |
|---|---|---|---|
| 旧算法（MVP） | 87.5% / 67% | 89.6% / 83% | 约 1.2 秒 |
| + 增量记忆评估、模型按单项分从高到低搜索、更紧的上界、"不取整"模型（邻近市中心和已有区域的半个加成计入）、整组平移 | 98.8% / 93% | 95.5% / 89% | 约 1.2 秒 |
| 模型深度优先搜索换成集束搜索（宽 400） | 100% / 100% | 97.4% / 94% | 约 0.3 秒 |
| + 4 轮扰动重建 | 100% / 100% | 98.3% / 94% | 约 0.56 秒 |
| + 集束先放与其他区域互惠最多的（现行） | 100% / 100% | 99.2% / 96% | 约 0.56 秒 |

计入地块部分时结果相近（8 个区域标准档 99.1%）。快速档 8 个区域 98–99%、约 0.13 秒；精细档全部 100%、约 2.2 秒（分帧）。

几个发现：
- 旧算法的主要问题是模型深度优先搜索被节点预算截断时，只看过编号小（地图左上）的格子；以及单个区域移动无法把整片区域搬到更好的位置。
- 模型本身相当准：漏掉的好方案，模型分往往比找到的更高，问题在搜索没走到。所以把预算从模型搜索节点挪到集束搜索，比加深搜索有效得多。
- 首次改进（first improvement）、两两成对移动在这些场景里没有收益，未启用。

| `SDP_SiteSolver` | 第 1 步的组合搜索（3.5）：间距、接力连通、组合修正（重叠格归失去它损失最大的城；奢侈、战略的新种类只算一次；两城区域落在同一格扣较小的一方的单项分），分支定界，多套差异方案。 |
| `SDP_Preview` | 地图预览：`Hex_Coloring_Placement` 图层按城着色（需要时打开，清除时关回），`WorldAnchor` 图标。关面板、切页签、换方案、进入游戏的放置模式（`InterfaceModeChanged`）时清除。 |
| `SDP_PageSites`、`SDP_PageMulti` | 面板的"选城址""多城"两个页签（`SDP_Panel` 改为三个页签，单城页不变）。 |

多套方案（第 2 步）：候选为全局最好方案和每个起点的结果，按价值排序，与前面每一套至少有 max(2, 槽位数 20%) 个对象位置不同才保留。

### 16.2 与设计的出入

- **"需相邻区域"的奇观没有加"同城"限制**：合法性完全按 DMT（相邻有该区域即可，不论属于哪座城）。设计里"保守地要求同城"要等风险 12 实测游戏规则后再定；若游戏要求同城，在 `SDP_Search.Evaluate` 加一道筛选即可。
- **城址评分不含有帝国上限的区域**（政府广场等）：每个城址都算一份会重复计算。
- **城址的区域分用完整的单城搜索**（快速档参数）而不是只用线性模型：共享 `SDP_Board` 的记忆让它足够便宜，估计更准。
- **多城页签暂不能逐城修改计划**：所有城市共用一份计划，现有城市自动跳过已建和已有钉的区域。接口已支持 `Plans`（按城覆盖），界面以后再加。
- **多城页签没有"允许砍伐"开关**：始终允许（与单城默认一致）。
- **渐进显示**：计算中只显示进度百分比，全部算完才列出方案（设计 6 的"第 1 套出来即可预览"未做）。

### 16.3 离线测试

- `spec_multi`：参与城市与开关、上限；新城不能用现有城市的格子；一格一个对象、帝国上限、不差于逐城依次规划；现有城市跳过已建区域；确定性；小规模与暴力枚举一致；共享地块只归一城；多套方案互不相同；奇观（已建、已有钉、缺少所需区域、需相邻区域时摆在规划的区域旁边）。
- `spec_sites`：候选排除规则、`CITY_MIN_RANGE` 读游戏数据、水源/奢侈/战略的计分、组合的间距与接力、确定性、分支定界与逐对枚举一致、修正不会让组合超过各城址分之和。
- `spec_panel`：用 `tests/offline/ui.lua` 的控件替身加载整个面板，三个页签依次求解（同步与分帧）、预览、打钉与撤销、关闭面板后后台算完的提示。只能证明脚本逻辑无误，布局与真实点击仍要在游戏里看。

### 16.4 多城离线基准

`tests/offline/bench_multi.lua`：4 个种子的随机地图（21×15），首都 + 3 个市中心钉，每城 5 个区域 + 政府广场，有/无地块部分。参照解为精细档 + 继续优化 1 次 + 模拟退火中最好的。

| 档位（平均 / 最差，占参照解） | 只算相邻 | 计入地块部分 | 预计耗时（推算） |
|---|---|---|---|
| 逐城依次规划（起点 1 本身） | 92.7% | 94.7% | — |
| 快速 | 94.1% / 87% | 97.4% / 93% | 约 1.3 秒 |
| 标准 | 98.2% / 95% | 98.4% / 96% | 约 6 秒 |

迭代中的发现：
- 只加起点（城市顺序）几乎没有收益；扰动重建在标准档受布局尝试上限限制，40 轮以上无差别。
- 一个场景里最优方案把三座新城的区域并成一大片（跨城相邻互给加成）。逐城规划时束宽越大，第一座城越"自顾自"地选最好的位置，反而走不到这种形状；快速档的窄束偶然走到了。于是起点改为固定的组合：逐城（全宽）、联合（所有城的区域一次束搜索）、逐城（三分之一束宽）、逆序（全宽、三分之一束宽）……标准档计入地块时从 97.3% 提到 98.4%。
- 预计耗时按单城的单价推算；多城一次布局评估更重（棋盘大、每城一个地块模型），在离线虚拟机里与推算之比约为单城的两倍，游戏内标准档可能在 8–10 秒，仍远低于设计的 30–50 秒，待实测。精细档的离线基准未跑完，参数沿用设计。

## 17. 游戏内验证与校准（2026-10-20）

三种规则集各开一局（固定种子，`game.py newgame --capital --reveal`），跑全部游戏内测试，再测单价、各档耗时、分帧与关闭面板的行为，截图核对三个页签和预览。结果明细见 [self-test-report.md](self-test-report.md)。

### 17.1 风险的结论（第 10 节）

| # | 风险 | 结论 |
|---|---|---|
| 1 | 协程是否可用 | 可用：`SDP_Panel` 状态里协程可创建、恢复、跨帧挂起；分帧结果与一次算完相同 |
| 2 | 面板关闭后 `SetUpdate` 是否继续 | **不继续**：弹窗出队会隐藏上下文，隐藏的上下文收不到 `SetUpdate`，计算停在原处。改法比第 10 节的预案简单：计算中关闭面板时只隐藏窗口控件、保持上下文显示，算完再隐藏（`KeepRunningHidden`，AGENTS 坑 23）。实测关闭面板后精细档照常算完、启动栏按钮出现标记 |

### 17.2 游戏内发现并修改的问题

- **城址精评取不到能连通的城址**：地图揭示较多时，粗评前 M 名可能都离本方城市超过接力距离 D，组合全部不连通，结果为"无城址"。改为按粗评顺序只取"能连回"的城址精评：离本方城市或城址钉 D 格内，或离已精评的城址 D 格内（最多 K − 1 次接力）。
- **后台结果把预览画到地图上**：面板关闭时算完会渲染结果并显示预览。现在面板关闭时算完即清除预览，打开页签再显示。
- **方案行和选中页签的文字看不清**：按 `TradeOverview` 的做法，选中、未选中各用一套文字。
- **多城档位不单调**：离线基准里快速档在一张图上比标准、精细档好（47 对 45），原因是搜索路径不同（交换动作、穷举上限），不只是束宽。现在每档先跑轻一档的起点（`SDP_Tiers.Multi.*.Prelude`，`Session:RunPrelude`），起点结果只取决于输入和参数，所以不会低于轻一档的起点。共享的记忆评估让这部分几乎不增加 DMT 调用。前置有自己的预算：跑完后重新设定预算，本档的起点和扰动仍有全部预算（不这样做时精细档在一张图上反而少 1 分）。精细档前置标准档后，自身起点从 6 个减到 4 个，质量不变（离线 98.2% / 100%），耗时少约 15%；只前置快速档的方案更省时，但计入地块时会低于标准档，未采用。

### 17.3 耗时校准

- 单价：一次 DMT 调用约 0.042 毫秒，一次布局评估约 0.01 毫秒，一个模型节点 0.002–0.005 毫秒。`SDP_Tiers.UNITS_PER_TRY` 改为 0.25、`NODES_PER_UNIT` 改为 20，一个单位约等于一次 DMT 调用；一次算完时每秒约 2 万单位，分帧时单城每秒 7400–9900 单位、多城约 15000 单位（`SDP_Task.DEFAULT_SPEED` = 11000 取中间，每次算完后按本机实测更新；`AT_ONCE_SPEED` = 20000）。
- 工作量：搜索通常远在预算用完之前收敛，原先"按预算估计"偏长 5–10 倍。现在按实测的典型工作量估计（`Work`）：单城 = 格数 × (a·k + b·k²)；多城 = 每槽每格的工作量 × 30 格 × 槽数 × (城数 / 2)^0.35，再加前置档位；城址 = 每个精评城址每个区域的工作量 + 组合数（约 C(M, K) 的四分之一）。预算上限仍按原来的计数，结果不受估计影响。
- 实测（一次算完，最终版本）：单城标准档 6 个区域 0.25 秒；多城 3 城 × 6 区域标准档 2.7 秒、精细档 4.3 秒；选城址 3 座精细档 3.5 秒。经面板分帧：多城标准档实际等待 4.4 秒、精细档 9.1 秒。都远低于第 8 节推算的 30–50 秒。预计工作量与实测相差在 10% 以内。

### 18.1 吸收这些功能后，怎样保持评估公平

本次离线对比的主指标是本 mod 的目标（DMT 显示的相邻加成）。吸收地块产出、覆盖范围、改良设施这类功能后，评估要同步改，原则是不让任何一方的目标函数单独当裁判：

1. **多把尺子，不只用本模组的目标**：每个方案同时报告：DMT 相邻加成（钉上显示的数）、**城市总产出**（相邻加成 + 市民耕作最好的若干块地，人口多少就算几块，各产出权重 1；本次已加入），以及每个新功能自己的指标（如工业区、娱乐中心覆盖的城市数，改良设施的产出）。这些指标由裁判独立计算，不复用任何规划器的代码。汇总时用帕累托支配（在所有指标上都不差、至少一项更好）计数，而不是只比一个加权和。
2. **交叉评分**：用对手自己的目标函数（AMT 的 `EvaluatePlan`、EP 的规则引擎）给所有方案打分。本模组的方案在对手自己的标准下也不差，结论才算稳；在它们的标准下输了，如实写出。
3. **每把尺子都给对手最好的设置**：对每个指标，对手用最贴近该指标的设置（计入地块时用它们自己的地块惩罚，只看科研时给它们科研焦点），必要时在它们的参数空间里搜索取最好的一组，作为对手的上限；同时保留面板默认设置的结果。本模组同样报告默认设置（面板默认计入地块损失）。
4. **多组权重**：在几组产出权重（均衡、科研、生产、信仰……）下各评估一次，结论不能只在“全部为 1”时成立。
5. **留出场景**：指标和场景在改算法之前定下来。开发新功能时只用一部分种子调参，最终对比用从没用过的新种子，避免把算法调成只适合这批场景。
6. **引擎校准**：在游戏里抽样，把方案真的建出来，读引擎实际给出的相邻产出，与 DMT 裁判对照，确认裁判本身没有偏差。
7. **统计与公开**：逐场景配对比较，报告胜 / 平 / 负和置信区间，不只报平均；裁判只看地图钉、不知道方案来自谁；公开原始结果和测试框架，任何人都能重跑。

已做到：第 1 条的城市总产出（`CmpRun.Judge` 的 `output = gain + worked`）、第 3 条的默认设置（AMT `DEFAULTW`、EP `DEFAULT`、本 mod `STANDARD_LAND`）、第 7 条的盲评与配对比较；裁判还区分漏放的区域“确实放不下”（`no_plot`）与“有位置却没放”（`placeable`：方案打成钉后城市仍有槽位，且 3 环内有一格 DMT 可放、不违反其他规则）。2026-10-20 的结果：单城 72 个场景本模组标准档 97% 拿到最高加成（AMT 54%、EP 26%），漏放中“有位置却没放”本模组 0、AMT 52、EP 75；城市总产出本模组（计入地块）83% 最高（AMT 58%、EP 35%）。交叉评分、多组权重、留出场景、引擎校准留到吸收功能的阶段。
