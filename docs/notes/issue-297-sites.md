# #297 选城址怎么选：步骤、共用地格、住房（2026-11-05）

合作者在 [#297](https://github.com/SmallSpider0/civ6-smart-district-planner/issues/297) 问选城址的具体步骤：几个城址是依次选还是按组合选、与已有城市共用的格怎么算、住房为什么把粮仓和港口的建筑也算进去。本篇按 `main`（v1.7.3 之后，358672a）的代码回答，并记下为这几问做的离线实验。

## 1. 实际步骤（`SDP_SiteSolver`，设计文档 3.2–3.5）

1. **候选**（`SDP_Sites.Candidates`、`SiteExclusion`）：全部已揭示的格，去掉水域、山脉、不可通行、不能建城的地貌（`Features.Settlement = false`）、他国领土、离任何城市（本方、他国、城邦）或本方市中心钉不超过 `CITY_MIN_RANGE`（3）格的、离本方最近的城市或市中心钉超过“新城数量 × 最远距离”格的，以及三环内一半以上没揭示的。
2. **粗评**（`SDP_Sites.Coarse`，不调 DMT）：每个候选算地块、地貌、住房、奢侈、战略、魅力和缺格扣分，不算区域相邻加成。
3. **精评**（`Session:Refine`、`SDP_Sites.Fine`）：按粗评分从高到低，取能接回本方城市的前 M 个（档位快速 / 标准 / 精细 20 / 40 / 80；“能接回”：离本方城市或已精评的城址不超过最远距离），用 DMT 在每个城址周围摆计划的区域（必建的加从候选里挑“数量 − 必建”个），重算地块和住房。
4. **组合**（`Session:Combine`，分支定界）：从精评过的城址里选“新城数量”个的所有组合，要求彼此距离大于 3、每个城址沿不超过最远距离的连线接回本方城市（别的新城址可以接力）；组合的值 = 各城址分之和，再做组合级修正（`Session:Value`）：两个城址都够得着的格只归一个，同一种新资源只算一次新种类，两个城址的区域抢同一格时扣掉较小的那份。节点上限按档位 10 万 / 50 万 / 200 万。
5. **多套方案**（`Session:Distinct`）：留前 N 套“足够不同”的组合（至少一个城址与前面每一套的所有城址都隔 2 格以上）。

所以三个城址是**按组合**一起选的，不是依次选；例外是“密铺”，它按贪心一个个往外排（设计 3.5“密铺”）。粗评不含区域分，相邻加成很高但地块一般的格可能在第 3 步之前就被筛掉，这是已知的取舍（设计 3.2“两级筛选”）。

## 2. 共用地格

三种格分开算：

| 格 | 怎么算 | 代码 |
|---|---|---|
| 已经属于本方某座城的格 | 新城完全不算：不耕作、不放区域、上面的资源不算 | `SDP_City.ScanSite` → `ExclusionReason` 的 `OTHER_CITY`（`SDP_Land.WORKABLE_EXCLUSIONS` 不含它） |
| 在已有城市三环内、还没归属的格 | 新城全额算，不和已有城市分 | 同上：无主格不查离哪座已有城市近 |
| 两个新城址都够得着的格 | 只归一个城址：没有它损失更大的那个，同样时给离市中心近的，再同样给格子编号小的 | `Session:Value` 的 `owner` |
| 地图上已有的市中心钉的一环 | 新城不算（建城时归那座城） | `SiteRings`，`SITE_RING` |

地块分只算最好的 P 格（P = 3 × 特色区域数 − 2，默认 3 个区域时 7 格），三环约 36 格，丢掉几格共用的格多半不影响前 7 格。所以共用地格只在很弱的程度上把新城推离已有城市；反过来也没有任何一项奖励“靠近”，新城离已有城市多远主要由“最远距离”（默认 5，即离已有城市 4 或 5 格）和接力规则限定。

## 3. 住房现在怎么算

`SDP_Sites.WaterPart`：

```
住房分 = 住房权重 × (10 / 3) × [HV(城址住房) − HV(无水城址住房)]
城址住房     = 水源住房 + 已研究的市中心建筑（粮仓） + 计划里沿海区域（港口）的已研究建筑
无水城址住房 = 2 + 已研究的市中心建筑
```

- 水源住房：河边、湖边、挨着绿洲 5，沿海 3，都不是 2（`GlobalParameters.CITY_POPULATION_RIVER_LAKE / COAST / NO_WATER`）。
- 建筑（`Buildings.Housing`，#188 起只算已研究的）：粮仓 +2（制陶术），灯塔 +1（天文导航）、风云变幻里沿海城市的灯塔再 +2（`LIGHTHOUSE_COASTAL_CITY_HOUSING`），码头 +1（电力）。港口只在城址周围的区域摆法里选中了港口时才加。
- HV（#91 方案 B，`SDP_Land.HousingValue`）：拐点 K = max(目标人口 + 1, 当前人口 + 2)，目标人口 = 3 × 特色区域数 − 2；拐点以内每点住房算 1，超过的每点是前一点的一半。默认 3 个区域：目标 7、拐点 8。
- “10 / 3”：比无水城址多 3 点住房记 10 分（#88，`SDP_Sites.REFERENCE.Housing`）。

例（风云变幻，默认 3 个区域、住房权重 1，已研究制陶术和天文导航）：

| 城址 | 城址住房 | 比无水多 | 住房分 |
|---|---|---|---|
| 无水、不沿海 | 2 + 2 = 4 | 0 | 0 |
| 只沿海，不建港口 | 3 + 2 = 5 | 1 | 3.3 |
| 河边，不沿海 | 5 + 2 = 7 | 3 | 10 |
| 只沿海，选了港口 | 3 + 2 + 1 + 2 = 8 | 4 | 13.3 |
| 河边且沿海，选了港口 | 5 + 2 + 3 = 10 | 4.75（超拐点的 2 点按 0.5、0.25） | 15.8 |

- 粮仓两边都加，在拐点以内正好抵消，**不影响选哪个城址**；只在城址住房超过拐点时（已经有港口建筑时）让差值略小。
- 港口的建筑才是让结果和直觉不符的那部分：只沿海、选了港口的城址住房分比河边城址高，而灯塔要先建港口（占一个区域名额）、再花生产力建灯塔，淡水的 +3 是建城就有。

游戏规则（`GlobalParameters`）：

| 参数 | 值 | 含义 |
|---|---|---|
| `CITY_POPULATION_RIVER_LAKE` | 5 | 河边、湖边或挨着绿洲、火山口湖的城市（`Features.AddsFreshWater`） |
| `CITY_POPULATION_COAST` | 3 | 沿海 |
| `CITY_POPULATION_NO_WATER` | 2 | 都不是 |
| `CITY_POPULATION_AQUEDUCT_MIN` | 6 | 建了引水渠的无淡水城市，水源住房提到 6 |
| `CITY_POPULATION_AQUEDUCT_BOOST` | 2 | 有淡水的城市建引水渠 +2（到 7） |
| `CITY_HOUSING_LEFT_50PCT_GROWTH` / `25PCT` / `ZERO` | 1 / 0 / −4 | 住房比人口多 1 时增长减半，相等时剩四分之一，人口超出住房 4 时停止 |

引水渠（工程学）建好以后，淡水城市比无淡水城市只多 1 点；城址分现在不算引水渠（“只显示”，设计 3.3），所以淡水的 +3 是按“一直多 3 点”算的。

## 4. 离线实验：住房只算水源（2026-11-05）

`tests/compare/cmp_sdp.lua` 加了两个只在对比里用的变体：`_HWATER`（住房分不计任何建筑：市中心建筑和沿海区域的建筑都去掉，水源照旧）、`_HOUSE<n>`（均衡预设、住房权重 n）。60 个选城址场景（12 个 `C`、48 个 `ZS`，每个选 2 个城址），面板默认的区域格（每城 3 个，`_GRID`）、距离成本 0.5（`_DIST050`），标准档：

```
python3 -I tools/remote.py run i297-house --slots 6 -- node tools/compare.mjs -s '^(C|ZS)[0-9]' -p sdp --add sdp:STANDARD_GRID_DIST050,sdp:STANDARD_HWATER_GRID_DIST050,sdp:STANDARD_HWATER_HOUSE2_GRID_DIST050 --only sdp:STANDARD_GRID_DIST050,sdp:STANDARD_HWATER_GRID_DIST050,sdp:STANDARD_HWATER_HOUSE2_GRID_DIST050 -j 6 --out logs/remote/i297-house.jsonl
```

第二台机器 6 个格子约 33 分钟。城址的水源和住房按 `stats.sdpSiteInfo`（这次加的，`x,y:水源:住房:离本方最近距离`）统计；其余是裁判的指标。结果文件只在 `logs/`，不入库。

| 120 个城址 | 现在 | 只算水源 | 只算水源 + 住房权重 2 |
|---|---|---|---|
| 河边、湖边 | 56 | 74 | 95 |
| 只沿海（无淡水） | 41 | 7 | 8 |
| 没水 | 23 | 39 | 17 |
| 挨着海（`IsCoastalLand`，含河边又挨海的） | 49 | 14 | 18 |
| 住房分里算了港口建筑的 | 61（只沿海 41，淡水又挨海 18，其他 2） | — | — |
| 选出的城址变了的场景（共 60） | — | 36 | 41 |
| 违规 | 0 | 0 | 0 |
| 裁判城址分（每城最好 8 块地 + 区域潜力） | 3875 | 4035（+4.1%） | 3950（+1.9%） |
| 其中区域潜力 | 657 | 733（+12%） | 758 |
| 其中地块 | 3218 | 3302 | 3192 |
| 新奢侈资源种类 | 65 | 68 | 56 |
| 新战略资源种类 | 74 | 78 | 63 |
| 与本方城市、彼此重叠的格 | 857 | 868 | 889 |

- 现在一半的城址（61 / 120）住房分里算了港口建筑，只沿海的城址主要靠它胜出：去掉以后只沿海的从 41 个降到 7 个，河湖边的从 56 升到 74。
- 只算水源时裁判的每一项都不变差：区域潜力 +12%，地块 +2.6%，新资源种类也略多。
- 再把住房权重调到 2，河湖边到 95 个，但新奢侈、新战略种类各少十多种，地块变少，裁判分低于只算水源。看重淡水的玩家可以用“成长优先”预设（住房 2、食物 2）。
- 例：`ZS22`（高卢，高地，文艺复兴）原来的城址 (17,15) 只沿海、摆了港口，住房算 8；只算水源后挪 2 格到河边的 (17,13)。`ZS18`（马里，沙漠，古典）(19,14) 挪 1 格到河边的 (18,15)。`ZS03`（朝鲜，全部科技）两个只沿海的城址都换成了另一处的两个河边城址，裁判分 64 → 73。

## 5. 结论与建议（写在 #297）

- 客观事实（已核对代码和规则库）：按组合选；粮仓两边抵消；港口建筑当作建城就有的住房算；共用地格只轻微地影响远近。
- 建议方案 A：住房分只算水源；建筑照旧只在悬停里列出“建好后另加”。粮仓去掉不改变结果，只是算法好懂。代码：`SDP_Sites.Context` 不再把建筑计入 `Housing.Center`，`WaterPart` 不加沿海区域建筑的住房（悬停的列表照旧算出）；城址钉的住房（`SDP_Land.ScanHousing`，多城、单城页用）不在本 Issue 内。
- 待合作者定：方案 A；淡水要不要更值钱（建议不改，用“成长优先”）；请他给一个不符合直觉的例子。

### 6.2 灯塔给海面格的食物

对比变体 `_HLIGHT`：只算水源，再在玩家有天文导航时给每块近海格（`TERRAIN_COAST`，含湖）的地块值 +1 食物（`LIGHTHOUSE_COAST_FOOD`），相当于每个城址都建了港口和灯塔。60 个场景的结果与 `_HWATER` 完全相同：没有改良的近海格地块值 1.25（1 食物 + 1 金币 × 1/4），加 1 也只有 2.25，而草原、平原改良后 3 以上、丘陵 7（`ZS14` 全部科技），进不了最好的 7 格。所以靠地块分抬不起海边城址。

### 6.4 第二轮建议（写在 #297）

推荐 B：照顾合作者说的海边城市（只沿海 21 个、挨着海 35 个，A 是 7、14），去掉“只沿海、摆了港口比河边还高”；裁判的地块、区域潜力都比现在好，只是不如 A。问合作者选 A 还是 B。实现时 B 只需在 `WaterPart` 和 `Context` 里把建筑住房乘 0.5（一个常量），悬停的“建好后另加”照旧写建筑的全额。
