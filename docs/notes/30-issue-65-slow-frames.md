# 30. 游戏的帧慢时分帧计算不再停住（2026-10-25，#65）

> 原为 [multicity-design.md](../multicity-design.md) 第 30 节，编号不变，引用“第 30 节”仍指这里。

**现象**：#63 的规模测量里，2 座城快速档一次算完 0.34 秒，分帧算用了 17.5 秒，之后预计耗时显示几千秒。

**测量**（`tests/bench/probe_frames.py`，新开局，一次算完约 3.1 万单位/秒）：在面板的 Lua 状态里逐帧计时，先空跑，再按面板的做法每帧推进一个合成任务（每个单位是固定的一段计算）。

| 情况 | 帧长 | 任务吞吐（单位/秒） |
|---|---|---|
| 机器空闲，游戏在前台 / 在后台（另一个桌面空间）/ 隐藏 | 29–31 毫秒 | 4.6 万 / 4.1 万 / 3.9 万 |
| 另有 5 个离线对比进程 | 31–33 毫秒 | 2.0–2.3 万 |
| 游戏每帧额外慢 60 毫秒（`--slow-ms 60`），修正前 | 78 毫秒 | 52，每帧 4 个单位 |
| 同上，修正后 | 59 毫秒 | 3300，每帧 194 个单位 |

结果文件：`tests/bench/results/probe_frames.json`（空闲）、`probe_frames-load.json`（有负载）、`probe_frames-slow-old.json`、`probe_frames-slow.json`。

**原因**：在这台 Mac 上，窗口在前台、后台还是隐藏，帧长都一样，不是窗口状态的问题。当时机器上同时跑着十几个离线对比进程（负载 13–18），游戏自己的帧一直长于目标。原来的配额只看帧长：帧长超过目标 1.25 倍就乘 0.75，于是每帧降一次，几十帧后停在最小值 4，再也回不来。这次运行算出的速度（修正前的测量里是 63 单位/秒）又被记成本机速度，后面的预计耗时就成了几千秒。

**修正**（`SDP_Task`）：
- 按这一帧做的单位数估计自己占了多少时间（按一次算完的速度 2 万单位/秒折算）。帧长了，只有自己那份超过目标的一半才减量；不到四分之一就加量。游戏自己的帧就慢时，每帧的工作量停在目标的四分之一到一半之间，每帧最多多出约半个目标帧（约 17 毫秒）。
- 平均帧长超过目标 3 倍的运行不用来校准速度。

结果不受影响：每帧做多少只改变在哪里暂停，算的还是同一段代码（约束 6）。离线测试 `tests/offline/spec_task.lua` 加了两项：游戏的帧慢时每帧工作量不降到最小、不改变记下的速度；自己的工作让帧变长时照样减量。两项都在旧代码上失败。

Windows 上没有测。窗口状态的结论只对这台 Mac 成立。
