# #329 平时每周跑一个规则集的整套游戏内测试

2026-11-07。维护者给 #329 打了 `auto`，照 Issue 的建议做：每周一个夜里跑一个规则集的整套游戏内测试，三种规则集轮流；有失败按 bug 处理。

## 起因

#327 的评审：#314、#319、#320 都要到发版测试才露出来。平时的 PR 只跑和改动相关的测试文件，三种规则集的整套游戏内测试只在发版前跑；#319、#320 和那一版的改动无关，是游戏升级到典藏版让测试地图变了。

## 做法

让工具记着，不靠人每周排（maintaining.md §10“能让工具强制的不写成规则”）：

- `sdplock.py queue weekly` 往夜间队列加一项“每周整套游戏内测试（某规则集）”，带一个“从哪一夜起”的日期。命令是：在仓库主检出上 `git pull --ff-only origin main`、`deploy.py`、`run_tests.py --rulesets <规则集>`。
- 跑的人照常 `queue done ID`（通过）或 `--failed`，工具这时自动排下一周的一项，规则集按原版 → 迭起兴衰 → 风云变幻轮流。失败了也排，否则一次失败就断了。`--last` 关掉且不再排。
- 没到那一夜的项不出现在 `queue list` 和 `status` 的排着的项里（列在 `later:` 下），值守的 `pr_wait.py --list` 也不为它报“夜间队列到点”。所以它可以提前一周排着，不会让别的夜里多跑一次。
- 同时只能有一项排着，重复 `queue weekly` 被拒绝。

## 定下的细节和理由

| 细节 | 定了什么 | 理由 |
|---|---|---|
| 频率 | 每周一次 | Issue 的建议 |
| 哪一夜 | 本机配置 `weekly_night`（这台 Mac 设成 `"sat"`，即周五夜里到周六早上的那个夜间窗口）；仓库里只说“每周一个夜里” | 和机器有关的值不进仓库；周末本来就可以开游戏，失败了第二天白天就能修，不挤平日夜里发版测试和 PR 的夜间测试 |
| 从哪个规则集开始 | 风云变幻，之后原版、迭起兴衰 | 它的规则最多（运河、防洪堤只有它有），#314 就出在风云变幻；之后的顺序和 `run_tests.py --rulesets all` 相同 |
| 跑哪份代码 | 主检出上最新的 `main` | 要找的是 `main` 上已经有的问题，不是哪个分支的；`main` 的 modinfo 版本号不低于各分支并入的版本，部署不会被拒（坑 45），发版准备分支抬了版本号还没合并时例外，那时 `deploy.py` 以退出码 5 停下，跑的人照失败报告 |
| 晚跑了 | 照样只跑一次，下一项排在今天之后第一个设定的星期几 | 机器某夜没开、错过了，不补跑几次 |
| 失败谁处理 | 跑夜间队列的子 agent 每个 bug 开一个 Issue（`bug`、`auto`、下一个第三位版本的里程碑），`--failed --result` 写上 Issue 号，报给主会话；主会话按发版测试测出的 bug 当场修（sdp-release §1 第 2 步） | 和发版测试的 bug 同一套，不另立规则 |

## 测试

`tests/tools/test_sdplock.py` 的 `WeeklyTest`、`tests/tools/test_pr_wait.py` 的 `test_not_for_the_weekly_test_before_its_night`：在旧代码上失败（没有 `queue_weekly`），新代码通过。假时钟覆盖：排在设定的星期几、没到那一夜不列出、关掉后轮到下一个规则集、失败也续排、跨午夜的夜间窗口、错过一周、提前关掉、没配星期几时排一周后、`--last`、重复排被拒。

## 没验证的

真正的第一次周跑要等合并后排上、到那一夜由夜间队列跑；游戏内的部分这次没开游戏。
