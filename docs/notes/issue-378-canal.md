# #378 运河放到游戏不允许的格子上

状态：现行（第一步保守版 + 第二步游戏内标定），2026-11-25 按引擎真实规则收紧。

## 报告与复现

创意工坊评论（2026-11-23，英文）：玩家说模组总把运河放在不合法的格子上，只能手动放。本机没有游戏，未做游戏内复现；离线用例把问题钉住（`tests/offline/spec_canal.lua`，其中 4 条在旧代码上失败）。

## 原因（读代码所得）

运河"必须连通水域"只在 GameCore DLL 里，DMT 的 `CanPlacePin` 不查（[pitfalls](../pitfalls.md) 坑 27）。本模组原有的一层复核是 `SDP_City.EngineRefused`：向引擎要该区域的可建格（`CityManager.GetOperationTargets`，游戏放置透镜用的就是它），列表外的本城格判不可放。两处缺口正好覆盖规划场景：

1. `SDP_Overlay.EngineRefuses` 在 `plot:GetOwner() ~= playerID` 时直接放行——城 2/3 环还没买下的格、选城址页的全部格从不复核。
2. `SDP_City.EngineRefused` 在引擎给出空表时返回 nil，交回 DMT。运河 `PrereqTech = TECH_STEAM_POWER`，规划期通常未解锁，引擎必然空表。

规则库（本机 `Cache/DebugGameplay.sqlite`，只读）确认：`Districts_XP2.Canal = 1`；`District_ValidTerrains` 给运河列出草地、平原、沙漠、冻土、雪地（无丘陵）；`Districts` 表 40 列里没有任何距离或水域字段。所以"连通水域"只能自己判，且只能用数据驱动的方式认出运河。

## 做法

| 位置 | 内容 |
|---|---|
| `SDP_Rules.IsCanal` | `Districts_XP2.Canal`（与 `AutoKind` 用 `PreventsFloods` 认堤坝同理，不写类型名） |
| `SDP_Rules.ValidTerrains` | `District_ValidTerrains`，按 `GameInfo` 缓存；没有行就返回 nil |
| `SDP_City.CanalSides` | 六邻里每个方向的"边"：水域（海岸/大洋/湖）、城中心、已建运河。河不算 |
| `SDP_City.CanalSidesJoin` | 两条边相隔 2（60° 弯，中间那条边是陆地）或相隔 3（直穿，其余四条边都是陆地）→ 成立 |
| `SDP_City.CanalCannotLink` | 运河 + 地形在表里 + 陆地 + 没有成立的两条边 → true |
| `SDP_Overlay.EngineRefuses` | 已拥有格：引擎有列表就以引擎为准；引擎没答案或格未拥有：非运河放行，运河走本地判定，规划中的城中心钉按方向加入边（每次评估现算，缓存里只有地图自己的边） |

**不做**：规划中的**运河钉**不算边。`SDP_Board` 的合法性记忆假设"只取决于本格与固定地图"，纳入要改记忆键，属另一次改动。

## 第二步：游戏内标定（2026-11-25，`tests/bench/probe_canal.lua`）

4 局 6 座城（海岸河口、地峡、内陆河网、湖区），逐格对比引擎 `CityManager.GetOperationTargets` 与本地判定：

| 问题 | 结论 |
|---|---|
| 两条边相隔多少才算 | 2（60° 弯，中间那条边是陆地）或 3（直穿，其余四条边都是陆地）；相隔 1 的格子引擎全部拒绝 |
| 两侧相对临水（无城中心） | 成立，如地峡 (69,13) 水在 0/3 |
| 水 + 城中心 | 成立，60° 弯也算 |
| 湖 | **算**水域：(64,22)、(65,22)、(25,21) 唯一水域是湖，引擎允许 |
| 河 | **不算**：内陆河网城 10 个临河格引擎一个都不给 |
| 三面以上临水 | 只有在存在合法的一对边时才允许 |
| 已建运河 | 引擎在同一座城建成 1 条运河后，对该城的运河可建格返回**空列表**；是"一城一条"还是"运河不能相邻"未分离（没有合适的测试地形），**未编码** |

拟合结果：80 个有引擎答案的格里本规则与引擎**零偏差**；旧保守版误杀 0、误放 26（10 格纯因"临河放行"，16 格几何不成立）。数字与四格误放的地形见 [tests/bench/results/canal_multi_summary.txt](../../tests/bench/results/canal_multi_summary.txt)，逐格原始数据由 `tests/bench/probe_canal.lua` 按 seed 重跑得到。

## 第三步：多图复核（2026-11-25 下午）

45 局（10 局随机图 + 35 局 Dido 海岸种子），逐城扫描 1267 个陆地格：

| 量 | 数 |
|---|---|
| 引擎给出答案的格 | 465（其余 802 格：内陆城，引擎对运河返回空列表，没有真值） |
| 其中 DMT 也允许（可用来判规则） | 337 |
| 规则与引擎一致 | 333（98.81%） |
| 误杀（引擎允许、规则拒绝） | **0** |
| 误放（引擎拒绝、规则放行） | 4 |

四条误放都出在同一类地形：一格宽的地峡/小湖，两端是同一片水域，或城中心已经被水包围。
试过的代理都不成立：按"水种相同就拒绝"会误杀 (62,32)、(49,24)（同为 COAST，引擎允许）；
按"直穿优先、不许改弯"会误杀 (62,32)。真正的判据是水域连通体，Lua 没有 API（`Plot` 不暴露），
洪水填充又放不进求解循环，所以**不实现**。

多图还查出一条可以编码的：**5 面是水的格子**（只剩一个陆地角）上 60° 弯等于在开阔水面切角，
引擎拒绝（seed1009 的 (62,33)）。已加进 `CanalSidesJoin`：弯道的外侧三条边至少有一条是陆地。
加之前 208 格里误放 2、加之后 1、误杀仍是 0。

## 第四步：对照社区结论（知乎「文明6 运河到底怎么建？」）

| 说法 | 我们的实测 |
|---|---|
| 平地才行（沙漠/草原/平原/雪地/冻土，无丘陵） | 一致，`District_ValidTerrains` 就是这么列的 |
| 尾端是水域（海/湖），首端是城中心或水域 | 一致；**湖算**，**河不算** |
| 只能 0° 或 60°，120° 不行 | 一致（相隔 3 或 2，相隔 1 的格子引擎全部拒绝） |
| 不能三向连接（三面水，或两面水+城中心） | 部分成立：三面水的格子多被拒；但我们的数据里也有三面水被允许的（(9,24)、(27,22)），按"存在合法的一对边"判更贴近数据 |
| 水路两侧都要有完整陆地 | 一致，我们按"弯道中间那条边 + 外侧至少一条边是陆地"实现 |
| **两条运河不能相邻；一城可以建多条** | **一致，已实测**：在 (8,33) 建一条后，相邻的 (9,34) 从引擎列表消失、距离 2 的 (10,34) 仍在。规划里相邻的两条运河也拒绝 |
| 巴拿马运河可以和普通运河相邻、接成长链 | 未建模（本模组只认 `DISTRICTS_XP2.Canal` 区域行，不认奇观），相邻奇观会被误拒 |

## 测试

`tests/offline/spec_canal.lua`（15 条）：规则识别、内陆格被拒、水对水直穿、水+城中心、只有一条边（城中心或水）被拒、60° 弯、三面水不成通道、已建运河只是一条边、规划中城中心算边、城中心钉单独不够、丘陵留给 DMT、河不算边、同回合新增钉子能生效（缓存只存地图）、非运河不变、引擎有列表时以引擎为准、未解锁仍被拦、求解器不选内陆格。
