智能区域规划器的工作流

一个维护者、一个合作者，加上 Claude Code 的主会话和它派出去的子 agent，怎样从一条 Issue 走到创意工坊上的新版本；哪些步骤已经自动化，哪些仍由人决定。流程本身都写在公开仓库里，下文各处附了文件链接。

01全流程

  • 需求一律先记成 Issue：维护者在对话里说的，由代理来提。
  • bug 直接修；功能和优化先调研，方案由维护者在对话里或合作者在 Issue 下明确回复定了，再写代码。
  • 一个 Issue 一个分支、一个 PR，相关的测试过了就合并；整套测试留到发版前跑一次。
  • bug 确认时、功能方案定了时才挂里程碑，里程碑就是一个版本；不做的写明原因后关掉，以后再说的打 later 标签。
  • 合并到 main 不会到玩家手里，打了 tag 的版本才会。

参考：docs/maintaining.md「一轮工作的流程」sdp-issueIssue 示例：#82 的调研与决定

02角色与会话

  • 方案由维护者在 Claude Code 对话里拍板，或由合作者在带 auto 标签的 Issue 下明确回复（选定方案、逐条回答）来定；两人意见不同以维护者为准。只修 bug 的版本按规则自动发，其余的发版只等维护者的话。
  • 主会话管全局：提 Issue、分派、转达决定、管里程碑、更新状态页、跑夜间队列、Issue 监听、改对外页面（创意工坊）、汇报；几行的小修也在这里做。
  • 调研、测量和每个 Issue 的开发交给子 agent，开发的各用自己的 git 工作树；它们任何时候都能派出去，怎么选模型、什么时候交接见第 03 节。维护者点名要看着做的、或改动大来回多的，主会话直接另开子会话（不先问），做完归档。要求一次写完整：会话正在做事时发给它的消息，要等它这一轮结束才看得到。
  • 维护者事先同意不用问的事（各种评论、自己分支的提交和 PR、自动合并、测试、里程碑、到期的修 bug 版本）对每个会话和子 agent 都有效，它们不再请示，也不等转来的同意；要等维护者的事只由主会话处理。
  • 需要人确认的问题写到 Issue 上和状态页“要你决定的事”里，工作照常往下走，不停下来等。

03子 agent 怎么派

  • 子 agent 每调用一次工具，都要把整个上下文重读一遍。2026-10-27 统计了已有的子 agent，重读占了花费的绝大部分，思考和输出只占小头。所以省钱先靠上下文短，其次才是选模型和思考强度。统计的数字只写在 docs/maintaining.md 里。
  • 主会话每派一个子 agent、开一个子会话，都按任务选模型和思考强度，并在要求里写上下面的交接规则。

选哪个模型、多大思考强度

模型、思考强度什么活例子
Sonnet、medium要求写清楚的机械活变基、合并已知的改动、重跑测试、跑测量脚本、翻译或同步文档、维护状态页和队列
Opus、medium默认开发已定方案的 Issue、原因已知的 bug、写测试、写调研结论
Opus、high要想得深的求解和计分的设计、合法性规则、原因不明的 bug、给维护者权衡方案的调研，以及 medium 做错过一次的任务
主会话自己始终用 high分派、转达决定、汇报

一个子 agent 从派出到交回

  1. 要求：Issue、分支、已定的事、测什么、机器怎么用，以及这一节的交接规则。给文件路径（Issue、docs/notes/、日志），不把内容贴进去。
  2. 工作：工具输出只取需要的几行（tail、grep），日志写进文件，大文件按段读，不整个读。
  3. 检查点：任务停在这里。开发是写完、离线测试跑过、PR 开了；调研是结论写完；其间的一次提交、一次测量做完也算检查点。
  4. 交回：结果报回主会话；还有要等的事，先挂好会叫醒自己的命令（见下文）。

什么时候交接

约 20 万 token 是信号

上下文过了约 20 万 token，不是马上停：做完手上这一步，到下一个检查点再交接。Opus、high 那一档的活信号是约 40 万，那里积累的推理很难写下来。调试的假设、方案比较做到一半时不交接。新的子 agent 重建上下文本身也要花不少，剩下的调用不多时不必交接。

后续的活换新的

变基、夜间游戏内测试失败、审阅意见，都派一个新的子 agent，附交接说明。白天写代码的子 agent 停在 PR 开了；夜里的测试结果交给新的子 agent 改问题。

交接说明写什么

做完了什么；定了什么、为什么；试过但不行的和原因；还没验证的假设；文件和日志在哪。写进 docs/notes/issue-<编号>-<主题>.md 或自己的临时目录，接手的先读它再做别的。

按这样拆能省多少是估算，还没有实测；两个阈值也是估的。接手的子 agent 因为交接而重做或弄坏了之前的工作时，在这个 Issue 的记录里写一笔，用来调整阈值。

不等不会叫醒自己的东西

会话只在这几种情况下再运行：维护者发消息、它在后台启动的命令结束、子 agent 或子会话回报、定时任务触发、Auto-fix 看到 CI 失败、冲突或审阅评论。CI 通过、自动合并都不叫醒任何人。还有活要做时，结束前在后台启动一个等到事情发生就退出的命令：

  • PR：gh pr checks 编号 --watch，或循环到 PR 的状态是已合并；
  • 第二台机器上的任务：remote.py wait 名字；
  • 夜里另加一个约一小时后的定时兜底。

最后一句话写明什么会叫醒自己。macOS 上夜里无人值守的运行还会被隐私弹窗卡住，开跑前先碰一遍要用的文件夹（docs/dev-macos.md“隐私弹窗”）。

做完就收尾，子 agent 的也算

  • PR 合并后：从 Claude Code 的 PR 栏移除，拉取 main，worktree.py prune --remote 清掉已合并的工作树和本地分支，以及 GitHub 上内容都已在 main 或发版 tag 里的分支（没开过 PR 的调研分支、合回 main 的发版分支）；带着 main 没有的改动的只列出来，状态页上能看到。子 agent 开的 PR 也挂在主会话的 PR 栏上，它自己移不掉，所以子 agent 报告合并后、每次发版后，主会话查一遍 PR 栏，把已合并、已关闭的都移除。
  • 夜间队列里的一项谁跑谁关：跑完马上标成完成并写上结果，白天经维护者同意提前跑的也一样；没关的一项会一直显示在排队。

参考：docs/maintaining.md「子 agent 怎么派」（含统计数字）docs/notes/tools/remote.py

04共用资源：一个游戏、两台机器

几个会话同时开发时，游戏和 CPU 都会被抢。每样资源归一个工具管，工具自己拿锁、排队，会话不用互相商量。

游戏锁

游戏、调试连接、Mods 文件夹只有一套。碰游戏的工具（部署、测试、点击、截图）自己拿锁；别的工作树正拿着，就以退出码 4 停下，可以在后台等锁。退出游戏时放锁。

tools/sdplock.py

本机重活

有第二台机器时，超过约一分钟的计算都排到它上面；本机只跑不到一分钟的小任务，或第二台机器格子全满又不能等的。本机上一次只跑一个，worker 上限按本机配置（白天、夜里可以不同），游戏锁被拿走时自动暂停。不经这两个工具直接启动的计算不进排队，别的会话看不到它；子 agent 也照此办理。

tools/README.md「sdplock.py」

第二台机器

可选，用 ssh 连接，不用装游戏。所有会话共用一个队列，按排队先后分格子；排在前面的任务放不下时，后面放得下的先跑，每个排队任务最多被越过 3 次，独占任务不被越过。任务在工作树的快照里跑，结果取回本机；用完的快照和没人再用的工作树副本一周后自动清掉。

tools/remote.pytools/sdpsched.py

夜间队列

机器有人用时，占屏幕的步骤（真实点击、截图、压力测试、发版前的三种规则集）由各会话排进共用队列，由主会话在本机配置的夜间时段（工作日白天不开游戏）统一跑：队列不空时，主会话安排一个在时段开始后几分钟叫醒自己的一次性定时任务；游戏内测试也可以排进去。周末可按本机配置算作夜间。

05测试分层

  • 每个 PR 只跑和它相关的测试文件，整套离线测试 CI 会跑；三种规则集、真实点击、压力测试在发版前跑一次。
  • 游戏内测试只能晚些跑时（比如要等夜间时段），PR 先开着，测过了再打开自动合并。离线重活放在第二台机器，不和游戏抢 CPU。
  • 改了代码的 PR 先请 Codex 审（tools/codex_review.py），审完、意见处理完再开自动合并；只改文档的不审。Codex 的每条意见先核实：属实的写测试再改，不属实的写明原因，都回复后标为已解决。全程由代理做完，只有要维护者拿主意的意见才进状态页“要你决定的事”并在 Issue 下说明。
  • 汇报时分清“已自动验证”和“需要人确认”，没验证的不说成通过。

06发版

谁来定

只修 bug 的版本自动发，满足任一条即可：

  • 攒够 3 个修复；
  • 离第一个修复合并满 7 天；
  • 修好一个严重 bug：线上版本崩溃、面板不能用，或者方案在普通设置下违反游戏规则。

其余的版本（含功能、优化，或默认值、界面调整，哪怕只升第三位）：测试和准备都做完，报告“可以发了”（里面有什么、测出什么、还剩什么），等维护者说一句“发 vX.Y.Z”。

版本号

按改动的大小定：

  • 第三位：修 bug、文字和提示、界面小改、默认值和参数调整、求解和计分的局部改进（方案会变也算）、性能；
  • 第二位：加了一类新能力（新页签、新玩法开关），或某块功能大改（如计分重做）；
  • 第一位：存档或设置不兼容、依赖变了、整体重做。

版本号不说明方案会不会变：会让同样的设置给出不同方案的改动，在 CHANGELOG 和更新说明里写明。

步骤

  1. 里程碑里的 Issue 都合并后开始。发版前测试：三种规则集的游戏内测试；界面或文字改了加英文界面，界面改了加真实点击和中英截图；压力测试（只改界面的版本不跑）。占屏幕的进夜间队列；求解器或合法性改了再跑离线对比，放第二台机器。
  2. release.py prep 改版本号，起草更新说明，再改成英文在前、中文在后、写给玩家的话。
  3. 功能或限制变了，同步改 README、创意工坊简介、介绍页；自测报告写这一轮。
  4. 开一个发版准备的 PR，CI 过了自动合并。
  5. release.py publish 发 GitHub Release。CI 打出模组压缩包和创意工坊提交包，把介绍页和本页发布到 GitHub Pages。
  6. release.py workshop 用 SteamCMD 上传，再下载回来逐字节比对（也可由合作者在 Windows 上传）。简体中文的标题、简介和图片在物品页上改。
  7. 没做完的 Issue 移到下一个里程碑，关掉这个里程碑，告诉维护者发了什么、查过什么、没查什么。

参考：sdp-releasetools/release.pyrelease.yml示例：v1.5.0

07哪些已经自动化

分四档。前两档不需要人；第三档由代理执行，但要按事先定好的规则判断，或者等人一句话；第四档必须由人来做。

步骤自动化程度怎么做还要人做什么

规律：凡是能由脚本判断对错的（测试、打包、核对上传结果）都交给脚本；需要取舍的（方案、默认值、对外怎么说）留给人；介于两者之间的写成规则（比如“3 个修复 / 7 天 / 严重 bug”），由代理照章执行。

08状态页

状态页是维护者自己看进度用的一个网页：要维护者处理的事、开着的 Issue 和谁该回复、各里程碑的进度和下一步、两台机器上正在跑和排队的任务、夜间队列及结果、最近的发版。

代码在仓库的 tools/status/（用法见 tools/README.md“status/”；服务器端的模板在 tools/status/server/，搭服务器的步骤在同一节）。页面上的内容几乎都是自动生成的：后台一个循环每分钟读一遍两台机器的调度记录，每 5 分钟读一遍 git 和 GitHub（分支和 PR、里程碑、Issue、发版）和夜间队列，概览和每个里程碑的“下一步”由页面从这些数据算出来。发版记录只从 GitHub 来，摘要取自发布说明，不手写。

手写的只有三类，主会话在事情发生的那一步写：要维护者决定的事、调度记录说不清的任务说明（如调研）、里程碑的目标和预计时间。页面的地址、推送用的服务器、账号和机器名只在维护者的本机配置里，不进仓库；推送前脚本会查一遍有没有路径、IP、邮箱和这些词。

09几条约定

不卡在提问上

需要定的事写进 Issue，然后先做别的。方案以维护者在对话里的话，或合作者在带 auto 标签的 Issue 下的明确回复为准；含糊的赞同只当意见。

一个 Issue 一个 PR

小 PR 好审、好回退，分支活得短不容易冲突。CI 一次约 6 分钟，只改文档的只跑校验；往 PR 上推新提交会取消没跑完的那一轮，所以提交攒几个一起推。

先调研、再动手

功能类 Issue 的调研评论固定分“已查证的规则 / 玩家共识 / 个别意见 / 建议方案 / 待定问题”，写给懂游戏、不看代码的人：每个待定问题是一句能直接回答的问话，附上建议；代码位置和公式折叠在末尾。

对外只写自己

README、创意工坊、介绍页只介绍本模组；同类模组只列客观事实的对照表；和它们的对比数据放在开发者文档里。

机器有关的不进仓库

仓库是公开的：worker 数、夜间时段、第二台机器写在本机配置里，仓库只写有哪些项和默认值；账号也不进仓库。反过来，怎么做事的规则都写进仓库，维护者本机的个人规则只留机器、账号和个人的东西，两边不一致以仓库为准。

子 agent 的上下文要短

重读上下文是子 agent 花费的大头。模型怎么选、什么时候交接、交接说明写什么，见第 03 节。

结束前安排好叫醒

CI 通过、自动合并都不会叫醒会话。还有活要做时，结束前在后台挂一个等待的命令，做法见第 03 节最后一段。

收尾不留尾巴

PR 合并后，解除会话和 PR 的绑定、拉取 main、清掉工作树、本地分支和 GitHub 上多出来的分支（worktree.py prune --remote）；子会话做完由主会话归档，只留正在进行的工作。
